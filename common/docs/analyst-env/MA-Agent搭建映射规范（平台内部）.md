# MA Agent 搭建映射规范（平台内部）

> 版本：v1.0 · **平台内部文档**，面向中台研发
> **适用范围：** 基于火山方舟 Managed Agents（MA）底座搭建数字员工（Agent）。本文规定：拿到业务方按《MA Agent 搭建交付规范》交付的资源包后，如何校验、如何映射并构建成 MA 上的 Agent、Environment、Vault、Memory Store 等资源；多个业务方共用同一个 MA 项目时如何区分与治理；可复用能力如何注册与升级；如何变更、升级与回滚。
> 业务方不需要阅读本文。业务方的交付格式见《MA Agent 搭建交付规范》。

---

## 1. 定位与原则

### 1.1 范围

```text
业务方交付                  中台处理                                  MA 上的结果
资源包（交付规范）    ──→  ①接收校验 ②补全 ③编译 ④命名与区分 ⑤apply  ──→  Agent / Environment / Vault
                                                                          / Memory Store / Skill / 会话参数
```

本文覆盖 ① 至 ⑤ 以及之后的版本、升级、回滚。

### 1.2 原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | 业务交付物为唯一输入 | 构建只依据资源包与中台补全项，不依据口头约定 |
| P2 | 业务线标识隔离 | 业务线 ID 全局唯一，所有资源携带它，不依赖名称的偶然唯一 |
| P3 | 以标识定位，不以名称定位 | MA 多数资源允许同名，一律靠元数据标识与注册表中的 ID 定位 |
| P4 | 原子能力集中注册 | 可复用能力只在注册表登记一次，业务线按版本引用 |
| P5 | 密钥与配置分离 | 构建产物与注册表只出现凭证名称、类型、引用，不出现值 |
| P6 | 只读优先、变更可归因 | 初始化与启动阶段不修改既有资源；写入经评审、有版本、有记录 |
| P7 | 幂等 | 同一份清单重复执行，无变化时零写操作 |
| P8 | 平台漂移显式化 | 记录依赖的 MA 版本，平台升级时靠比对发现差异 |

## 2. 业务方与中台的分工

业务方不具备中台的全局视角，因此需要全局视野的决定由中台做，只有业务方知道的内容由业务方提供：

| 事项 | 业务方 | 中台 |
|---|---|---|
| 业务目标、使用对象、验收用例 | **提供并确认** | 汇总 |
| 业务知识、提示词的业务内容 | **提供并维护** | 审核结构与完整性，补充平台约束 |
| 外部系统与凭证提供人 | **提供** | 判断凭证类型、登记、存入密钥存储 |
| 记忆库内容与读写权限 | **决策** | 提示风险、显式落地 |
| 业务线 ID、资源命名、元数据 | 使用中台分配的业务线 ID | **分配（全局唯一）、校验、强制** |
| 模型、上下文长度、压缩策略 | 提出效果与合规要求 | **选型并配置**（含成本与合规） |
| 沙箱依赖与资源规格 | 提出需要什么 | **校验版本下限与清单内部自洽、锁定版本** |
| 可复用能力 | 提出需求、贡献实现 | **统一登记、版本管理、引用治理** |
| 对象存储挂载与产物存储 | 提出需要保留什么 | **统一规划桶、前缀、保留期** |
| 平台版本、升级、灰度 | 被通知、配合验收 | **主导** |
| 额度、成本、监控 | 被告知 | **主导** |

| # | 校验 | 依据 |
|---|---|---|
| 1 | 路径为 `ma-resources/<业务线ID>/<数字员工ID>/`，两级 ID 合法且与 `registry/employee.json` 一致；`identity/coordinator/identity.md`、`registry/` 存在 | 交付规范第 2 章 |

| 4 | `environment.json` 的依赖均带版本下限 | 交付规范 5.3 |
| 5 | `connections.yaml` 每条写明域名、变量名、提供人，且无凭证值 | 交付规范 5.4 |
| 6 | 每个记忆库已逐个决策；选可修改的写明内容类型、巡检人、巡检频率与备份来源 | 交付规范 5.5 |
| 7 | 引用的可复用能力均已登记，版本范围合法 | 交付规范第 6 章 |

## 4. 业务线标识与多业务方兼容

### 4.1 为什么必须有全局唯一的业务线标识

同一个 MA 项目内，各资源对"同名"的处理并不一致，因此**不能靠名称区分业务方**：

| 资源 | 同名再建 | 元数据 | 标签 | 按名称服务端过滤 |
|---|---|---|---|---|
| Agent | 允许，得到不同 ID | 支持 | 支持（`[{key, value}]`） | 支持 |
| Environment | **拒绝**（项目内名称唯一，返回冲突） | 支持 | — | **不支持** |
| Vault | 允许 | 支持 | — | **不支持** |
| Memory Store | 允许 | 支持 | — | 支持 |
| Skill | 以内容指纹区分版本 | — | — | — |

由此得到三条硬约束：

1. **Environment 名称必须全项目唯一**，因此名称必须带全局唯一的业务线 ID；
2. **Agent、Vault、Memory Store 允许重复，同名会造成静默混淆**（两个业务方各建一个同名 Agent，系统不会报错），因此**不得以名称作为定位依据**；
3. **列表接口不是可靠的查找手段**（部分资源不支持过滤；项目内资源数量已较多；列表没有完整的分页标记），定位必须依赖注册表中记录的 ID。

这三条共同要求：每个资源都要带一个**全局唯一、由平台控制**的标识，这个标识就是业务线 ID。

### 4.2 业务线 ID 与数字员工 ID

| 标识 | 规则 |
|---|---|
| 业务线 ID `<topic>` | 小写字母、数字、连字符，3 到 24 位；**由中台统一分配，全局唯一**，分配后不可变更；不得与保留标识 `platform` 重复 |
| 数字员工 ID `<emp>` | 小写字母、数字、连字符，3 到 24 位；在业务线内唯一；由业务方提出、中台确认；分配后不可变更 |
| 资源完整标识 | `<topic>.<emp>.<role>` |

- `<topic>`、`<emp>` 来自业务交付物的路径 `ma-resources/<业务线ID>/<数字员工ID>/`；
- **业务线 ID 全局唯一是整个命名与区分机制的前提**：资源名称、Environment 唯一性、元数据校验、产物存储前缀、额度统计，都依赖它；
- `platform` 为中台保留的业务线 ID，用于中台持有的共享资源（共享原子能力、共享只读记忆库），业务方不得申请；
- 回收的业务线 ID 永久保留，不重新分配，避免标识复用造成混淆。

### 4.3 资源命名

| 资源 | 名称规则 | 示例 |
|---|---|---|
| Agent | `<topic>-<emp>-agent` | `sales-assistant-agent` |
| 子 Agent | `<topic>-<emp>-sub-<name>-agent` | `sales-assistant-sub-cleaner-agent` |
| Environment | `<topic>-<emp>-env`（**必须唯一**） | `sales-assistant-env` |
| Vault | `<topic>-<emp>-vault` | `sales-assistant-vault` |
| Memory Store | `<topic>-<emp>-mem-<purpose>` | `sales-assistant-mem-playbook` |
| Skill 展示名 | `<atomic-id>@<内容指纹前 12 位>` | `sales.report@3a9c1e0b77d2` |
| Session 标题 | `<topic>/<emp>/<task_id>` | `sales/assistant/T-1024` |

名称仅用于人读。**程序定位一律使用元数据标识加注册表 ID。**

### 4.4 元数据与标签

所有顶层资源创建时必须携带以下元数据，值均为字符串：

| 键 | 含义 | 示例 |
|---|---|---|
| `ma-registry.topic` | 业务线 | `sales` |
| `ma-registry.employee` | 数字员工 | `assistant` |
| `ma-registry.role` | `agent` / `environment` / `vault` / `memory` / `skill` | `agent` |
| `ma-registry.owner` | 责任团队（与注册表一致） | `sales-data` |
| `ma-registry.managed-by` | 创建与维护它的工具或流水线 | `ma-build` |
| `ma-registry.spec` | 遵循的本规范版本 | `1.0` |
| `ma-registry.version` | 对应的业务线发布版本 | `1.2.0` |
| `ma-registry.stage` | `dev` / `staging` / `prod` | `prod` |

规则：

- Agent 同时写入标签 `[{"key":"topic","value":"<topic>"},{"key":"emp","value":"<emp>"}]`，用于 Agent 列表的快速检索；
- **更新元数据必须先读后合并**：更新是整体替换，只传部分键会丢失其余键；
- 描述（`description`）写人读说明与责任人联系方式，不承载程序依赖的信息；
- 元数据不得包含凭证、个人信息、业务敏感内容；
- 缺少任一必填元数据的资源视为无主资源，巡检时标记并通知责任团队。

### 4.5 定位与防误操作

查找顺序：

1. 注册表中记录的资源 ID（主）；
2. ID 缺失或失效时，按元数据 `topic` + `employee` + `role` 筛选：Agent、Memory Store 可先用名称服务端过滤缩小范围，其余资源在客户端过滤全量列表；
3. 命中多个时**停止并报告冲突**，不得自行择一。

写入前必须校验目标资源的元数据 `topic` 属于调用方被授权的业务线，不属于一律拒绝。**不得按名称删除或覆盖资源**，只能按 ID 且校验业务线归属后操作。

### 4.6 共享与隔离

| 类别 | 处理 |
|---|---|
| 同一业务线下多位数字员工 | 资源完全独立：每位员工各有自己的 Agent、Environment、Vault、记忆库，**互不共用** |
| 员工之间需要共用的内容 | 各自保留副本；需要统一维护、统一升级的，登记为原子能力（第 5 章）并引用 |
| 跨业务方共用的能力 | 登记为原子能力（第 5 章），由中台持有，业务方按版本引用 |
| Memory Store 跨业务方共享 | **默认不允许**；确需共享的，由中台创建只读共享库，业务线 ID 为 `platform`，业务方只能只读挂载 |
| Vault 与凭证 | 永远按业务线隔离 |
| Environment | 一位数字员工一个，不跨员工、不跨业务方共用；因此**不存在跨员工、跨业务线的依赖冲突**，也不需要合并 |
| 额度与并发 | 按业务线统计；超限由中台限流 |

## 5. 原子能力注册表（对接说明）

可被多个业务线复用的最小能力（Skill、工具、MCP、业务知识、模板、提示词片段）统一在**原子能力注册表**登记，业务线按版本引用，不得复制。

**注册表的设计（表结构、状态机、API、升级流程、运维要求）见独立文档《原子能力注册表设计》**，建表脚本见 `registry/atomic-registry.schema.sql`。本章只说明业务线构建流程与注册表的对接点。

### 5.1 业务线怎么用注册表

| 环节 | 做法 | 对应注册表接口 |
|---|---|---|
| 声明引用 | 业务方在 `registry/skills.json`、`tools.json` 中写 `id`、`range`、`used_by` | `PUT /refs` |
| 解析并锁定 | 构建时为每个 `(智能体, 阶段)` 按 `range` 选最高合法版本并锁定 | `POST /refs:resolve` |
| 取回内容 | 按版本的地址下载并校验指纹 | `GET /capabilities/{atomic_id}/versions/{version}` |
| 写锁定清单 | 回填资源锁定清单（7.5）的 `atomic` 段，**与注册表保持一致** | `GET /agents/{topic}/{employee}/{agent_role}/capabilities` |
| 升级影响面 | 发布新版本或平台升级时，找出受影响的智能体 | `GET …/versions/{version}/impact` |
| 回滚 | 引用的锁定版本回退 | `POST /refs/{ref_id}:rollback` |

### 5.2 构建时的校验

`plan` 阶段必须通过（任一失败即阻断，已列入 7.3）：

1. 引用的每个原子能力在注册表中存在；
2. 版本状态允许当前阶段：`candidate` 只能用于 `dev`、`staging`，不得进入 `prod`；`retired` 不可被新引用；`deprecated` 告警；
3. 版本在 `range` 内、依赖可满足、所需凭证已在 `connections.yaml` 声明、`compat` 与当前 `ma_runtime` 相符；
4. 资源锁定清单与注册表中的锁定记录一致，不一致视为漂移。

### 5.3 平台升级时的使用

平台升级（见 9.4）时，先按 `compat` 在注册表中筛选受影响的版本，再用 `impact` 找到受影响的智能体，按 A、B 类变更走完整流程。

### 5.4 与业务线标识的关系

原子能力标识 `atomic_id` 形如 `<owner_topic>.<name>`，其中 `<owner_topic>` 是提供该能力的**业务线 ID**，或中台保留的 `platform`（中台持有的共享能力）。业务线 ID 的规则见 4.2；标识的校验规则见《原子能力注册表设计》。

## 6. 映射：交付物到 MA 资源

### 6.1 总映射

| 业务交付物 | MA 资源 | 字段 / 落点 |
|---|---|---|
| 路径 `ma-resources/<业务线ID>/<数字员工ID>/` 与 `registry/employee.json` | 清单与元数据 | `manifest.yaml` 的 `topic`、`employee`、`version`、`owner`；资源元数据 `ma-registry.topic`、`employee`、`owner`、`version`。两处必须一致，不一致则退回 |
| `identity/coordinator/`（身份、编排、交接） | Agent | `system`，按 6.2 严格拼接 |
| `subagent/<名称>/` | 子 Agent | 每个子智能体生成一个独立 Agent，`system` 拼接规则同上 |
| 模型诉求（收集表） | Agent | `model.*`，由中台选型 |
| `skills/`、引用的 `skill` 类原子能力 | Skill → Agent | Skill 版本 + `skills[]` |
| 引用的 `mcp` 类原子能力、`connections.yaml` 中 `kind: mcp` | Agent + Vault | `mcp_servers[]` + `tools[] mcp_toolset` + MCP 类凭证 |
| `tools/` 契约 | 文档 | 实际执行靠 MCP / Skill 脚本 |
| 业务知识目录（`knowledge.yaml` 声明；默认 `knowledge/`） | 专用知识记忆库（只读） | 见 6.8：**每个已声明的知识目录对应一个知识记忆库**，挂载固定 `read_only`；容量由业务方控制、构建时校验，平台不自动切分或拆库；逻辑引用在构建时替换为自然语言指引加精确位置 |
| `knowledge.yaml` | 构建输入 | 决定哪些目录进入知识记忆库；不映射为 MA 资源 |
| `registry/environment.json` | Environment | `config.packages` / `networking` / `env` / `setup_script` |
| `connections.yaml` | Vault / Credential | 见 6.4 |
| `memory/` 与 `memory/stores.yaml` | Memory Store + 会话挂载 | 见 6.5 |
| `io/contracts/` | 不映射 | 供网关与质检校验 |
| 产物保留诉求（收集表） | 产物存储 | `config.tos`，由中台规划 |
| 工作空间（任务、运行） | 会话参数 | 见 6.6 |

### 6.2 Agent

| 要点 | 规则 |
|---|---|
| 名称与元数据 | 按 4.3、4.4 |
| 提示词 | 严格按 6.2.1 拼接；摘要哈希写入锁定清单；不含密钥 |
| 业务口径引用 | 按 6.8 解析逻辑引用，不内联复制；替换结果指向知识记忆库 |
| 压缩策略 | `context_management`，创建会话时固定，修改只对新建会话生效 |
| Skill 列表 | 整体替换语义，必须写完整数组；单个 Agent 最多 50 个 |
| MCP | 整体替换语义；鉴权走 Vault |
| 工具与权限 | 工具集类型以 `ma_runtime.toolset_type` 为准；逐项登记权限策略 |
| 更新 | 必须带当前 `version`；遇版本冲突须重新查询并合并，不得只自增版本号重试 |

#### 6.2.1 系统提示词拼接

`system` 由 `identity.md`、`orchestration.md`、`handoff.md` 按**固定顺序**拼接，平台**不改写、不增删、不调整**业务方的文字，只插入三个固定标题：

```text
# 身份
<identity.md 原文>

# 编排
<orchestration.md 原文>

# 交接
<handoff.md 原文>
```

| 规则 | 说明 |
|---|---|
| 顺序 | 固定：身份 → 编排 → 交接。这是平台的约定，MA 本身对 `system` 的内部结构没有要求 |
| 标题 | `# 身份`、`# 编排`、`# 交接` 由构建器插入；缺少某个文件时，整段（标题加内容）省略，其余顺序不变 |
| 分隔 | 段与段之间保留一个空行 |
| 业务文件内标题 | 必须从二级（`##`）开始；出现一级标题则退回，避免与固定标题冲突 |
| 子智能体 | `subagent/<名称>/` 下的同名文件按同样规则拼接，生成各自独立的 Agent |
| 逻辑引用 | 拼接前先按 6.8 替换逻辑引用 |
| 产物 | 拼接后的完整提示词保存为 `identity/system.md` 的构建产物，并提供给业务方确认 |
| 一致性检查 | 构建时检查：`handoff.md` 提到的角色在 `identity.md` 或 `orchestration.md` 中有定义；同一规则不跨文件重复。发现问题退回，不自动修改 |

**模型字段：**

| 字段 | 方舟模型 | 自带模型（BYOK Direct） |
|---|---|---|
| `id` | 方舟模型目录 ID | 客户模型的实际模型 ID |
| `provider` | — | 必填，网关名称 |
| `base_url` | — | 必填，完整服务地址（到 `/v1/chat/completions`），公网可达 |
| `protocol` | — | 必填，仅 `openai_chat_completions` 或 `anthropic_messages` |
| `token_limits` | — | 必填，三个值均为大于 0 的整数，按模型真实能力填写 |
| 鉴权 | 方舟 Key | 请求级：每次发送事件携带 `X-User-Model-Header-<原始 Header 名>`，不写入 Agent、Session 或清单 |

### 6.3 Environment

由 `registry/environment.json` 编译：

| 业务字段 | Environment 字段 | 规则 |
|---|---|---|
| `dependencies.python` / `node` / `system` | `config.packages.pip` / `npm` / `apt` | 必须带版本下限；只校验**同一份清单内部**是否自洽（同一个包不得有互相矛盾的版本要求），不存在跨员工冲突 |
| `tools[]` | `config.setup_script` | 中台生成安装段：以 `set -e` 开头；下载二进制必须校验 sha256；注明来源；多段用子 shell 隔离 |
| `network` | `config.networking` | `unrestricted` 或限定域名列表 |
| `env_vars[]` | `config.env` | 只允许非敏感配置，构建时再次扫描 |
| `runtime.max_task_minutes` | 会话等待上限（网关） | 不写入 Environment |

名称 `<topic>-<emp>-env`，**项目内唯一**。**Key、Secret、Token、密码一律不得进入 `env`。**

### 6.4 Vault 与凭证

由 `connections.yaml` 编译。每条连接生成一条凭证：

| 业务 `kind` | MA 凭证类型 | 说明 |
|---|---|---|
| `mcp` | `static_bearer` / `mcp_static` / `mcp_oauth` | 创建时立即与 MCP 服务握手，服务不可达则创建失败；按服务鉴权方式选类型 |
| `api_key` | `environment_variable` | 沙箱内是不透明占位符，**出站时**替换为真实值，Agent 看不到密钥；业务方不区分用于接口、命令行还是 SDK，平台统一按同一方式处理 |
| `oauth_token` | `env_oauth` | 带自动刷新时须同时提供过期时间与完整刷新信息 |

字段映射：

| 业务字段 | MA 凭证字段 |
|---|---|
| `secret_name` | `auth.secret_name` |
| `hosts` | `auth.networking`：类型 `limited`，`allowed_hosts` = `hosts`（**必须逐个列出**；无法提前枚举时才允许 `unrestricted`，须评审） |
| `name` | `display_name` |
| `system`、`purpose`、`owner` | 凭证库元数据与注册表 |
| `rotation` | 注册表的轮换计划；到期前由中台通知提供人，更新凭证值（仅密钥值可更新，无需重建） |
| `access`（read / write） | 评审依据：`write` 类连接须安全评审，并在冒烟中验证写入范围 |

规则：

- 同一 Vault 内，`mcp_server_url`（MCP 类）与 `secret_name`（环境变量类）必须唯一，重复创建返回冲突；每个 Vault 最多 100 个凭证；
- 凭证密钥只写不读，创建后无法读回；结构性字段（`secret_name`、`mcp_server_url`、令牌端点、`client_id`）创建后锁定，修改须删除重建；仅密钥值与 `display_name` 可更新；
- **替换仅发生在出站方向**：若客户端用存储的密钥换取临时令牌，返回的令牌会以未脱敏形式进入运行环境，此类流程由业务侧管理令牌交换，须在评审时识别；
- 启动时校验凭证格式的客户端可能拒绝占位符，需在冒烟中覆盖；
- OAuth 刷新要求令牌端点返回 JSON，`access_token` 为字符串，`expires_in` 为整数秒，否则刷新失败；
- 已挂载 Vault 的既有会话感知不到之后新增的凭证，新增后必须新建会话；
- 凭证真实值由提供人单独交付，只存入密钥存储与 Vault，不经文档、聊天、邮件；
- Vault 按业务线隔离，不跨业务方共用。

### 6.5 Memory Store

由 `memory/` 与 `memory/stores.yaml` 编译：

| 业务字段 | MA 落点 | 规则 |
|---|---|---|
| `name` | Memory Store 名称 `<topic>-<emp>-mem-<purpose>` | 按 4.3；`knowledge-<目录序号>` 为知识记忆库保留，业务长期记忆库不得使用 |
| 条目文件 | 记忆条目，路径即记忆路径 | 单条不超过 100 KiB；单个库不超过 2,000 条。**长期记忆库与知识记忆库的此上限均由业务方控制，平台在构建时校验，不自动处理**（见 6.8.3） |
| `access` | 会话挂载的 `access` | **逐个记忆库**；未配置的一律按 `read_only` |
| `maintainer`、`purpose` | 注册表（记忆库责任人与用途） | 必填 |
| `allowed_content` / `inspector` / `inspect_cadence` / `backup_source` | 注册表与巡检 | 选 `read_write` 时必填；**`inspector` 指事后巡检人，不是写入前审批人** |

规则：

- **挂载时必须显式下发 `access`，不得省略**：平台挂载时缺省为读写，省略会让未声明的库变成可写；
- **MA 对可写入（`read_write`）的记忆库，没有任何机制能按设定拦截或审批写入内容**；能硬拦截的只有 `read_only`。MA 也没有可调用的历史版本回溯接口（条目虽带 `memory_version_id` 字段，但无法据此查询或还原）。因此写入的内容立即生效，写错或被污染后只能人工改回或从备份重建；
- 选读写的，须登记写入内容类型、巡检人、巡检频率与备份来源，因为智能体处理的不可信内容可能被写入，并在后续会话中被当作可信信息读取；巡检是**事后**手段；
- **内容摘要基线（平台内部措施）**：对 `read_write` 的记忆库，构建器在每次构建与每次发布时，记录该库全部条目的路径与内容摘要，保存为基线（`memory/baseline/<库名>.json`，不含条目正文）。该基线供巡检比对使用：与当前库内容比较，找出新增、被改动、被删除的条目。这是平台为弥补 MA 无版本回溯而做的补偿，**不改变 MA 的行为，也不拦截写入**；基线只能发现变化，不能还原内容，还原依赖 `backup_source`；
- 提示词里"不要写入"只是文字约束，**平台不会据此拦截**，权限以挂载设置为准；
- 单个会话最多挂载 10 个库；**该上限由知识记忆库与业务长期记忆库共用，合计不超过 10**（见 6.8.3）；该数字已明确告知业务方（交付规范 5.2）；
- **知识与长期记忆是两类不同的库，构建时分别建库，不合并**：知识记忆库由平台管理、固定 `read_only`，不由业务方决策权限；长期记忆库由业务方决策读写（`purpose` 不得使用 `knowledge`）；
- 跨业务方共享见 4.6。

### 6.6 会话创建参数

| 要点 | 规则 |
|---|---|
| 记忆库 | `type: memory_store`，显式 `access` |
| TOS 目录 | `type: tos`：`tos_bucket` + `tos_key`，沙箱路径 `/mnt/session/storage/`，只读 |
| 输入文件 | `type: file`，单个会话最多 10 个，运行中可追加 |
| Vault | `vault_ids` |
| Agent 版本 | 灰度、复现、审计时固定版本 |
| 产物存储 | 创建会话时通过环境覆写 `config.tos` |
| 标题 | `<topic>/<emp>/<task_id>`，便于检索与审计 |

**TOS 挂载与产物存储是两个独立配置：**

| | 配置位置 | 沙箱路径 | 用途 |
|---|---|---|---|
| TOS 资源挂载 | 会话 `resources[] type: tos` | `/mnt/session/storage/` | 输入或共享数据 |
| 产物存储 | `config.tos`：`bucket`、`prefix` | `/mnt/session/outputs/` | 交付物的持久位置 |

TOS 挂载规则：

- 一个会话可挂载多个 TOS 目录，完全相同的目录不能重复；
- `tos_key` 必须是以 `/` 结尾的目录，且该前缀下已存在对象，否则创建会话失败；
- 桶必须与 MA 服务同地域，并已在方舟项目中完成授权；
- 预检逐个目录进行，任一目录不可用，整个创建请求失败；
- `memory_store` 与 `tos` 只能在创建会话时挂载。

产物存储规则：

- 交付物需要长期保存的，**必须配置产物存储**；否则落在平台公共存储，到期被清理；
- 优先在创建会话时覆写，不修改可复用的 Environment；
- `bucket` 与 `prefix` 必须同时提供，`prefix` 以 `/` 结尾；
- **多业务方共用同一个桶时，前缀必须包含业务线 ID**：`<topic>/<emp>/`，由中台统一规划；
- 写入前缀为 `{prefix}outputs/{env-id}/{session-id}/`；删除会话不会删除桶中对象，生命周期在对象存储中管理。

| 要点 | 规则 |
|---|---|
| 入口 | 单聊、群聊（群聊须 @ 机器人） |
| 可用范围 | 白名单，留空表示不限 |
| 飞书应用 | 一位数字员工一个应用；权限与事件订阅登记在渠道清单；需订阅长连接接收消息事件，创建版本并发布后生效 |
| 模型鉴权 | 只登记 Header 名与持有人 |
| 会话映射 | 以（会话域、话题、用户）为键，保存会话 ID 与所用版本快照，不含凭证 |

### 6.8 知识的映射与逻辑引用

MA 没有"知识库"的概念。当前决定：**业务知识映射到专用的知识记忆库**，不映射到 Skill。后续可能调整承载方式，**但不影响业务侧的逻辑引用写法**（交付规范 5.2）。

#### 6.8.1 读取方式的约束（已实测）

| 读取方式 | 结果 |
|---|---|
| bash 访问 `/mnt/memory/` | 目录存在但**为空**，读不到记忆条目 |
| 记忆工具 `memory_ls` / `memory_tree` / `memory_read` / `memory_grep` / `memory_search` | 可用；根为 `/`，其下是 `/<记忆库ID>/`，再往下是条目路径 |

因此：

- 智能体只能通过记忆工具读取知识，**不能用文件路径**；
- 记忆库 ID 出现在记忆工具可见的路径里，创建库之后才知道，所以必须由构建器在构建时写入，不能由业务方预先写死；
- 知识库是只读参考资料，**挂载时固定 `access: read_only`**，不由业务方决定。

#### 6.8.2 映射规则

| 步骤 | 规则 |
|---|---|
| 范围 | 只处理 `knowledge.yaml` 声明的目录；未声明时默认 `knowledge/`；未声明的目录不进入知识库 |
| 对应关系 | **一个已声明的知识目录对应一个知识记忆库**，命名 `<topic>-<emp>-mem-knowledge-<目录序号>`。**序号在首次构建时按声明顺序分配并记录在映射表中，此后固定不变**：调整 `knowledge.yaml` 中的声明顺序不改变序号，删除目录不回收序号，新增目录取下一个未用序号；否则调整顺序会让记忆库名称与映射表错位 |
| 文件类型 | `.md`、`.txt`；其他类型阻断并退回 |
| 条目路径 | 条目路径为文件在该知识目录内的相对路径，例如 `/统计口径.md`。因为每个目录对应独立的记忆库，路径中**不再保留目录名**；同名相对路径出现在不同目录时互不冲突，由记忆库区分 |
| 条目内容 | 文件原文，不改写；文件头的"名称、适用范围、版本、负责人"原样保留 |
| 索引条目 | 每个知识记忆库由构建器额外生成一条 `/_索引.md`：列出该库全部条目的路径、名称、适用范围，供智能体先检索再读取；索引由构建器维护，业务方不写，**占用 1 条容量** |
| 挂载 | 固定 `read_only`，显式下发 |
| 变更 | 知识变动只需更新记忆库条目，**即时生效，不需要升级会话**；条目新增、删除、移动须同步更新索引与映射表（6.8.4） |

#### 6.8.3 容量：业务方控制，构建时校验

平台**不自动切分文件，不自动拆分目录或记忆库**。容量由业务方在交付时控制，构建时严格校验，超限则失败并退回。

| 限制 | 数值 | 来源 | 校验方式 |
|---|---|---|---|
| 单个文件大小 | 不超过 100 KiB（102,400 字节） | MA 单条记忆上限 | 逐个文件检查字节数 |
| 单个知识目录的文件总数 | 不超过 **1,990** | MA 单个记忆库 2,000 条上限，扣除索引 1 条，并预留 9 条余量 | 递归统计目录内全部文件数 |
| 知识记忆库数 + 业务长期记忆库数 | 合计不超过 **10** | MA 单个会话最多挂载 10 个记忆库 | 统计两类库的总数 |

校验失败时，错误必须包含：超限项、实际值、限制值、涉及的文件或目录，以及处理指引（引导业务方按知识的主题粒度调整，见交付规范 5.2）。例如：

```text
知识目录 "业务口径" 文件数 2,013，超过上限 1,990。
请按主题划分为多个知识目录并在 knowledge.yaml 中分别声明，参见《MA Agent 搭建交付规范》5.2。
```

**拆分不要求说明，只做一致性检查：**

- 平台**不要求**业务方说明拆分原因，也不记录"从哪个目录拆分而来"——拆分是业务方按知识粒度做出的组织决定，不需要审批；
- 构建器只检查结构合法：知识目录互不嵌套、都在资源包内、`knowledge.yaml` 中无重复声明；
- 同一相对路径出现在多个知识目录中是允许的（各目录对应独立的记忆库，互不冲突），不告警；
- 拆分后，逻辑引用按业务方更新后的目录名解析，构建器不做自动改写；引用的文件不存在时按引用校验失败处理。

**名额的计算：**

- 业务方交付的知识目录数加上长期记忆库数，合计不得超过 10，这个数字已在交付规范 5.2 明确告知业务方；
- 每个已声明的知识目录占 1 个名额，每个长期记忆库占 1 个名额；
- 合计超过 10 时阻断并退回业务方，错误里列出两类库各自的数量与清单，引导业务方合并主题相近的目录（见交付规范 5.2）；
- 业务方确实需要超过 10 个的，属于平台容量问题，由中台评估（例如改用其他承载方式），**不能通过放宽校验绕过**。

**增量更新时的容量：**

- 更新知识只写入变化的文件；新增文件后目录文件数超过 1,990 时同样阻断；
- 文件被删除后释放的容量立即可用。

#### 6.8.4 映射管理

构建器维护一份映射表，记录每个知识文件到记忆库条目的对应关系，随构建产物保存（`memory/knowledge.map.json`，不含凭证）：

```json
{
  "stores": [
    { "name": "<topic>-<emp>-mem-knowledge-01", "id": "memstore-…", "source_root": "业务口径", "entries": 118 }
  ],
  "files": [
    {
      "source": "业务口径/统计口径.md",
      "sha256": "…",
      "entries": [
        { "store": "<topic>-<emp>-mem-knowledge-01", "path": "/统计口径.md" }
      ]
    }
  ]
}
```

- 映射表是逻辑引用替换、增量更新、清理失效条目的唯一依据；
- 知识库中**只由构建器写入和删除**条目，业务方、智能体、人工均不得直接改动；巡检发现映射表之外的条目，按异常处理；
- 增量更新：比对 `sha256`，只写入变化的文件；已删除的文件在知识库中同步删除；
- 记忆库 ID 只出现在映射表与锁定清单中。

#### 6.8.5 逻辑引用的解析

业务方在提示词与知识文件里写：

```text
{{knowledge:业务口径/统计口径.md}}
```

引用的第一级是知识目录名（仅声明了一个知识目录时可省略），构建器据此找到对应的知识记忆库，根据映射表替换为**自然语言指引加精确位置**，替换后不再保留逻辑引用标记：

```text
（使用记忆工具查阅记忆库 <记忆库ID> 中的 /统计口径.md）
```

| 情形 | 替换结果 |
|---|---|
| 单个知识目录 | `（使用记忆工具查阅记忆库 <ID> 中的 <条目路径>）` |
| 多个知识目录 | 通过引用中的目录名确定记忆库，同样输出 `（使用记忆工具查阅记忆库 <该目录对应ID> 中的 <条目路径>）` |
| 一个文件对应的是业务方拆分后的多个文件 | 业务方在提示词里分别引用各文件，构建器逐个替换，不自动合并 |

- **不写死工具名**（`memory_read` 等）：工具名属于平台，可能变化；指引只说"使用记忆工具"，由模型选择具体工具；
- 路径与记忆库 ID 来自映射表，随知识更新自动刷新；
- 替换发生在 6.2.1 拼接之前。

校验（任一失败即阻断，退回业务方）：

1. 被引用的文件存在于 `knowledge.yaml` 声明的目录中；
2. 声明了多个知识目录时，引用必须带目录名；仅声明一个时目录名可省略；
3. 业务文件中不含运行环境绝对路径（以 `/mnt/`、`/workspace/` 开头）；
4. 替换完成后文本中不再含 `{{` 标记；
5. 构建后抽样读取：对每个被引用条目，用记忆工具读取一次，内容摘要与映射表一致。

#### 6.8.6 后续可能调整

承载方式（记忆库 / Skill / 其他）可能调整。调整时：业务侧交付物与逻辑引用写法不变；变化限于映射规则与替换结果，需同步更新本节、映射表格式与冒烟用例。

> 业务方写的是逻辑位置，真实位置只在构建时生成。把路径或记忆库 ID 硬编码在提示词里，库重建或知识迁移后会失效，因此它们不出现在业务交付物中。

## 7. 构建产物与定位

### 7.1 构建目录

交付物是业务信息；构建产物是把它编译成 MA 资源所需的声明：

```text
ma-build/<topic>/<emp>/
├── README.md
├── registry/
│   ├── manifest.yaml             # 主清单
│   ├── resources.lock.json       # 资源锁定清单（7.5）
│   ├── version_mapping.md
│   └── CHANGELOG.md
├── identity/
│   ├── agent.json                # 由交付物 identity/coordinator/ 编译
│   ├── system.md                 # 按 6.2.1 拼接的完整提示词，供业务方确认
│   └── subagents/<名称>/         # 每个子智能体一份 agent.json 与 system.md
├── environment/
│   ├── environment.json          # 由 registry/environment.json 编译
│   └── setup.sh
├── vault/
│   └── credentials.spec.yaml     # 由 connections.yaml 编译；无值
├── memory/                       # 设置记忆时才有
│   ├── memory-store.json
│   ├── knowledge.map.json        # 知识映射表（6.8.4）
│   ├── baseline/<库名>.json      # 可写记忆库的内容摘要基线（6.5），无正文
│   └── <路径>/*.md
├── session/
│   └── session.yaml              # 挂载、权限、产物存储
├── channel/
│   ├── channels.yaml
│   └── gateway.env.example
└── verification/
    ├── smoke.md
    └── acceptance.md             # 由业务验收用例整理
```

### 7.2 主清单

```yaml
spec_version: 1
topic: <topic>
employee: <emp>
version: 1.0.0
owner: { team: "", primary: "", backup: "" }

ma_runtime:
  docs_snapshot: "YYYY-MM-DD"
  toolset_type: agent_toolset_20260916
  base_agent: ark_agent_preview
  api_base: https://ark.cn-beijing.volces.com/api/v3
  region: cn-beijing

stage: dev                        # dev | staging | prod

resources:
  agent:       { name: <topic>-<emp>-agent,  file: identity/agent.json }
  environment: { name: <topic>-<emp>-env,    file: environment/environment.json }
  vault:       { name: <topic>-<emp>-vault,  spec: vault/credentials.spec.yaml }
  memory:      []                  # 例：[{ name: <topic>-<emp>-mem-<purpose>, access: read_only }]
  session:     { file: session/session.yaml }

atomic_refs:
  - { id: platform.report-cover, range: "^1.2.0", used_by: [coordinator, "subagent:cleaner"] }
```

### 7.3 编译与校验

`plan` 阶段必须通过以下校验，任一失败即阻断：

1. **接收校验**：第 3 章全部通过；
2. **业务线标识**：所有资源名称、元数据、标题中的 `<topic>`、`<emp>` 与交付路径一致，且 `<topic>` 属于调用方被授权的业务线；
3. **唯一性**：Environment 名称在项目内无冲突；元数据标识下同角色资源无多个命中；
4. **引用**：每个原子能力存在、状态允许当前 `stage`、版本在 `range` 内、依赖可满足、所需凭证已在 `connections.yaml` 声明；
5. **兼容**：原子能力的 `compat` 与当前 `ma_runtime` 相符；
6. **凭证**：构建产物与环境变量中无密钥明文；每条凭证的域名已逐个列出；
7. **记忆**：每个挂载的记忆库权限已显式声明；
8. **数量**：未超平台上限（Skill 50、工具 128、环境变量 64、Vault 凭证 100、会话文件 10）；**会话记忆库（知识记忆库加长期记忆库）合计不超过 10**；知识文件 ≤ 100 KiB、单个知识目录文件数 ≤ 1,990，任一超出阻断并退回业务方（见 6.8.3）。

### 7.4 版本固定

业务线发布时，原子能力引用的 `range` 解析为确切的 `pin`，写入锁定清单。**没有锁定清单的业务线不得发布到 `prod`。**

### 7.5 资源锁定清单

记录当前发布版本各资源的确切身份，是升级、回滚、`plan` 比对的依据：

```json
{
  "topic": "<topic>", "employee": "<emp>", "version": "1.0.0", "stage": "prod",
  "ma_runtime": { "docs_snapshot": "YYYY-MM-DD", "toolset_type": "agent_toolset_20260916" },
  "agents": [
    { "role": "coordinator",      "id": "agent-…", "version": 3, "system_sha256": "…", "model_fp": "…" },
    { "role": "subagent:cleaner", "id": "agent-…", "version": 1, "system_sha256": "…", "model_fp": "…" }
  ],
  "environment": { "id": "env-…", "config_sha256": "…" },
  "vault":       { "id": "vlt-…", "credentials": ["<name>"] },
  "memory":      [ { "id": "memstore-…", "access": "read_only", "entries_sha256": "…" } ],
  "atomic":      [
    { "id": "platform.report-cover", "agent": "coordinator",      "pin": "1.2.3", "fingerprint": "…", "skill_id": "skill-…" },
    { "id": "platform.report-cover", "agent": "subagent:cleaner", "pin": "1.0.5", "fingerprint": "…", "skill_id": "skill-…" }
  ]
}
```

- 由 `apply` 生成并随发布提交，**不得手工编辑**；
- `plan` 将清单、锁定清单、平台现状三方对照；
- 资源 ID 只允许出现在锁定清单中，不出现在其他文件；
- 主智能体与每个子智能体各占一条记录，引用的原子能力按智能体分别锁定。

### 7.6 会话版本快照

灰度、复现问题、事后审计时，需要知道某个会话按什么版本运行。创建会话时固定 Agent 版本，并在网关侧记录：

```text
会话 = Agent 版本 + Environment + Vault + 记忆库及权限 + TOS 挂载 + 产物存储 + 原子能力 pin 列表 + 模型鉴权 Header 名称
```

该记录保存在网关侧，不含凭证值。

## 8. 原子能力（Skill）打包

| 项 | 要求 |
|---|---|
| 目录 | ZIP 内只有一个顶层目录 `<skill_name>/`，目录下直接包含且仅包含 1 个 `SKILL.md` |
| 体量 | 不超过 500 个文件；上传原始总大小不超过 30 MiB；解压后单文件不超过 30 MiB、总计不超过 120 MiB |
| 版本指纹 | 内容变化即新版本（同一 Skill ID）；重新打包同样内容不得产生新版本 |
| 展示名 | `<atomic-id>@<内容指纹前 12 位>` |
| 登记 | 上传后将 `skill_id` 与版本写入注册表地址字段 |
| 自检 | 打包后重新解压并实际运行 |

## 9. 变更、版本与升级

### 9.1 变更类别与对已有会话的影响

| 类别 | 变更内容 | 对已有会话的影响 | 上线方式 |
|---|---|---|---|
| A | Agent：模型、提示词、工具、MCP、Skill 引用 | 不自动切换。须对处于空闲且上一轮正常结束的会话调用升级，或新建会话 | 新建会话固定新版本灰度，再升级存量 |
| B | Environment：依赖、脚本、环境变量、网络、产物存储 | 同 A | 同 A |
| C | Vault：新增或修改凭证 | 既有会话感知不到新增凭证 | 新建会话 |
| D | 会话资源：记忆库、TOS（含权限）；新增知识记忆库（含业务方新增知识目录） | 只能在创建时挂载 | 新建会话 |
| K | 知识内容变更（记忆库条目更新，库数量与挂载不变） | 即时生效，已有会话下一次读取即可见 | 更新条目与映射表；不需升级会话 |
| E | 文件资源 | 运行中可追加 | 即时 |
| F | 原子能力版本 | 不直接影响；须更新引用并随 A 上线 | 随 A |
| G | 网关配置 | 不影响 MA 资源 | 重启网关 |
| H | 模型请求鉴权 | 不影响 MA 资源 | 重启网关 |
| I | 飞书应用权限与事件订阅 | 无 | 创建版本并发布后生效 |
| J | 注册表：原子能力状态、引用关系 | 无直接影响 | 按《原子能力注册表设计》第 7 节 |

补充约束：

- 升级会话不能换绑其他 Agent 或 Environment；同一会话不能同时存在多个升级请求，且须先处于空闲；
- 不再使用的 Agent、Environment、会话优先归档，归档后保留配置与历史，已有会话继续使用创建时的快照；删除前必须确认无关联会话；
- **业务方的在途任务保持原版本不变，新任务使用新版本**。

### 9.2 变更流程

1. **变更说明**：写明类别（A 至 J）、涉及的清单与原子能力、预期影响面；
2. **`plan`（只读）**：把清单、锁定清单、平台现状三方对照，并执行 7.3 校验；差异须与变更说明一致；
3. **评审**：至少一名非作者；涉及密钥、网络、外发、产物存储、跨业务方共享的须安全评审；
4. **`apply` 到 `dev`**，通过后晋级 `staging`，再到 `prod`，不得跳级；
5. **冒烟**：执行 `verification/smoke.md`，保留真实输出；
6. **灰度**：新建会话固定新版本验证，再升级存量空闲会话；运行中的会话记入待升级清单，不强行中断；
7. **回写**：`apply` 重新生成锁定清单，更新 `CHANGELOG.md`、`version_mapping.md`、注册表；并向业务方反馈上线结果。

**回滚：** 以上一发布版本的锁定清单为目标：Agent 回退到其记录的版本；原子能力将 `pin` 回退；Environment 用上一版清单重新 `apply`。回滚同样走灰度。

### 9.3 版本与指纹

- 数字员工版本语义化：A、B、C 类不兼容变更升主版本；新增能力升次版本；仅文案、记忆、修复升修订版本；
- 指纹：Agent 模型配置指纹、原子能力内容指纹、提示词摘要，均写入锁定清单，`plan` 时比对；
- 变更记录条目：

```markdown
## 1.1.0 — YYYY-MM-DD
- 类别：A, F
- 变更：<做了什么>
- 原子能力：platform.report-cover 1.2.3 → 1.3.0
- 影响面：存量空闲会话需升级；运行中会话记入待升级
- 验证：smoke.md 用例 1-8 通过
- 回滚：Agent 回退到上一版本；pin 回退
```

### 9.4 MA 平台升级

平台升级（文档合集变化、接口、字段、工具集类型、术语）时，不等故障出现：

1. **同步文档**：执行文档同步脚本，贴出标题、类型、字段名的变化；
2. **比对**：核对 `ma_runtime` 与各清单、各原子能力 `compat` 中的类型、字段、接口路径，是否仍出现在最新文档中；
3. **分级**：
   - **兼容**：一致，只更新 `docs_snapshot`；
   - **漂移**：使用的类型或字段已不在最新文档中。在 `dev` 新建会话验证旧值是否仍可用、行为是否一致，再决定升级时机，不得凭文档推断；
   - **破坏**：旧值被拒绝或行为改变。按 A、B 类走完整流程，并通过 `referenced_by` 找出所有受影响的业务线、数字员工、智能体与原子能力；
4. 更新 `ma_runtime`，执行 9.2；
5. 评估架构图谱文档是否需要同步。

## 10. 安全红线与验收

### 10.1 安全红线（违反即驳回）

1. 交付物、清单、注册表、PR、日志、产出文件中不得出现任何密钥明文，只写名称、类型、引用；
2. Environment 的 `env` 不得存放密钥；
3. 初始化与启动阶段只读：不得更新、删除、重建已存在的资源；
4. 不得按名称删除或覆盖资源；写入前必须校验业务线归属；
5. 不得对生产资源先删后建；需要重建时先归档、再新建、再切换；
6. 记忆库的读写权限逐个声明、默认只读，挂载时显式下发；可写记忆库必须登记巡检人、巡检频率与备份来源，并保持内容摘要基线；不得向业务方暗示平台会拦截或审批写入；
7. 凭证只用于声明的域名，不得放宽为不限域名，除非无法枚举且经评审；
8. 跨业务方不得共享 Vault、Environment、可写记忆库；
9. 测试资源使用独立阶段标识并登记，仅按精确 ID 清理；正式资源不进入清理范围；
10. 业务数据进入模型的范围必须与业务方确认的结论一致；
11. 文档与脚本里的启动命令必须写明解释器与环境，不得依赖全局安装的同名命令。

### 10.2 `plan` 报告必含

- 清单与平台现状的差异，按资源、字段列出；
- 7.3 校验结果；
- 漂移项（平台上有、清单里没有）与无主资源；
- 缺失的凭证与待补充项，标记待补，对应项不创建，不得用占位值替代；
- 对存量会话的影响：可升级、需新建、待升级；
- 受影响的引用方（来自注册表）。

### 10.3 冒烟用例最低要求

| # | 用例 | 通过标准 |
|---|---|---|
| 1 | 单聊发一句话 | 收到回复，会话创建成功 |
| 2 | 触发一次沙箱命令 | 真实命令输出，不是文字复述 |
| 3 | 读取 TOS 挂载目录 | `/mnt/session/storage/` 下能列出预期文件 |
| 4 | 读取记忆库，并尝试写入 | 能引用记忆；写入按权限被允许或拒绝，与清单一致；知识记忆库写入必须被拒绝。可写记忆库：写入成功后，基线比对能发现该变化 |
| 4a | 按逻辑引用替换后的指引读取知识 | 对每个被引用条目，使用记忆工具能读到，内容与映射表一致；知识记忆库写入被拒绝 |
| 5 | 调用每个已接入的 MCP 与外部系统 | 每个至少成功一次；凭证只对声明的域名生效 |
| 6 | 产出一个文件到 `/mnt/session/outputs/` | 能取回；配置了产物存储后，桶中对应前缀下能找到对象 |
| 7 | 越界请求（索要密钥、无关泛聊） | 拒绝并引回职责 |
| 8 | 业务线归属校验 | 资源元数据中的 `topic` 与交付路径一致；用另一业务线的标识操作被拒绝 |
| 9 | 业务验收用例 | 业务方提供的用例全部通过，验收人签字 |

### 10.4 合入前检查单

- [ ] 接收校验（第 3 章）全部通过
- [ ] 业务线 ID、数字员工 ID、资源命名、元数据符合第 4 章，无必填缺失
- [ ] 引用的原子能力均已登记，状态与版本范围合法，`pin` 已写入锁定清单
- [ ] 新增的可复用能力已登记注册表，字段完整、地址可取回

- [ ] 依赖已锁定版本下限；初始化脚本带校验和
- [ ] 每条凭证的域名已逐个列出
- [ ] 每个记忆库的读写权限已逐个声明，挂载时显式下发；可写记忆库已登记巡检人、巡检频率、备份来源，并已生成内容摘要基线
- [ ] 交付物需要长期保存的，已配置产物存储，前缀含业务线 ID

- [ ] 变更记录与版本号已更新；回滚方案已写
