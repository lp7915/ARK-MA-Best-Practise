# MA Agent 搭建交付规范

> 版本：v1.1 · **面向业务方及其研发**（相对 v1.0 的变化见文末"修订记录"）
> **适用范围：** 基于火山方舟 Managed Agents（MA）底座搭建数字员工（Agent）。本文规定：为了让平台在 MA 底座上为你们搭建数字员工，你们需要交付什么、格式是什么、可复用的能力怎么登记、后续如何增量更新。
> **你们交付的是什么：** 一位数字员工的"资源包"——岗位提示词、业务知识、可执行能力、外部系统声明、长期记忆。一位数字员工对外是一个入口（主智能体），背后可以有多个子智能体（见 2.3）。平台据此在 MA 上创建并运行对应的 Agent。后续更新可以只交付变化的部分（见 2.4）。
> 平台如何在 MA 上落地，不是业务方需要关心的内容，见平台内部的《MA Agent 搭建映射规范》。
> 配套：《能力需求收集表》（收集这份交付规范里需要业务方提供的内容）。

---

## 1. 你需要交付什么

在 MA 底座上搭建一位数字员工，需要你们交付一个**资源包**（一个业务线下可以有多位数字员工），保存可以跨项目、跨任务复用的稳定内容：业务知识、岗位提示词、可执行能力、外部系统契约、输入输出结构。

资源包**不包含**：密钥与密码、某次任务产生的数据、会话与运行记录。

平台会在你们交付的基础上补全模型选型、资源命名、依赖版本、存储规划等需要全局视野的部分，并把结果回给你们确认。

### 1.1 三条基本原则

| 原则 | 含义 |
|---|---|
| 信息唯一归属 | 每类信息只放在一个位置，别处只引用、不复制 |
| 稳定与实例分离 | 资源包只放稳定内容；任务、运行、会话产生的信息不放进来 |
| 密钥不入包 | 资源包里只写凭证的名称、类型、用途、提供人，不写值 |

---

## 2. 资源包目录

一个业务线下可以有多位数字员工，**每位数字员工交付一个独立的资源包**：

```text
ma-resources/
└── <业务线ID>/
    └── <数字员工ID>/
        ├── identity/                      # 主智能体（目录名即主智能体名称，业务方自定，如 pm）
        │   └── <主智能体名称>/
        │       ├── identity.md            #   角色、职责、边界
        │       ├── orchestration.md       #   工作流程与分工
        │       └── handoff.md             #   与其他角色的交接规则
        ├── subagent/                      # 内部专业子智能体（有则放）
        │   └── <子智能体名称>/
        │       ├── identity.md
        │       ├── orchestration.md       #   可选
        │       └── handoff.md             #   可选
        ├── knowledge/                     # 业务知识（目录名与内部结构为建议，可自定义，见 5.2）
        │   ├── standards/                 #   生产与验收口径
        │   ├── templates/                 #   业务内容模板
        │   ├── examples/                  #   可复用案例（标准、边界、错误、回归）
        │   └── glossary.md                #   术语表
        ├── tools/                         # 外部能力契约：只写接口、用途、所需凭证类型
        │   ├── _overview.md
        │   └── <工具名>.md
        ├── skills/                        # 可直接执行的封装能力
        │   └── <能力名>/
        │       ├── SKILL.md
        │       ├── prompts/
        │       ├── scripts/
        │       └── references/
        ├── io/                            # 输入输出契约：写明"收什么、产什么"，供检查与对接（见 5.6）
        │   ├── README.md
        │   └── contracts/                 #   机器可读的结构定义，一个输入或产物一个文件
        ├── memory/                        # 长期记忆（仅需要时设置，见 5.5）
        │   └── <路径>/*.md                #   一条记忆一个文件，目录结构即记忆路径
        ├── acceptance/                    # 验收用例（见 9.2）
        │   └── cases.yaml
        ├── knowledge.yaml                 # 声明哪些目录属于业务知识（见 5.2）
        ├── connections.yaml               # 需要连接的外部系统与凭证声明（见 5.4），不含凭证值
        ├── change-set.yaml                # 仅增量交付时提供（见 2.4）；首次交付的完整包没有
        └── registry/                      # 本资源包的登记与版本
            ├── employee.json              #   业务线 ID、数字员工 ID、名称、负责人、版本
            ├── agents.json                #   智能体清单与各智能体的资源挂载（见 2.3）
            ├── skills.json                #   引用与自有的可复用能力（见第 6 章）
            ├── tools.json
            ├── environment.json           #   运行环境需求（见 5.3）
            └── version_mapping.md         #   人可读的版本说明
```

不适用的目录可以省略，但 `identity/<主智能体名称>/identity.md`、`registry/employee.json` 与 `registry/agents.json` 必须存在。

### 2.1 标识规则

| 标识 | 规则 |
|---|---|
| 业务线 ID | 小写字母、数字、连字符，3 到 24 位；**由平台统一分配，全局唯一**（不同业务方之间不会重复），业务方提出建议、平台确认；`platform` 为平台保留，不能使用 |
| 数字员工 ID | 小写字母、数字、连字符，3 到 24 位；在业务线内唯一；由业务方提出、平台确认 |
| 子智能体名称 | 小写字母、数字、连字符；在该数字员工内唯一 |

以上标识确认后**不可变更**。路径中的两级 ID 必须与 `registry/employee.json` 一致。

### 2.2 同一业务线下多位数字员工

- 每位数字员工的资源包**完全独立**，不设共享目录；
- 多位员工都需要的内容（例如同一套口径），**各员工各存一份副本**，副本以各自资源包为准，修改一方不会影响另一方；
- 如果某项内容确实需要多位员工、甚至多个业务线**统一维护、统一升级**，应把它登记为可复用能力（见第 6 章），通过引用使用，而不是复制。

### 2.3 一位数字员工的多智能体结构

一位数字员工对外只有一个入口，即**主智能体**（名称由你们自定，例如 `pm`、`assistant`）：直接面向使用者，按自己的编排规则理解需求，把任务分派给背后的**子智能体**，再汇总结果。

- 主智能体与子智能体在资源上**没有差异**：每个智能体都有自己的身份定位（提示词），主、子智能体都可以使用同一类资源——Skill、外部工具（MCP）、业务知识、长期记忆、外部系统凭证。差别只在入口和调用关系：使用者只接触主智能体，子智能体由主智能体分派；
- 调用关系按一层设计：主智能体 → 子智能体，子智能体之下不再嵌套子智能体。子智能体之间是否直接交接，以主智能体的分派和各自 `handoff.md` 为准，平台实际支持的消息路由方式会在回执中说明；
- 分派规则（什么任务交给谁、什么条件下分派）写在主智能体的 `orchestration.md`；子智能体向谁回传、回传什么写在各自的 `handoff.md`。平台不改写提示词（见 5.1），因此**新增或删除子智能体时，主智能体里对应的分派说明需要你们同步更新**。

#### 智能体清单与资源挂载：`registry/agents.json`

`agents.json` 是**智能体维度的总览**：列出每个智能体，以及每个智能体各自挂载哪些资源。资源本身仍只在原位置声明一份（唯一归属，见第 3 章），这里只按名称引用。

```json
{
  "agents": [
    {
      "name": "pm", "role": "entry",
      "description": "面向用户的入口：理解需求、分派任务、汇总结果",
      "mounts": {
        "skills":      ["platform.report-cover", "intent-router"],
        "tools":       ["crm-mcp"],
        "knowledge":   ["业务口径"],
        "memory":      ["playbook"],
        "connections": ["crm-api"]
      }
    },
    {
      "name": "hotspot", "role": "subagent",
      "description": "热点分析。适用：…；不适用：…",
      "mounts": {
        "skills":      ["hotspot-miner", "platform.report-cover"],
        "knowledge":   ["业务口径", "话术库"],
        "connections": ["datahub-key"]
      }
    },
    {
      "name": "insight", "role": "subagent",
      "description": "洞察生成。适用：…；不适用：…",
      "mounts": {
        "skills":      ["insight-writer"],
        "memory":      ["playbook"]
      }
    }
  ]
}
```

上例的挂载关系一目了然：

| 智能体 | Skill | 工具（MCP） | 知识 | 长期记忆 | 外部连接 |
|---|---|---|---|---|---|
| pm（主） | platform.report-cover、intent-router | crm-mcp | 业务口径 | playbook | crm-api |
| hotspot | hotspot-miner、platform.report-cover | — | 业务口径、话术库 | — | datahub-key |
| insight | insight-writer | — | — | playbook | — |

**每类挂载引用什么名称：**

| `mounts` 键 | 引用的名称 | 资源在哪里声明 |
|---|---|---|
| `skills` | 可复用能力写注册表标识（如 `platform.report-cover`）；包内自有 Skill 写 `skills/` 下的目录名 | `registry/skills.json`（引用的可复用能力）、`skills/`（自有） |
| `tools` | 工具名 | `registry/tools.json` |
| `knowledge` | 知识目录的 `path` | `knowledge.yaml` |
| `memory` | 记忆库的 `name` | `memory/stores.yaml` |
| `connections` | 连接的 `name` | `connections.yaml` |

规则：

- 智能体 `name`：**由你们自定**，规则同子智能体名称（小写字母、数字、连字符，在该数字员工内唯一，主、子智能体不得重名）。`role` 取 `entry`（主智能体，**有且仅有一个**）或 `subagent`。主智能体的目录是 `identity/<name>/`，子智能体的目录是 `subagent/<name>/`。目录里存在 `subagent/<名称>/` 就必须在清单里登记，反之亦然；
- `description`：一到两句话，写明"适用什么任务、不适用什么"，用于评审时核对分派范围；
- **挂载是显式的**：某个智能体没写的资源就是没挂载，没有"默认所有智能体"，也没有"默认只给主智能体"；
- `mounts` 里引用的名称必须已在对应位置声明，否则退回；已声明的资源**至少被一个智能体挂载**，否则视为多余声明，退回；
- 同一个资源（如同一个 Skill、同一个知识目录）可以被多个智能体同时挂载；同一个可复用能力在不同智能体上的版本范围相同，具体锁定到哪个版本由平台按智能体分别记录；
- 主智能体和子智能体可以挂载**同样的几类资源**，没有哪类资源只能主智能体用；
- Skill 和外部工具（MCP）在平台上确实按智能体分别配置，只有挂载了才可用；
- 业务知识、长期记忆库、外部连接的凭证在平台上属于数字员工级资源，同一次会话内共享。`mounts` 表达你们的设计意图并用于评审和影响核算，**平台暂不承诺对这三类资源做按智能体的访问隔离**；长期记忆库的读写权限（5.5）对所有智能体一致。需要严格隔离的敏感内容，请拆成独立的数字员工；
- 运行环境（`registry/environment.json`）一位数字员工只有一份，所有智能体共用，各智能体需要的依赖合并写在同一份清单里（清单内部必须自洽，见 5.3）。

### 2.4 增量交付：基线与最小增量

数字员工上线后，业务会持续演进：新增一个子智能体、只调整某一个智能体的提示词、补几个知识文件。这类变更**不需要重新交付完整资源包**，可以只交付变化的部分。首次交付必须是完整包。

#### 增量包是什么

增量包使用与完整包相同的目录结构，**只包含新增或修改的文件**，另在根目录提供 `change-set.yaml`：

```yaml
# change-set.yaml
change_id: 20261110-add-hotspot        # 本次变更的唯一编号，由业务方生成
base_version: 1.2.0                    # 本次变更基于的、平台已发布的版本
new_version: 1.3.0                     # 变更后的版本号，按第 7 章规则确定
add_agents: [hotspot]                  # 新增的子智能体；没有则省略
remove_agents: []                      # 要删除的子智能体；没有则省略
remove_entries: []                     # 要删除的资源声明，写法见下；没有则省略
remove_files: []                       # 要删除的文件，相对资源包根的路径；没有则省略
note: 新增热点分析子智能体，并让主智能体分派热点类需求
```

#### 增量包里的文件怎么写

文件分两类，**合并方式不同**：

| 类型 | 文件 | 增量里怎么写 |
|---|---|---|
| **清单类**：由一条条记录组成，每条有名称 | `registry/agents.json`（按智能体名称）、`registry/skills.json`、`registry/tools.json`（按 `id` / 名称）、`knowledge.yaml`（按 `path`）、`connections.yaml`（按连接 `name`）、`memory/stores.yaml`（按记忆库 `name`） | **只写变化的那几条**。增量里的某条记录会**整条替换**基线里同名的那条（不是只改其中一个字段）；没写到的记录不变 |
| **整体类**：一个整体，不拆条 | `registry/environment.json`、`registry/employee.json`，以及所有 `.md`、脚本、知识文件等内容文件 | 写改动后的**完整文件**，整个替换基线里的同路径文件 |

要点：`agents.json` 里每个智能体是一条记录，**包含它的整套 `mounts`**。所以只要改了某个智能体挂载的任何资源，就把**该智能体这一条**（带完整的 `mounts`，不是只写新增的那一项）放进增量，其他智能体不用写。

删除怎么表达（`remove_entries` 的写法是 `<类型>:<名称>`）：

```yaml
remove_entries:
  - "skills:old-skill"        # 类型：skills / tools / knowledge / memory / connections
  - "connections:crm-api"
```

删除一项资源时，所有挂载了它的智能体都必须在同一增量里更新（去掉挂载），否则退回。

#### 规则

1. **省略不是删除**。增量里没有出现的文件、记录、智能体，沿用 `base_version` 的内容；
2. **删除必须显式**。删除智能体、资源声明、文件，只能写在 `remove_agents`、`remove_entries`、`remove_files` 里，不能靠"不在包里"来表达；删除子智能体时，必须同时更新主智能体编排，去掉对它的分派说明（平台只检查编排里是否还出现该子智能体的名称，仍出现则退回）；
3. **新增与修改要分清**。`add_agents` 中的名称在基线里已存在，退回；增量里出现的 `subagent/<名称>/` 既不在基线中、也没写入 `add_agents`，退回；
4. **基线必须是最新的已发布版本**。`base_version` 与平台当前最新已发布版本不一致（别人先发布了新版本），退回，请基于最新版本重新交付；平台会告知差异；
5. **同一次变更只生效一次**。`change_id` 相同、内容也相同的重复提交视为同一次变更，不会重复生效；`change_id` 相同但内容不同，退回；
6. **影响范围由平台核算**。平台合并基线和增量，只更新受影响的智能体：改了谁的提示词、谁的 `mounts` 记录、谁挂载的 Skill 或 MCP 内容，就更新谁，没有变化的不动。运行环境、凭证这类数字员工级资源有变化时，会影响所有智能体，平台会在回执中写明；
7. **提交、构建、接受、发布是四个动作**。提交增量不等于发布；发布沿用第 7.3 节的灰度流程，进行中的任务保持原版本。

#### 只改某个智能体的某个资源：怎么做

下表以子智能体 `hotspot`、主智能体 `pm` 为例。"需要提供"之外的文件一律不用提供。

| 你想做的事 | 需要提供的文件 | `change-set.yaml` |
|---|---|---|
| 改 `hotspot` 的提示词 | `subagent/hotspot/` 下被修改的文件（完整文件） | 只写 `change_id`、`base_version`、`new_version` |
| 改 `hotspot` 挂载的**自有 Skill** `hotspot-miner` 的内容 | `skills/hotspot-miner/` 下被修改的文件 | 同上 |
| 给 `hotspot` **加挂**一个已有的可复用能力 `platform.chart` | `registry/skills.json`：只写 `platform.chart` 这一条（它之前没被任何智能体用过才需要）；`registry/agents.json`：只写 `hotspot` 这一条，`mounts.skills` 里在原有基础上加上 `platform.chart` | 同上 |
| 给 `hotspot` **去掉**一个 Skill `hotspot-miner` | `registry/agents.json`：只写 `hotspot` 这一条，`mounts.skills` 里去掉它。如果没有别的智能体还在用它，且你们要把它彻底删掉，再加下面一行 | `remove_entries: ["skills:hotspot-miner"]`；自有 Skill 的目录文件另在 `remove_files` 列出 |
| 调整 `platform.report-cover` 的版本范围 | `registry/skills.json`：只写这一条。**注意版本范围是能力级的，所有挂载它的智能体都按新范围解析**，只想让某一个智能体升级目前不支持 | 同上 |
| 让 `hotspot` 改用另一个知识目录 | 新知识目录里的文件；`knowledge.yaml`：只写新目录这一条；`registry/agents.json`：只写 `hotspot` 这一条，`mounts.knowledge` 改成新目录 | 同上 |
| 改 `hotspot` 用的某个连接（如换域名） | `connections.yaml`：只写这一条（整条，不是只写改动字段） | 同上 |
| 改某个记忆库的读写权限 | `memory/stores.yaml`：只写这一条 | 同上；该库所有挂载它的智能体都会受影响，平台会在回执中列出 |
| 新增一个子智能体 | `subagent/<名称>/` 提示词文件；`registry/agents.json`：写新智能体这一条（带 `mounts`）**以及主智能体 `pm` 这一条**（因为 `pm` 的编排要加分派说明，`mounts` 若无变化也需带上原样的 `mounts`）；它新用的资源在各自清单里加一条；`pm` 的 `orchestration.md` 完整文件；`acceptance/cases.yaml` 中新增分派路径的用例 | `add_agents: [<名称>]` |
| 删除一个子智能体 | `pm` 的 `orchestration.md`（去掉分派说明）；它独占的资源按上面方式删除 | `remove_agents: [<名称>]`，独占资源写入 `remove_entries` |
| 改运行环境（依赖、网络） | `registry/environment.json` 完整文件 | 同上；会影响所有智能体 |

**完整例子：只给 `hotspot` 加挂 Skill `platform.chart`**

增量包内容只有三个文件：

```text
change-set.yaml
registry/skills.json
registry/agents.json
```

```yaml
# change-set.yaml
change_id: 20261112-hotspot-chart
base_version: 1.3.0
new_version: 1.4.0          # 新增能力，次版本
note: hotspot 加挂 platform.chart，用于生成图表
```

```json
// registry/skills.json —— 只写新增的这一条
[ { "id": "platform.chart", "range": "^1.0.0" } ]
```

```json
// registry/agents.json —— 只写 hotspot 这一条，mounts 要写完整
{ "agents": [
  { "name": "hotspot", "role": "subagent", "description": "热点分析。适用：…；不适用：…",
    "mounts": {
      "skills": ["hotspot-miner", "platform.report-cover", "platform.chart"],
      "knowledge": ["业务口径", "话术库"],
      "connections": ["datahub-key"]
    } }
] }
```

平台合并后，只有 `hotspot` 会更新；`pm` 和其他智能体保持原样。

增量交付的回执在 2.5 的基础上，另包含：**合并后的完整资源包**；新增、修改、未变的文件和智能体清单；删除项；受影响的智能体；新版本号。你们确认后才进入后续验收与发布。

### 2.5 平台的构建回执

每次构建（首次交付或增量）后，平台把结果回给你们确认。回执至少包含下面这些，**区分"你们写的"和"平台定的"**：

| 内容 | 说明 |
|---|---|
| 提交标识与版本 | 交付内容的摘要；增量的 `change_id`、`base_version`、`new_version` |

| 完整系统提示词 | 每个智能体：你们写的原文、每个占位符替换后的结果、拼接后的完整提示词（见 5.7） |
| 依赖的实际版本 | `environment.json` 里的版本下限最终解析成的实际版本 |
| 可复用能力的锁定版本 | 每个智能体引用的每个能力，最终锁定到哪个版本 |
| 模型与环境 | 平台选定的模型、运行环境、任务时长与网络范围 |
| 知识与记忆库 | 各知识目录和记忆库的落地情况、读写权限 |
| 验收结果 | 每个用例的结论（见 9.2） |
| 状态 | 构建失败则给出失败原因和位置；成功则说明处于测试、灰度还是已发布 |

> 动态外部依赖（外部服务、可写记忆库、外部数据）无法完整冻结快照，回执会写明访问时点和限制，不保证事后可以完全重放同一次运行。

## 3. 信息放在哪里（唯一归属）

| 信息类型 | 唯一存放位置 |
|---|---|
| 业务方法、口径、标准、模板、案例、术语 | 业务知识目录（默认 `knowledge/`，可自定义，由 `knowledge.yaml` 声明） |
| 主智能体的角色、行为边界、提示词 | `identity/<主智能体名称>/` |
| 子智能体的角色、行为边界、提示词 | `subagent/<子智能体名称>/` |
| 外部能力的接口与所需凭证类型 | `tools/` |
| 可执行的封装能力 | `skills/`（可复用的须登记，见第 6 章） |
| 输入输出的结构定义 | `io/contracts/` |
| 需要连接的外部系统与凭证声明 | `connections.yaml` |
| 跨任务共享的长期记忆 | `memory/` |
| 运行环境需求（依赖、网络、环境变量） | `registry/environment.json` |
| 密码、API Key、Token、Cookie、私钥 | **外部密钥存储**，不进入资源包 |

边界规则：

- 业务知识放在业务知识目录里；某次任务的原始材料、聊天记录、失败文件**不要**放进资源包。
- 提示词需要引用业务口径时，使用逻辑引用（见 5.2）指向业务知识目录中的文件，不要在提示词里复制一份。
- 业务内容模板放在业务知识目录里；可执行的提示词和脚本放在对应能力的目录下。
- 案例（标准、边界、错误、回归）也放在业务知识目录里。
- `registry/` 只放登记与版本信息，不放任务、会话、运行产生的编号。

## 4. 工作空间（运行时数据，不属于资源包）

以下是平台运行时的信息归属，**业务方不需要交付**，但需要理解信息如何流转，以便决定哪些内容该放进资源包、哪些不该。

**两个相互独立的目标：** 工作材料与知识组织是两件事。

| 目标 | 由谁承载 | 内容 |
|---|---|---|
| 文件与共享协作位置 | **Workspace**（工作空间） | 工作材料、任务过程、成果，以及团队、项目的共享与共同编辑 |
| 知识、记忆、索引与读取规范 | **知识与记忆库**（对应本规范 5.2、5.5） | 业务知识、长期记忆 |

两者可以使用共同的底层存储，但职责保持独立：Workspace 里的材料**不会自动变成业务知识**，业务知识要进入资源包（5.2）。

**三类默认空间：**

| 默认空间 | 主要用途 | 访问边界 |
|---|---|---|
| Agent Workspace | 数字员工个人的工作材料、任务过程和成果；**Task 工作空间归入它的根范围** | 由该数字员工与获授权的管理者使用，不向协作者默认开放全部内容 |
| Team Workspace | 团队材料共享与共同编辑 | 按团队任职及授权提供；放入共享空间意味着遵守该空间的共享范围 |
| Project Workspace | 项目材料共享与共同编辑 | 有项目任职或相应授权时提供；项目之间相互隔离 |

下面是**逻辑结构**，用目录、数据库记录或对象元数据承载均可；对象存储里的物理路径由平台生成，不要求与此一致：

```text
Agent Workspace/{数字员工}/                  # 员工个人工作材料、任务过程和成果
├── personal/{user_id}/                     #   私聊：某个用户与该员工的个人上下文
│   ├── context/                            #     个人偏好、局部上下文（不公开到项目）
│   └── connections/                        #     个人连接（只存凭证引用，不存值）
├── groups/{chat_id}/                       #   群聊：该群的局部上下文与交流习惯
│   └── context/
└── tasks/{task_id}/                        #   Task 工作空间（归入 Agent Workspace，不放进项目目录）
    ├── task.json                           #     任务目标与交付要求；发起人、来源通道、
    │                                       #     所属项目（如有）、本任务采用的材料与资源包版本
    ├── context/                            #     本任务采用的上下文（采用的版本，不取代原始来源）
    ├── inputs/                             #     本任务的输入材料
    └── runs/{run_id}/                      #     一次运行
        ├── run.json                        #       本次运行冻结的资源包版本、模型、参数
        ├── attempts/                       #       每次执行或重试，真实回执与日志
        ├── artifacts/                      #       正式产物与产物清单
        ├── validation/                     #       针对某个明确产物的检查结果
        └── delivery/                       #       从产物导出、交付给使用方的版本

Team Workspace/{team_id}/                   # 团队材料共享与共同编辑
├── sources/                                #   团队共享材料
└── connections/                            #   团队连接（只存凭证引用）

Project Workspace/{project_id}/             # 项目材料共享与共同编辑，项目间隔离
├── project.json                            #   项目信息
├── context/                                #   项目事实与口径（项目内共享）
├── sources/                                #   项目原始资料
├── connections/                            #   项目连接（只存凭证引用）
└── registry/                               #   本项目采用的资源包版本等登记
```

私聊和群聊是**通道**：私聊里的偏好与局部上下文留在 `personal/`，群聊的留在 `groups/`，不会因此公开到项目。项目事实和口径默认在项目内共享，放在 Project Workspace。任务不论在私聊还是群聊发起，都归入 Agent Workspace，通过 `task.json` 关联发起人、通道和项目。

| 概念 | 含义 | 与资源包的关系 |
|---|---|---|
| 任务 | 一项有目标和交付要求的工作，其工作空间归入 Agent Workspace | 引用资源包的版本 |
| 运行 | 一次实际执行；记录采用的全部版本与参数 | 冻结引用的资源包版本 |
| 执行记录 | 运行下的每次执行或重试，过程文件在此 | 不是交付源 |
| 产物 | 正式、可引用、可送检、可交付的结果 | 由任务产生，不回写资源包 |
| 质检 | 对明确产物的检查记录 | 引用资源包中的验收口径 |
| 交付 | 从产物导出、打包给使用方的版本 | 不是后续编辑的源文件 |

流转原则：

1. 任务采用的材料来自用户输入，或 Agent、Team、Project 各空间；任务里记录的是"本任务采用的版本"，不取代原始来源；
2. 运行开始时冻结所采用的全部版本，任务后续变化不影响已有运行；
3. 过程文件不是交付源；需要保留、复用、送检、交付的结果才固化为产物；
4. 质检、交付都必须指向明确的产物，不以文件名或"最新"推断；
5. 交付件不是源文件，修改应回到产物重新生成；
6. **放入共享空间意味着遵守该空间的共享范围**：Team Workspace 的内容对团队授权成员可见，Project Workspace 的内容只对项目成员可见，Agent Workspace 的内容不默认对协作者开放；
7. 反馈按影响范围沉淀：只影响本次的保留在任务；对团队或项目后续有价值的放入对应的 Team、Project Workspace；可跨项目复用的方法、标准、案例，作为业务知识更新提交给平台评审，进入资源包的业务知识目录。

### 4.1 运行追溯的最低关联信息

上面的目录是逻辑结构，不要求每一层都建文件。运行下的各类记录至少要能追溯到唯一对象：

| 记录 | 最低要关联的信息 |
|---|---|
| 运行 | 数字员工、任务、运行编号（有项目的加项目）；采用的资源包版本（含各智能体版本）；实际使用的模型与环境 |
| 执行记录 | 属于哪个运行；第几次执行或重试；真实回执 |
| 产物 | 产物编号、版本、内容摘要、来源（由哪个运行、哪个智能体产生） |
| 质检 | 被检的产物、依据的规则版本、执行者、结论、证据位置 |
| 交付 | 来源产物、交付回执 |

运行记录**不回写**资源包。运行中产生的、值得沉淀的内容（新的口径、案例、提示词改进），经评审后作为资源包的新版本提交，原始日志仍留在运行空间，资源包的变更记录只引用证据位置（对应第 7.2 节）。

### 4.2 持久化、接续与多人协作

**哪些内容会被保留**，业务方需要分开看待，不要推定"整个工作目录都会保留"：

| 内容 | 保留方式 |
|---|---|
| 资源包（提示词、知识、能力声明等） | 由平台按版本保存，见第 7 章 |
| 任务产物 | 只有放入产物输出位置、且平台已为你们配置了产物存储的，才长期保留；否则按平台的默认保留期清理。需要长期保存的产物，请向平台说明 |
| 会话内的临时文件、中间结果 | **不承诺保留**，会话结束或沙箱重建后可能丢失 |
| 执行日志、验证证据 | 保留位置与期限由平台在回执中说明 |

**长任务的接续**：

- 阶段结束或中断前，把目标、采用的资源包版本、已有产物、已完成与未完成的检查、未决问题和下一步写入产物或任务记录；恢复时先核对这份记录与实际文件，再继续；
- 同一会话内继续、新会话接手是不同的情形，验收时分别验证。**不要假定新会话能看到上一个会话的临时文件**，需要接续的内容必须落在产物里；
- 已经发生、但结果未知的外部动作（发送消息、写外部系统等），先查回执确认结果，不要直接重放；

**多人协作**：

- 同一数字员工的资源包由多人修改时，各自基于明确的版本（`base_version`，见 2.4）修改，平台接收时检查冲突，不会覆盖他人已发布的内容；
- 材料在 Agent、Team、Project 三类空间之间的共享与隔离，由平台按团队任职、项目任职与授权配置，**不能由目录名或群聊名称推定**；需要共享或隔离的范围请向平台说明。

## 5. 各类内容的格式要求

### 5.1 智能体身份（`identity/`、`subagent/`）

| 文件 | 内容 | 要求 |
|---|---|---|
| `identity.md` | 角色、职责范围、适用场景、能力边界、可交付成果与格式 | 必须提供；写清"能做什么、不能承诺什么" |
| `orchestration.md` | 工作流程、各步骤用到的能力、质量标准 | 描述流程，不写一次性任务的具体数据 |
| `handoff.md` | 与其他角色交接的条件与内容 | 写明触发条件、交接信息、接收方 |

**这三个文件共同组成该智能体的系统提示词。平台严格按下面的固定顺序和格式拼接，不改写、不增删、不调整你们写的文字（仅替换占位符，见 5.7）：**

```text
# 身份
<identity.md 全文>

# 编排
<orchestration.md 全文>

# 交接
<handoff.md 全文>
```

- 顺序固定：**身份 → 编排 → 交接**；
- `# 身份`、`# 编排`、`# 交接` 三个标题由平台插入，文件内容原样放在对应标题下；
- 某个文件不存在时，对应的标题和内容整段省略，其余顺序不变；
- 文件内部的标题**从二级（`##`）开始**，不要使用一级标题，以免与平台插入的标题冲突；
- 拼接得到的完整系统提示词会作为构建产物提供给你们确认。

因为是严格拼接，三个文件必须彼此一致：

- 同一条规则只写在一个文件里，不重复、不矛盾；
- `handoff.md` 中提到的角色，必须在 `identity.md` 或 `orchestration.md` 中有定义。

**子智能体：** 每个子智能体放在 `subagent/<子智能体名称>/` 下，文件含义、拼接顺序和格式与主智能体完全相同，各自生成独立的系统提示词。内部专业子智能体是专业实现的一部分，不等于独立的岗位。

其他要求：

- 不得包含密钥、令牌、个人账号；
- 业务口径、术语写在业务知识目录里，用逻辑引用（见 5.2），不要复制。

### 5.2 业务知识

业务知识指口径、标准、模板、案例、术语等供智能体查阅的稳定内容。

#### 目录与结构：可自定义

`knowledge/` 及其下的 `standards/`、`templates/`、`examples/`、`glossary.md` **只是建议的组织方式**，你们可以按业务习惯自行命名和组织，例如 `业务口径/`、`话术库/`、`docs/`。

唯一的要求是：**用 `knowledge.yaml` 声明哪些目录属于业务知识**，平台只会处理被声明的目录。

```yaml
# knowledge.yaml
roots:
  - path: knowledge              # 相对资源包根的目录；可声明多个；由哪些智能体挂载见 2.3
    description: 默认知识目录
  - path: 业务口径
    description: 各业务线统一口径
```

规则：

- `path` 是相对资源包根的目录，不能越出资源包，不能互相嵌套；
- 没有 `knowledge.yaml` 时，默认只处理 `knowledge/`；
- 没有声明的目录，平台**不会**作为业务知识处理，里面的内容智能体读不到；
- 目录内的文件使用 Markdown（`.md`）或纯文本（`.txt`）；
- 每个文件开头写明：名称、适用范围、版本、负责人；
- 案例中某次任务的原始错误材料不要放入知识目录。

#### 容量

按知识本身的粒度组织：一个知识目录是一组主题相关、内聚的知识（例如"统计口径"、"话术库"、"典型案例"），一个文件讲清一件事。**不需要为迁就平台而改变知识的组织方式。**

当前平台底座对文件大小、目录文件数、知识目录与长期记忆库的数量有一些上限，具体数值、触及时的临时处理、平台的解决进度，见《MA Agent 搭建容量限制说明》（本规范附录）。超限时构建会直接失败并退回，错误里会指出超限项；平台不会自行切分文件或拆分目录。这些上限由平台逐项解决，解决后无需业务方改动。

建议的组织方式（可不采用）：

| 建议目录 / 文件 | 内容 |
|---|---|
| `standards/` | 生产口径与验收口径，每个标准一个文件，写明适用范围与版本 |
| `templates/` | 业务内容模板（报告结构、话术、表格） |
| `examples/` | 案例，按"标准 / 边界 / 错误 / 回归"分类 |
| `glossary.md` | 术语表，一个术语一条，写明定义与同义词 |

#### 引用写法

提示词（`identity/`、`subagent/`）和知识文件里需要引用知识时，**使用占位符，不要写路径**（占位符清单见 5.7）：

```text
{{knowledge:标准/口径.md}}
```

- 冒号后面是**相对于某个已声明知识目录的路径**。只声明了一个知识目录时，直接写该目录下的相对路径；声明了多个时，写成 `目录名/相对路径`，例如 `{{knowledge:业务口径/统计口径.md}}`；
- 路径中的目录名、文件名以你们自己的为准，平台不要求使用 `standards/` 等固定名称；
- 平台把逻辑引用替换为智能体能够直接理解的指引，你们不需要也不应该知道知识存放在哪里；
- 被引用的文件必须存在于已声明的知识目录中，否则构建失败并退回；
- 同一个相对路径在多个知识目录里重复出现时，必须写成带目录名的形式，否则退回；
- 不要在提示词和知识文件里写运行环境的路径（例如以 `/mnt/`、`/workspace/` 开头），写了会被退回；
- 可复用能力自己的文件（`SKILL.md`、`scripts/` 等）按第 6.5 节的要求编写，不受本条限制。

> 知识具体存放在平台的哪里，业务方不需要关心，平台负责保持引用与实际位置一致。

### 5.3 运行环境需求（`registry/environment.json`）

只描述**需要什么**，具体如何搭建由平台决定。

```json
{
  "dependencies": {
    "python": ["pandas>=2.0", "openpyxl>=3.1"],
    "node": [],
    "system": []
  },
  "tools": [
    { "name": "<命令行工具>", "purpose": "<用途>", "source": "<来源或下载地址>" }
  ],
  "network": { "mode": "unrestricted", "allowed_hosts": [] },
  "env_vars": [
    { "name": "TZ", "value": "Asia/Shanghai", "purpose": "时区" }
  ],
  "runtime": { "max_task_minutes": 10, "notes": "" }
}
```

规则：

- 依赖**必须写明版本下限**，如 `pandas>=2.0`，不写版本的不予接收；
- `env_vars` **只放非敏感配置**（时区、开关、非密钥地址）；任何密钥一律放 `connections.yaml`；
- 需要限制外网访问的，在 `allowed_hosts` 列出域名；
- 每位数字员工有独立的运行环境，**不会与其他数字员工或业务线的依赖冲突**；但同一份依赖清单内部的版本要求必须自洽（例如不能同时要求 `numpy<2` 与 `numpy>=2`），不自洽时构建失败并退回；
- 一位数字员工的主智能体和所有子智能体**共用这一份运行环境**，各智能体需要的依赖合并写在同一份清单里（见 2.3）；
- 上例中的 `max_task_minutes: 10` 和 `network.mode: unrestricted` 只是格式示例，不是平台默认值，也不代表对外网访问的授权；实际的任务时长上限、网络范围以平台回执为准。

### 5.4 外部连接与凭证声明（`connections.yaml`）

每个需要访问的外部系统一条。**只声明，不含凭证值。**

```yaml
connections:
  - name: <连接名>               # 业务内唯一，如 crm-api
    system: <目标系统名称>
    purpose: <用途，一句话>
    access: read | write         # 读写性质
    kind: api_key | mcp | oauth_token   # api_key：用密钥访问接口、命令行或 SDK；oauth_token：会过期、需要刷新的令牌
    hosts: [api.example.com]     # 会被访问的域名，必须逐个列出
    secret_name: CRM_API_KEY     # 在运行环境中以此变量名使用
    owner: <凭证提供人>
    rotation: <轮换周期，如 90d>
    notes: ""
```

规则：

- `hosts` 必须逐个列出被访问的域名，凭证只会被用于这些域名；
- 只写 `secret_name`（变量名），不写任何值；真实值由提供人交给平台存入密钥存储；
- `kind` 只有三种：`api_key`（用固定密钥访问接口、命令行工具或 SDK，不必区分是哪一种）、`oauth_token`（令牌会过期、需要刷新）、`mcp`（访问 MCP 服务，还需填写服务地址和协议）；
- 需要 OAuth 并带自动刷新的，额外写明令牌端点、是否需要客户端密钥，**这些值同样不入包**；
- 一条连接对应一类用途，不要把多个系统共用一个条目；
- `kind: mcp` 时，在同一条目里补充 MCP 服务信息（见下）；"用什么协议访问服务"和"用什么方式鉴权"是两件事，分别写；
- `kind: oauth_token` 时，补充令牌刷新信息（见下）；
- 凭证是数字员工级资源，同一次会话中各智能体共享，由哪些智能体挂载写在 `agents.json`，不构成按智能体的访问隔离（见 2.3）。

**MCP 连接示例**（服务地址和鉴权方式是公开信息，可以写进资源包；密钥值不写）：

```yaml
  - name: datahub-mcp
    system: DataHub
    purpose: 查询热点数据
    access: read
    kind: mcp
    hosts: [mcp.datahub.example.com]
    mcp:
      url: https://mcp.datahub.example.com/mcp     # 服务地址，必须可从公网访问
      auth: api_key                                # 鉴权方式：api_key（固定密钥）| oauth（令牌，需要刷新）| none
      key_injection: header                        # auth 为 api_key 时：密钥怎么传给服务，bearer | header | query
      key_injection_name: X-API-Key                # key_injection 为 header 或 query 时必填：请求头名或参数名
    secret_name: DATAHUB_MCP_KEY                   # 变量名，不写值
    owner: 张三
    rotation: 90d
```

- 平台的 MCP 声明只有服务地址，没有单独的"协议"字段，所以这里不需要写协议；
- `key_injection` 为 `bearer` 时按 `Authorization: Bearer <密钥>` 传递，不要写 `injection_name`，密钥本身也不要带 `Bearer` 前缀；
- 同一个智能体里，同一个 MCP 服务地址不能重复声明。

**OAuth 令牌示例**（需要自动刷新时）：

```yaml
  - name: feishu-oauth
    system: 飞书开放平台
    purpose: 读取用户文档
    access: read
    kind: oauth_token
    hosts: [open.feishu.cn]
    secret_name: FEISHU_ACCESS_TOKEN
    oauth:
      token_endpoint: https://open.feishu.cn/open-apis/authen/v2/oauth/token   # 令牌刷新地址，公开信息
      client_auth: client_secret_post              # 刷新时的客户端认证方式：none | client_secret_basic | client_secret_post
    owner: 李四
    rotation: 30d
```

- `client_auth` 为 `none` 表示公共客户端，不需要客户端密钥；另外两种都需要客户端密钥，由提供人单独交给平台；
- 令牌刷新要求令牌端点返回 JSON，其中 `access_token` 为字符串、`expires_in` 为整数秒；不满足时刷新会失败，请提前确认；
- **只有敏感值不进资源包**：令牌本身、刷新令牌、客户端密钥、`client_id` 一律由提供人单独交给平台；服务地址、鉴权方式、令牌端点是公开信息，可以写；
- 创建 MCP 类凭证时，平台会立即与服务握手，服务不可达则创建失败。

### 5.5 长期记忆（`memory/`，需要时设置）

这里的"长期记忆"指智能体在工作中积累、可能被修改的内容。**稳定的业务知识（口径、标准、模板、案例、术语）请放在业务知识目录里（见 5.2），不要放在长期记忆里**——两者由平台分别管理，权限也不同：业务知识始终只读。知识目录与长期记忆库的数量受平台当前上限约束，见《MA Agent 搭建容量限制说明》。

是否设置长期记忆、每个记忆库是否允许智能体修改，**由业务方决策**。

```yaml
# memory/stores.yaml
stores:
  - name: <记忆库用途，如 playbook>
    access: read_only            # read_only | read_write；不写则按 read_only
    purpose: <存什么>
    maintainer: <谁维护>
    # 选 read_write 时必填：
    allowed_content: <允许智能体写入哪类内容>
    inspector: <谁负责事后巡检>
    inspect_cadence: <多久巡检一次>
    backup_source: <内容的备份或可重建来源，丢失后怎么恢复>
```

规则：

- **每个记忆库单独决策**，没有说明的一律按只读；
- 记忆条目：一条一个文件，路径即记忆路径；单条大小和单个记忆库的条目数受平台当前上限约束，见《MA Agent 搭建容量限制说明》，超限时按记忆的自然分类拆成多个记忆库；
- 提示词里写"不要修改记忆"只是文字约束，**不具备强制力**，权限以 `access` 为准；
- 团队规范、术语口径等共享知识建议设为只读；
- 记忆库是数字员工级资源，同一次会话中主智能体和子智能体看到同一批记忆库，读写权限对所有智能体一致（见 2.3）。

> **⚠ 选择「可修改」之前，请了解这些事实**
>
> | | 只读（`read_only`） | 可修改（`read_write`） |
> |---|---|---|
> | 智能体能做什么 | 浏览、读取、搜索 | 另外可以新增、修改、删除、移动记忆 |
> | 平台能否拦截 | **能，硬拦截**：智能体写不进去 | **不能**：平台没有任何机制按设定拦截或审批写入内容 |
> | 写入前有无审核 | 不涉及 | **没有**：智能体写了就生效，并立即影响此后所有任务 |
> | 写错或被污染后 | 智能体不会写坏，但既有内容仍可能本身有误，或被维护方改错 | **没有历史版本可回溯**，只能人工改回或从备份重建 |
>
> 因此，选「可修改」时：
>
> - `inspector`、`inspect_cadence` 指的是**事后巡检**（定期检查记忆库里有没有不该有的内容），不是写入前的审批；
> - 智能体处理的不可信内容（用户上传、网页、第三方工具返回）可能被写入，并在此后被当作可信信息读取，风险由你们承担；
> - 必须说明 `backup_source`：内容丢失、被污染后，能从哪里恢复；
> - 如果只是想沉淀固定的规范或口径，请放进业务知识目录（始终只读），不要用可修改的记忆库；
> - 如果记忆内容可以由你们自己的程序来写，**优先让程序写入、智能体只读**，这是最稳妥的做法。

### 5.6 输入输出契约（`io/`）

**它是干什么的：** 契约用机器可读的方式写明"这位数字员工**收什么、产什么**"的结构，让别的系统和平台能自动检查，而不是靠人读文字。具体用途：

| 谁用 | 怎么用 |
|---|---|
| 调用方（飞书入口、网关、上游系统） | 按"输入契约"检查用户或系统给的材料是否齐全、格式是否对，缺什么先要求补，不浪费一次运行 |
| 质检 | 按"产物契约"检查产出的文件、数据是否符合约定的字段和格式 |
| 下游系统 | 按"产物契约"读取产出，知道文件在哪、字段是什么含义 |
| 智能体之间 | 主智能体向子智能体交接的内容、子智能体回传的内容，也可以写成契约，避免两边理解不一致 |

契约**不会**交给智能体当提示词：智能体怎么做事写在 `identity/`，契约只用来检查输入输出。平台也不把它映射成 MA 里的任何资源。

**什么时候需要写：** 数字员工有明确的结构化输入或产物（表格、固定字段的 JSON、固定章节的报告）才需要；纯自由对话可以不写，省略 `io/`。

**怎么组织：**

```text
io/
├── README.md                   # 导航：有哪些输入、产物；每个由哪个智能体产生、给谁用
└── contracts/
    ├── input.report-request.json      # 输入契约，一个输入一个文件
    └── output.weekly-report.json      # 产物契约，一个产物一个文件
```

- 命名建议 `input.<名称>.json`、`output.<名称>.json`；智能体之间的交接契约用 `handoff.<发出方>-<接收方>.json`；
- 使用 JSON Schema 描述，须写明：字段、类型、是否必填、示例、版本；
- **产物契约**还要写明：产物类型（文件、表格、消息）、内容在哪里能找到、由哪个智能体产生、依据哪些输入。

产物契约示例：

```json
{
  "$id": "output.weekly-report",
  "version": "1.0.0",
  "description": "热点周报：一份 Markdown 报告 + 一份数据表",
  "produced_by": "insight",
  "type": "object",
  "required": ["report_file", "data_file", "period"],
  "properties": {
    "report_file": { "type": "string", "description": "报告文件名，位于交付目录，.md" },
    "data_file":   { "type": "string", "description": "数据表文件名，位于交付目录，.xlsx" },
    "period":      { "type": "string", "description": "统计周期，如 2026-W45" }
  },
  "examples": [{ "report_file": "weekly.md", "data_file": "weekly.xlsx", "period": "2026-W45" }]
}
```

契约改动属于接口变化：输出结构变更按不兼容变更处理，升主版本（第 7 章）。

### 5.7 提示词中的占位符

提示词里需要引用业务知识和长期记忆时，**不能写运行环境的真实路径或资源编号**（例如 `/mnt/...`、记忆库编号）——它们只在构建时才产生，写死后环境一变就失效。因此用**占位符**：你们写占位符，平台在构建时替换成智能体能直接理解的文字。

**目前可使用的占位符只有两个：**

| 占位符 | 写什么 | 构建时替换成 |
|---|---|---|
| `{{knowledge:目录名/相对路径}}` | 业务知识中的一个文件（见 5.2） | 该文件的完整路径，如 `/<记忆库编号>/统计口径.md`，附"使用记忆工具读取"（只读） |
| `{{memory:记忆库名}}` | `memory/stores.yaml` 中的记忆库 `name`，指整个记忆库 | 该记忆库的路径，如 `/<记忆库编号>/`，附"使用记忆工具读取"或"使用记忆工具读写" |
| `{{memory:记忆库名/条目路径}}` | 记忆库里的某一条记忆 | 该条记忆的完整路径，如 `/<记忆库编号>/客户偏好/A.md` |

**为什么要用占位符：** 业务知识和长期记忆在平台上都存放在"记忆库"里，智能体运行时是通过路径找到它们的，而路径的第一段是记忆库编号。编号要等记忆库创建出来才有，你们写提示词时不可能知道，所以由你们写占位符，平台在构建时填入真实路径。两类的区别只在于：业务知识始终只读，长期记忆按你们声明的权限读写。
输入资料、产出文件、Skill、外部工具、子智能体，**暂时没有占位符**：提示词里用自然语言描述即可（例如"用户提供的资料""最终报告放到交付目录""交给热点分析子智能体"），仍然不要写真实路径。后续如增加占位符，会在本节更新。

写法示例（主智能体的 `orchestration.md`）：

```text
## 报告口径
- 周报结构按 {{knowledge:业务口径/周报模板.md}} 编写；
- 历史经验参考 {{memory:playbook}}。
```

规则：

- 占位符可以写在 `identity/`、`subagent/` 的提示词里；`{{knowledge:…}}` 还可以写在知识文件里。可复用能力自己的文件（`SKILL.md`、`scripts/`）不处理占位符；
- 被引用的知识目录、记忆库必须已声明，且已挂载到使用该提示词的智能体上（见 2.3），否则构建失败并退回；
- 除这两个之外的 `{{…}}` 一律退回，不要自创占位符；替换后文本里不会再残留 `{{`；
- 提示词里仍然不要直接写运行环境路径（以 `/mnt/`、`/workspace/` 开头），写了会被退回；
- **你们写的文字，平台只做占位符替换，不做其他改写**（顺序、标题、规则一字不动）；
- 回执会分开列出：你们写的原文、每个占位符替换后的结果、拼接后的完整系统提示词，便于逐项核对。

> 不要为了使用占位符而删减或改写已经确认的行为规则（安全、调试、验证等要求），只需要把写死的路径或编号换成占位符。

## 6. 可复用能力的登记

**需要被多位数字员工或多个业务线共同使用、并希望统一维护和升级的能力**（Skill、工具、成套的业务知识、模板、提示词片段、外部服务），必须登记到平台的**原子能力注册表**，各数字员工通过引用使用，不得各自复制。仅一位数字员工使用的，不必登记；多位员工各自保留副本且不要求统一升级的，也不必登记（见 2.2）。

### 6.0 能力从哪里来

可复用能力的**唯一信息源是平台的原子能力注册表**，登记和查询都以它为准。能力有三种来源，用标识的前缀区分：

| 标识形式 | 来源 | 你们能不能引用 |
|---|---|---|
| `platform.<名称>` | 平台提供的公共能力 | 可以，所有业务线都能引用 |
| `<你们的业务线ID>.<名称>` | 你们自己登记的能力 | 可以，并由你们负责维护 |
| `<其他业务线ID>.<名称>` | 其他业务线登记的能力 | 默认不可以；确需使用，须该能力提供方同意，由平台办理 |

标识格式为 `<提供方>.<名称>`，名称为小写字母、数字、连字符，登记后不可变更。

**查询：** 当前注册表放在飞书多维表格《原子能力注册表》：https://bluefocus.feishu.cn/base/ZRg5bp8lZavDRPsq9eQcp32UniO （分"能力""版本"两张表，业务方只读，访问权限向平台申请）；分析师研发环境直接读取这张表；用法见 6.4。
**登记：** 把 6.1 的各项内容提供给平台，由平台录入注册表；你们不直接改注册表。

### 6.1 登记哪些信息

| 字段 | 内容 | 填写要求 |
|---|---|---|
| 团队 | 提供团队 | 真实可联系 |
| 原子能力 | 名称与类型 | 类型：skill / tool / mcp / knowledge / template / prompt |
| 描述 | 何时用、做什么、输入输出 | 一到三句话，面向选用者 |
| 版本 | 语义化版本 | 主.次.修订 |
| 被谁引用 | 引用它的业务线、数字员工，以及具体是主智能体还是哪个子智能体 | **由平台自动生成**，不用填 |
| 地址 | 能取回该版本确切内容的位置 | 仓库路径加提交，或对象存储位置加内容摘要；MCP 写服务地址与协议版本 |
| 责任人 | 主责任人、备份 | 各一名 |
| 依赖 | 依赖的其他能力及版本范围 | 没有写"无" |
| 所需凭证 | 凭证类型与用途 | 只写类型，不写值 |
| 变更说明 | 本版本改了什么 | 面向使用方 |

### 6.2 版本规则

| 变更 | 升哪一位 | 对引用方的影响 |
|---|---|---|
| 修复缺陷，行为兼容 | 修订 | 在引用方允许范围内，可批量升级 |
| 新增能力，向后兼容 | 次要 | 引用方按自己的版本范围决定是否纳入 |
| 不兼容变更 | 主要 | **不会自动纳入任何引用方**，每个引用方需评审后升级 |

- 同一版本发布后**内容不可变**，修改必须发布新版本；
- 下线前先标记"即将下线"，写明时间与替代能力，所有引用方迁移完成后才能下线。

### 6.3 在业务线中引用

在 `registry/skills.json`、`tools.json` 中声明：

```json
[
  { "id": "<能力标识>", "range": "^1.2.0" }
]
```

- `id` 必须是注册表里已登记的能力标识（取值见 6.4），不得自拟；
- `range` 表示接受的版本范围；具体使用哪个版本由平台在发布时锁定；
- 由哪些智能体使用，写在 `registry/agents.json` 的 `mounts.skills` / `mounts.tools`（见 2.3）；同一能力被多个智能体挂载时，平台按智能体分别锁定版本；
- 不得把能力的内容复制进资源包。

### 6.4 查询注册表里已有的能力

写资源包之前，先到注册表（见 6.0）查有没有现成的能力可以引用，避免重复建设。注册表**对你们只读**：你们能查询，登记和锁定由平台完成。

| 你需要的信息 | 在注册表里看哪里 |
|---|---|
| 有哪些能力、做什么、适用范围 | "能力"表：标识、类型、名称、描述、提供团队、责任人，以及适用领域、适用条件、不承接范围 |
| 能引用哪些版本 | "版本"表：只选状态为"已发布"的；"候选"只能用于开发和预发，不能用于生产 |
| 输入输出是什么 | "版本"表：输入概要、输出概要 |
| 该版本需要什么凭证、依赖什么 | "版本"表：所需凭证类型、依赖的其他能力 |
| 它是否即将下线 | "版本"表：状态为"即将下线"的写明替代版本，新引用请选替代版本 |

选好之后：

1. 在 `registry/skills.json`、`registry/tools.json` 里写 `id` 和 `range`（见 6.3）；
2. 在 `registry/agents.json` 里，把它挂到使用它的智能体的 `mounts.skills` / `mounts.tools` 上（见 2.3）。

分析师研发环境会替你们完成查询和这两步写入，查询入口和权限由平台提供。引用关系（被谁引用、锁定到哪个版本）由平台在构建时写入注册表，你们不需要、也不能自己登记引用。

### 6.5 可复用能力（Skill）的内容要求

| 项 | 要求 |
|---|---|
| 目录 | 只有一个顶层目录 `<能力名>/`，其下直接包含且仅包含一个 `SKILL.md`；可选 `scripts/`、`references/` |
| `SKILL.md` | 写清何时触发、做什么、输入输出、限制；描述具体到能判断"该不该用我" |
| 通用性 | 定义可复用的能力，不写一次性任务的具体数据 |
| 体量 | 受平台当前上限约束，见《MA Agent 搭建容量限制说明》 |
| 禁止项 | 密钥、令牌、个人账号；缓存与临时文件 |
| 依赖 | 需要的包与工具写入 `registry/environment.json`，不得用脆弱的绕法掩盖环境缺失 |
| 自检 | 打包后重新解压并实际运行一遍，保留输出 |

## 7. 版本与变更

### 7.1 版本号

数字员工资源包使用语义化版本（整个数字员工一个版本号，包含主智能体和全部子智能体；增量交付也沿用这个版本号，见 2.4）：

- 不兼容变更（提示词边界改变、输出结构变更、移除能力、**删除子智能体**）：主版本；
- 新增能力、新增知识、**新增子智能体**：次版本；
- 文案、案例、修复：修订版本。

### 7.2 变更说明

每次交付更新，在 `registry/version_mapping.md` 记录：

```markdown
## 1.1.0 — YYYY-MM-DD
- 变更：<做了什么>
- 影响：<影响哪些任务、哪些使用方>
- 引用的可复用能力：<能力标识 旧版本 → 新版本>
- 验证：<跑了哪些用例，结果>
```

### 7.3 变更生效

业务线更新后，平台会评估影响并分阶段上线：先在测试环境验证，再灰度，最后全量。**进行中的任务保持原版本不变**，新任务使用新版本。

## 8. 安全要求

1. 资源包、登记信息、变更记录、日志、截图中**不得出现任何密钥明文**，只写名称、类型、引用；
2. 环境变量里不放密钥；密钥的声明与引用一律放 `connections.yaml`，真实值只进入平台的密钥存储；
3. 凭证的真实值由提供人单独交给平台，不通过文档、聊天、邮件传递；
4. 凭证只用于声明的域名，不得扩大范围；
5. 业务数据发送给模型的范围必须与业务方确认的结论一致；
6. 记忆库的修改权限必须逐个决策并登记，默认只读。

### 9.2 验收用例

随资源包提供验收用例，写在 `acceptance/cases.yaml`，**至少 3 个**，由业务方描述、业务方验收人判断是否合格。

```yaml
# acceptance/cases.yaml
cases:
  - id: AC-01
    title: 热点周报（正常流程）
    category: 正常                  # 正常 | 边界 | 失败 | 接续
    route: dispatch                 # direct：主智能体自己完成；dispatch：分派给子智能体并汇总
    agents: [pm, hotspot]           # 预期参与的智能体
    input: 提供 50 条样本数据文件，并发消息"出一份本周热点周报"
    expected: 在交付目录产出 weekly.md 与 weekly.xlsx，字段符合 io/contracts/output.weekly-report.json；热点不少于 5 条，每条带数据来源
    acceptor: 张三（业务负责人）
  - id: AC-02
    title: 材料缺失时追问
    category: 失败
    route: direct
    agents: [pm]
    input: 只发消息"出一份周报"，不提供数据
    expected: 不分派、不产出报告，明确说明缺什么材料并请求补充
    acceptor: 张三
  - id: AC-03
    title: 容易误路由的需求
    category: 边界
    route: direct
    agents: [pm]
    input: "帮我写一段热点话术"（属于话术需求，不是热点分析）
    expected: 不分派给 hotspot，按话术口径直接回答或转给对应智能体
    acceptor: 李四
```

每个用例写明：

| 项 | 内容 |
|---|---|
| `title` | 一个具体、可重复的业务场景 |
| `category` | 正常、边界、失败、接续（长任务中断后恢复）之一 |
| `route`、`agents` | 这个用例走主智能体直接完成，还是分派给哪些子智能体 |
| `input` | 提供什么材料、说什么话 |
| `expected` | 期望的产物与质量要求，尽量写成可检查的条件 |
| `acceptor` | 谁来判断是否合格 |

**覆盖要求：**

- 至少覆盖正常、边界、失败（或接续）各一类，优先使用你们已有的业务样例；
- 有子智能体的，至少有一个**分派给子智能体并汇总回来**的用例，以及一个**容易被误分派、实际应由主智能体或另一个智能体处理**的反例；
- 增量交付新增或修改了智能体的，用例需覆盖被改动的智能体及其分派路径，并抽查一个未改动的场景确认没有退化；
- 修复 Skill 的，至少包含原来失败的用例和一个正常用例。

**执行与结论：** 平台执行用例，并把每个用例的结果写进回执：受检版本、实际使用的模型与环境、输入、预期、真实输出、执行时间、结论、证据位置。结论只有四种：**通过、失败、无结论、未执行**；没有实际运行过的用例必须写"未执行"，不能写"通过"。最终是否合格，由 `acceptor` 在回执上给出接受结论。

平台另行执行通用的冒烟检查（对话、命令执行、读取资料、产出文件、越界拒绝等）。
