## 1. 设计目标

来源：原页`#design-intent`。本版主线是：**在专业分工基础上适配MA一层子Agent约束，简化执行与校验调用。**

### G01. 项目协作有归属，运行互不覆盖

- 原页依据标签：ADA自查·本轮重点。
- 当时现状：Session分开，但handoff、项目目录与部分记忆共享，交接缺少独立项目标识。
- 设计目标：项目组织协作，用户权限决定访问，每次运行独立保存状态与产物。

### G02. 领域方法集中，客户记忆分域

- 原页依据标签：用户输入＋ADA自查。
- 当时现状：Topic方法跨角色分布；共享LM中包含客户和项目专属内容。
- 设计目标：聚合专业方法与版本，公共知识、客户信息和项目记忆按范围管理。

### G03. 执行上下文精简，调用可追溯

- 原页依据标签：候选目标·收益待验证。
- 当时现状：Producer任务重；数据调用使用共享身份，回执与项目缺少统一关联。
- 设计目标：能力接收必要输入，保留身份、项目、权限预算与回执，支持受控并发。

### G04. 本版已明确的方向及验证边界

1. 客户统一面对ADA。
2. PM为主Agent；领域、策略、通用三类分析师为同级子Agent。
3. Validator为Skill。
4. 策略默认参与新的有效分析任务。
5. 原页还写有“策略负责最终交付核对”；这是已被后续BASE-22替代的历史表述，按第0.2节处理。
6. 具体路由、并发和门禁执行仍待验证；目标及候选收益不等于已实现能力。

## 2. 架构

### A01. 总体结构：三层职责，一层子Agent

来源：原页`#architecture`。**三层表示职责分工，不表示三层Agent嵌套。**

```text
业务用户 / 品牌客户
└─ 统一面对ADA协作集群
   ├─ 第一层：项目管理层
   │  └─ PM / Project Agent：MA主Agent
   │     ├─ 直接子Agent：领域分析师 / Topic Agent（T）
   │     ├─ 直接子Agent：策略Agent（S）
   │     └─ 直接子Agent：通用数据分析Agent（G）
   │        上述三类角色共同组成第二层“分析师层”
   └─ 第三层：执行 / 能力层
      ├─ 业务与数据Skill
      ├─ Tool、脚本、API及服务
      ├─ Validator Skill
      └─ 交付与企业支持能力
         PM及分析子Agent按需调用，能力调用不新增Agent层级

外部接入：数据供应商 / 研究服务 / 蓝标企业专业资源 → 能力层
运行与治理：MA Runtime承载；BlueFlare为拟接入的平台治理边界
```

该拓扑明确：PM是唯一主Agent，T/S/G是PM的直接子Agent；分析子Agent不再向下创建子Agent，Skill内部也不嵌套创建子Agent。执行层通过能力调用承接具体操作。

MA一层限制的证据来源是**用户转述团队讨论**，已作为本版设计约束采用；不是独立检查目标MA环境后得到的运行结论。

### A02. 第一层：项目管理层——PM / Project Agent

PM职责：

1. 受理需求，管理需求与范围。
2. 维护项目背景及项目上下文。
3. 分配任务，调度或恢复直接子Agent的分析任务。
4. 管理任务状态与异常。
5. 在同级协作中转交问题、任务和产物引用，以及返回节点信息。

职责边界：专业判断交给分析师；PM不再审阅整份报告或代做综合策略。只有PM承担当前拓扑中的直接子Agent调用/恢复。

### A03. 第二层：领域分析师——Topic Agent / T

领域分析师职责：

1. 按既定领域的固定工作流产出专业成果。
2. 覆盖人群洞察、行研用研、社媒等具体领域；这些是原图示例，不代表本次已验证的服务清单。
3. 核心领域洞察由领域分析师自身完成。

领域分析师与策略、通用分析师为同级角色；领域专业责任不因PM路由或能力调用而转移。

### A04. 第二层：策略Agent / S

v0.7.20原页列出的专业工作：

1. 跨领域整合与商业判断。
2. 自身商业补证。
3. 策略与行动建议。
4. 默认参与新的有效分析任务；领域与策略可独立推进，真实并发待验证。

**历史表述提醒：** 原图另列“S09最终交付核对”，协作说明写“无策略交付要求时提供内部参考”。这两项属于本页当时的工作流表达，后续适用规则见第0.2节；不得据此把S重新设计成T/G成果审核或返工门禁。

策略只补自身商业证据；保留用户追问、报告版本和专业交互，供后续复盘，**不自动提交领域能力研发需求**。

### A05. 第二层：通用数据分析Agent / G

通用分析师职责与承接边界：

1. 承接未绑定Topic的标准分析需求。
2. 仅在已有数据与方法能力范围内承接。
3. 超出能力范围时请求支持。

“未绑定Topic”和“在能力范围内”是共同条件；不能只凭没有Topic就认定通用分析能够完成任务。

### A06. 第三层：执行 / 能力层

| 能力类别 | 原图列出的职责 |
|---|---|
| 业务与数据Skill | 取数、处理、统计、表达。 |
| Tools / 脚本 / API | 接口接入与确定性操作。 |
| Validator Skill | 执行已登记的关键节点门禁。 |
| 交付与企业支持 | 发送回执、公共求助入口。 |

PM和分析子Agent按需调用这些能力，能力返回结果。**调用Skill、Tool、脚本或服务不等于新增一层Agent。** Skill内部也不得嵌套创建子Agent。

### A07. Validator Skill的调用与边界

原页定义的调用过程：

```text
PM或分析节点命中已登记规则
→ 固定被检查对象及规则版本
→ 调用Validator Skill
→ 返回PASS / FAIL / INCONCLUSIVE
→ 结果返回调用节点
```

返回状态含义：

- `PASS`：通过。
- `FAIL`：失败。
- `INCONCLUSIVE`：无法判断。

普通节点可以自检；Validator用于已登记的关键门禁。**Validator改为Skill不自动提供独立上下文，也不证明具备强制拦截能力。** 权限、费用与执行控制仍须平台落实，Skill不能替代平台鉴权与费控。

### A08. 同级协作与专业责任

来源：架构后的`#strategy-collaboration`说明。

当前候选适配是：**同级业务协作经PM路由。** PM转交任务、材料引用与返回位置，专业工作仍由对应分析师完成。是否支持直接同级通信，以及消息、挂起、任务恢复等实际机制，尚需实现方核实。

#### A08.1 局部策略咨询

```text
领域分析师提出问题与材料引用
→ PM路由
→ 同级策略Agent回复
→ PM返回原领域节点
```

沿用既定范围时不新增逐次业务审批；具体消息、挂起与恢复机制待实现方核实。此处的“不新增逐次业务审批”不取消原有的权限、费用或业务授权边界。

#### A08.2 原页最终交付链——历史工作流表达

以下为v0.7.20原页的交付链，**其中S09核对职责已被后续决议替代，不作为当前S门禁实现依据**：

```text
领域定稿 / 完整策略
→ 经PM关联产物
→ 策略S09最终核对〔历史表述，见第0.2节〕
→ E02授权交付
→ P05接收状态
```

原页说明：PM只路由领域产物和状态；完整策略在策略任务内衔接；适用关键门禁调用Validator Skill。页面当时以策略负责专业核对来区分PM统筹与专业工作。后续BASE-22取消的是S的上游复核、门禁与自动退回职责，PM和分析师的专业分工仍须保留。

`S09`、`E02`、`P05`是页面使用的流程节点标识，不是新增的Agent层级。原页链接的策略流程为v0.5；最新策略细节应按第0.2节另行核对。

### A09. 数据供应链与蓝标资源接入

原图列出的资源范围：

1. 供应商数据API。
2. 研究服务。
3. 企业专业资源。

这些资源通过能力层接入；调用与结果应携带项目、权限、费用及回执引用。图中的资源入口是架构设计，不等于相关资源已经采购、获权或完成接入。

### A10. MA Runtime与BlueFlare边界

- MA Runtime承担运行承载。
- BlueFlare对应拟接入的平台治理。
- 任务、权限、空间、费用及恢复接口仍待核实。
- 不因图中出现平台名称，就认定具体接口、治理能力、并发能力或恢复机制已经可用。

### A11. 跨层共同要求

以下要求贯穿PM、分析师、执行能力及资源接入：

1. 客户与项目访问边界。
2. 固定版本。
3. 产物归属。
4. 状态与回执可追溯。

图中纵向关系表示主/子Agent调度与能力调用；同级协作经PM路由是当前候选适配。专业责任没有上收至PM，客户始终面对统一ADA。
