# 原子能力注册表设计

> 版本：v1.0 · **平台内部文档**，面向中台研发
> **定位：** 注册表是"团队 - 原子能力 - 描述 - 版本 - 被谁引用 - 地址"的**唯一事实源**，用 MySQL 存储，通过 API 登记、读写和维护版本。可复用的最小能力（Skill、工具、MCP、业务知识、模板、提示词片段）统一在这里登记，业务线按版本引用。
> **适用场景：** 基于火山方舟 Managed Agents（MA）底座搭建数字员工时，可复用能力的注册、引用、升级与下线。
> **配套文档：**
> - 《MA Agent 搭建映射规范（平台内部）》：业务交付物如何落到 MA、业务线标识与多业务方区分、构建与升级流程。本文由它的原第 5 章拆出，成为独立文档。
> - `registry/atomic-registry.schema.sql`：建表脚本，与第 2 节一致，改动须同步。
> **业务方不需要阅读本文。** 业务方只需在《MA Agent 搭建交付规范》第 6 章了解如何登记和引用。

---

注册表是**唯一**记录"团队 - 原子能力 - 描述 - 版本 - 被谁引用 - 地址"的事实源，用 **MySQL** 存储，通过 **API** 登记、读写和维护版本。建表脚本见 `registry/atomic-registry.schema.sql`。

## 1. 原子能力的分类

可被多个业务线复用的最小能力单元。**当前分类够用，后续按场景扩展**：

| 类型 | 含义 | 承载形式 |
|---|---|---|
| `skill` | 可执行的封装能力 | MA Skill |
| `tool` | 外部能力契约 | `tools/` 契约文档；实际执行靠 MCP 服务或 Skill 脚本 |
| `mcp` | 远端 MCP 服务 | Agent 的 `mcp_servers` |
| `knowledge` | 成套业务知识（需多位员工或多个业务线统一维护时登记） | 业务知识目录；引用方的构建器各自把它写入自己的知识记忆库 |
| `template` | 业务内容模板 | 业务知识目录中的模板文件 |
| `prompt` | 可复用提示词片段 | 文本 |

**扩展方式**：`type` 是字符串字段，新增分类不需要改表结构。新增时只需：① 在 API 的允许值列表里增加该类型；② 在第 3 节补充该类型的 `address` 结构；③ 在《MA Agent 搭建映射规范（平台内部）》第 6 章补充该类型如何映射到 MA 资源。已有数据不受影响。

## 2. 表结构

四张业务表加一张审计表。关系如下：

```text
atomic_capability (1) ──< (N) atomic_capability_version
        │                          ▲
        └──< capability_agent_ref ─┘   (pinned_version_id)
                    │
                    └──< capability_agent_ref_history
registry_audit_log   （记录以上三张表的变更）
```

| 表 | 作用 | 关键约束 |
|---|---|---|
| `atomic_capability` | 原子能力身份：标识、名称、类型、团队、责任人、描述 | `atomic_id` 全局唯一 |
| `atomic_capability_version` | **独立的版本记录表**：每个版本一行，含语义化版本、内容指纹、地址、依赖、兼容性、凭证类型、变更说明、状态 | `(capability_id, version)` 唯一；released 后内容字段不可变 |
| `capability_agent_ref` | **原子能力与 Agent 的关联表**：哪个智能体引用哪个能力、版本范围、当前锁定版本、该智能体的 MA Agent ID | `(capability_id, topic, employee, agent_role, stage)` 唯一 |
| `capability_agent_ref_history` | 引用锁定的变更历史（声明、锁定、升级、回滚、移除） | 只追加 |
| `registry_audit_log` | 全部变更的审计日志（前后内容、操作人、请求 ID） | 只追加 |

### 2.1 `atomic_capability`（身份，不随版本变化）

| 字段 | 含义 | 规则 |
|---|---|---|
| `atomic_id` | 业务标识 | `<owner_topic>.<name>`，全局唯一，创建后**不可变**；`<name>` 为小写字母、数字、连字符，3 到 48 位 |
| `owner_topic` | 提供方 | 提供该能力的**业务线 ID**，或中台保留标识 `platform`；与 `atomic_id` 前缀一致，冗余存储便于按提供方查询 |
| `name` | 名称（人读） | |
| `type` | 类型 | 见 第 1 节 |
| `team` | 提供团队 | 必须真实可联系 |
| `owner_primary` / `owner_backup` | 主责任人 / 备份责任人 | 各一名 |
| `description` | 描述 | 写"何时用、做什么、输入输出"，面向选用者 |
| `status` | 能力整体状态 | `active` / `archived` |
| `latest_released_version_id` | 当前最新的 released 版本 | 冗余字段，加速查询 |

### 2.2 `atomic_capability_version`（版本，内容不可变）

| 字段 | 含义 | 规则 |
|---|---|---|
| `capability_id` | 所属能力 | |
| `version` / `ver_major` / `ver_minor` / `ver_patch` | 语义化版本 | 三段数字冗余存储，用于排序与范围匹配 |
| `fingerprint` | 内容指纹 | SHA-256；内容不变则指纹不变 |
| `address` | 能力地址 | JSON，结构随类型不同，见 第 3 节 |
| `depends_on` | 依赖的其他原子能力 | `[{atomic_id, range}]`，用于计算影响面 |
| `compat` | 兼容性声明 | 所需 MA 工具集类型、模型要求、文档快照日期 |
| `credentials` | 所需凭证类型 | 只写类型与用途，**不含值** |
| `changelog` | 本版本变更说明 | 面向使用方 |
| `status` | 版本状态 | 见 第 4 节 |
| `deprecated_at` / `retire_after` / `replaced_by_version_id` | 下线信息 | 即将下线时必填替代版本与计划下线时间 |
| `created_by` | 登记人 | |

**不可变规则**：`status` 为 `released` 及之后的版本，`address`、`fingerprint`、`depends_on`、`compat`、`credentials` 不得修改；只能修改状态与下线信息。需要修改内容必须发布新版本。该规则由 API 层强制，同时在数据库层可用触发器兜底（上线前评估）。

### 2.3 `capability_agent_ref`（被谁引用）

引用关系在**智能体**这一层发生：主智能体和每个子智能体各自有独立的 Skill 与 MCP 列表，可以引用不同的原子能力、不同的版本。

| 字段 | 含义 | 规则 |
|---|---|---|
| `capability_id` | 被引用的能力 | |
| `topic` / `employee` | 业务线 / 数字员工 | |
| `agent_role` | 智能体 | `coordinator` 或 `subagent:<名称>` |
| `stage` | 环境阶段 | `dev` / `staging` / `prod`；同一智能体在不同阶段可锁定不同版本 |
| `version_range` | 业务方声明的可接受范围 | 如 `^1.2.0` |
| `pinned_version_id` | 当前锁定的版本 | 声明后尚未发布时为空；同一能力在不同智能体上可锁定在不同版本 |
| `ma_agent_id` | 该智能体在 MA 上的 Agent ID | 锁定后回填，用于升级时定位 |
| `status` | `active` / `removed` | 移除时置 `removed`，不物理删除，以保留历史 |

### 2.4 查询示例

| 问题 | 查询思路 |
|---|---|
| 某能力某版本被哪些智能体锁定（升级影响面） | `capability_agent_ref` 按 `pinned_version_id` 关联版本表，限定 `status=active` |
| 某智能体用了哪些能力、各是什么版本 | 按 `(topic, employee, agent_role, stage)` 查 `capability_agent_ref` |
| 某能力下一个满足 `^1.x` 的最新 released 版本 | 版本表按 `ver_major=1` 且 `status=released`，三段版本倒序取第一 |
| 某团队提供了哪些能力 | `atomic_capability` 按 `team` |
| 哪些能力即将下线、还有谁在用 | 版本表 `status=deprecated` 关联引用表 |

## 3. 能力地址

`address` 必须能让中台**自动取回该版本的确切内容**，不依赖人工转交：

| 类型 | `address` 结构 |
|---|---|
| `skill` | `{"repo": "...", "path": "...", "commit": "...", "ma_skill_id": "skill-…", "ma_skill_version": "1"}` |
| `tool` / `template` / `prompt` | `{"repo": "...", "path": "...", "commit": "..."}` 或 `{"bucket": "...", "key": "...", "sha256": "..."}` |
| `knowledge` | 同上，指向知识目录 |
| `mcp` | `{"url": "...", "protocol": "...", "credential_name": "..."}`，`credential_name` 只写凭证名称，不含值 |

同一版本发布后**内容不可变**，修改必须发布新版本。

## 4. 状态与生命周期

版本状态机：

```text
draft ──→ candidate ──→ released ──→ deprecated ──→ retired
  │            │            ▲             │
  │            └────────────┘             └──→ released（撤销下线）
  └───────────────────────→ released（审核未启用时可直接发布）

预留（当前不启用）：draft / candidate ──→ in_review ──→ released
                                              └──→ rejected ──→ draft
```

| 状态 | 含义 | 规则 |
|---|---|---|
| `draft` | 草稿 | 内容可修改；不可被引用 |
| `candidate` | 候选 | 内容可修改；仅可被 `dev`、`staging` 阶段的引用锁定，**不得进入 `prod`** |
| `released` | 已发布 | 内容**不可变**；可被所有阶段引用 |
| `deprecated` | 即将下线 | 必须写明 `retire_after` 与替代版本；仍可被引用，新增引用需告警 |
| `retired` | 已下线 | 不可再被新引用；`referenced_by` 必须为空才能进入 |
| `in_review` / `rejected` | **预留** | 当前阶段**不做审核**，状态已在设计中预留；启用后 `draft`/`candidate` → `in_review` → `released`，不通过则 `rejected` |

**审核的预留方式**：状态字段与状态机已包含 `in_review`、`rejected`，API 层有一个开关（默认关闭）。关闭时，这两个状态不可达，`draft` / `candidate` 可直接发布；启用后发布必须先经过 `in_review`，并需要补充"审核人、审核时间、审核意见"字段（届时再加表，不影响现有结构）。

## 5. 引用声明与锁定

业务方在数字员工的 `registry/skills.json`、`tools.json` 中声明引用，并写明**引用方是哪个智能体**：

```json
{
  "id": "platform.report-cover",
  "range": "^1.2.0",
  "used_by": ["coordinator", "subagent:cleaner"]
}
```

- `used_by`：引用它的智能体；不写则默认只有主智能体；
- `range`：业务方声明可接受的版本范围；
- 构建时中台为每个 `(智能体, 阶段)` 解析 `range`，在 `capability_agent_ref` 中写入 `pinned_version_id`，同时更新 `ma_agent_id`，并写入 `capability_agent_ref_history`；
- `pin` 是**按智能体分别**锁定的确切版本，同时写入映射规范的资源锁定清单（7.5）；
- `referenced_by` 不单独存储，由 `capability_agent_ref` **实时查询得到**，保证"被谁引用"始终准确：

```json
{
  "id": "platform.report-cover",
  "referenced_by": [
    { "topic": "sales", "employee": "assistant", "agent": "coordinator", "stage": "prod", "range": "^1.2.0", "pin": "1.2.3" },
    { "topic": "sales", "employee": "assistant", "agent": "subagent:cleaner", "stage": "prod", "range": "^1.0.0", "pin": "1.0.5" }
  ]
}
```

- 业务线不得复制原子能力内容到资源包。

## 6. API

通过 API 完成登记、版本维护、引用管理和查询。**当前阶段不做审核**，所有写接口都需要鉴权并记入审计日志。

### 6.1 通用约定

| 项 | 约定 |
|---|---|
| 风格 | REST，JSON，路径前缀 `/registry/v1` |
| 鉴权 | 服务端校验调用方身份；写接口按团队授权：只有 `team` 对应团队成员或中台管理员可写 |
| 幂等 | 写接口支持 `Idempotency-Key` 请求头，同一个键重复提交返回第一次的结果 |
| 并发 | 修改类接口带 `If-Match: <updated_at 或版本号>`，不匹配返回 409，防止覆盖 |
| 错误 | 统一 `{code, message, details}`；业务校验失败 422，冲突 409，不存在 404，无权限 403 |
| 审计 | 每次成功写入记一条 `registry_audit_log`，含前后内容、操作人、请求 ID |
| 分页 | 列表接口 `page`、`page_size`（默认 20，最大 100）；返回总数 |
| 凭证 | 请求与响应中**不得出现凭证值**，字段里只写类型与用途 |

### 6.2 原子能力

| 方法与路径 | 作用 | 关键规则 |
|---|---|---|
| `POST /capabilities` | 登记原子能力 | `atomic_id` 唯一；`type` 必须在允许值内；`team`、责任人必填 |
| `GET /capabilities` | 列表查询 | 过滤：`team`、`type`、`status`、`owner_topic`、`q`（名称/描述关键词） |
| `GET /capabilities/{atomic_id}` | 详情 | 含最新 released 版本摘要 |
| `PATCH /capabilities/{atomic_id}` | 修改团队、责任人、描述 | `atomic_id`、`type` 不可改 |
| `POST /capabilities/{atomic_id}:archive` | 归档 | 仅当没有 `active` 引用时允许 |

### 6.3 版本

| 方法与路径 | 作用 | 关键规则 |
|---|---|---|
| `POST /capabilities/{atomic_id}/versions` | 新增版本，初始 `draft` | 版本号唯一且必须大于已有最高版本（可由 `bump=major|minor|patch` 自动计算）；`address`、`fingerprint` 必填；校验 `depends_on` 引用的能力存在 |
| `GET /capabilities/{atomic_id}/versions` | 版本列表 | 过滤 `status`；按语义化版本倒序 |
| `GET /capabilities/{atomic_id}/versions/{version}` | 版本详情 | 含 `referenced_by` 摘要（引用数） |
| `PATCH /capabilities/{atomic_id}/versions/{version}` | 修改版本内容 | **仅 `draft`、`candidate` 可改**；`released` 及之后返回 422 |
| `POST /capabilities/{atomic_id}/versions/{version}:transition` | 状态变更 | 请求体 `{to, reason}`；按 第 4 节 状态机校验；`released`→`deprecated` 必须带 `retire_after`、`replaced_by`；→`retired` 要求无 `active` 引用 |
| `GET /capabilities/{atomic_id}/versions/{version}/impact` | 影响面评估 | 返回锁定在该版本的所有智能体（含子智能体）与其 `ma_agent_id` |

### 6.4 引用

| 方法与路径 | 作用 | 关键规则 |
|---|---|---|
| `PUT /refs` | 声明或更新引用 | 请求体含 `atomic_id`、`topic`、`employee`、`agent_role`、`stage`、`version_range`；按唯一键幂等 |
| `POST /refs:resolve` | 解析并锁定 | 对给定智能体与阶段，按 `range` 选最高合法版本写入 `pinned_version_id`；`candidate` 不得用于 `prod`；返回锁定结果，写入历史 |
| `POST /refs/{ref_id}:pin` | 手动指定锁定版本 | 用于升级与回滚；必须在 `range` 内，除非带 `override_range=true` 且写明原因 |
| `POST /refs/{ref_id}:rollback` | 回退到上一个锁定版本 | 读取历史表得到上一个版本；写入历史 |
| `DELETE /refs/{ref_id}` | 移除引用 | 软删除，置 `status=removed`，写入历史 |
| `GET /refs` | 查询引用 | 按 `topic`、`employee`、`agent_role`、`stage`、`atomic_id`、`pinned_version` 过滤 |
| `GET /agents/{topic}/{employee}/{agent_role}/capabilities` | 某智能体用了哪些能力 | 按阶段返回能力、范围、锁定版本 |

### 6.5 构建对接

构建流水线只依赖三个接口：

1. `GET /capabilities/{atomic_id}/versions/{version}`：取回确切地址与指纹，下载内容并校验指纹；
2. `POST /refs:resolve`：为每个 `(智能体, 阶段)` 解析并锁定版本；
3. `GET /agents/.../capabilities`：回填映射规范的资源锁定清单（7.5）的 `atomic` 段。

## 7. 使用与升级

| 场景 | 处理 |
|---|---|
| 新增引用 | `PUT /refs` 声明；`POST /refs:resolve` 解析；校验兼容性、状态、凭证；`candidate` 不得进入 `prod` |
| 发布修订版本 | 兼容修复。落在引用方 `range` 内的，通过影响面接口通知引用方，可批量 `:resolve` 升级 |
| 发布次要版本 | 向后兼容的新增。引用方按 `range` 决定是否纳入 |
| 发布主要版本 | 不兼容变更。**不自动纳入任何引用方**，逐个业务线评审、灰度、改 `range` 后升级 |
| 影响面评估 | 发布前调用 `impact`，得到受影响的业务线、数字员工、**具体智能体（含子智能体）**；验证范围精确到这些智能体；再结合 `depends_on` 计算间接影响 |
| 紧急修复 | 可标记强制升级，中台批量 `:pin` 并通知；仍走映射规范第 9 章灰度，不得跳过冒烟 |
| 下线 | 先 `transition` 到 `deprecated`（带计划下线时间与替代版本），通知所有引用方，迁移完成且过保留期后 `retired` |
| 回滚 | `:rollback` 将锁定回退到上一版本；已发布内容不可变，回滚总是安全 |

升级只影响新建的会话与按映射规范第 9 章升级的存量会话；运行中的会话保持原版本。

## 8. 与构建流程的衔接

- 业务线构建发布时，对每个引用调用 `:resolve`，结果写入映射规范的资源锁定清单（7.5），**锁定清单与 `capability_agent_ref` 必须一致**；`plan` 阶段检查二者是否漂移；
- 引用的能力在注册表中不存在、状态不允许当前阶段、或兼容性不满足时，`plan` 失败；
- 平台升级时，按映射规范 9.4 通过 `compat` 字段在注册表里筛选受影响的版本，再用 `impact` 找到受影响的智能体。

## 9. 注册表自身的运维要求

- MySQL 使用 InnoDB、`utf8mb4`；时间统一存 UTC；
- **服务需支持分布式部署**：注册表服务无状态，可多实例；幂等键、乐观锁都落在 MySQL，不依赖实例内存；
- 迁移脚本版本化，变更表结构走评审；
- 每日备份；`registry_audit_log` 与 `capability_agent_ref_history` 只追加，不做物理删除；
- 读多写少，列表接口加上述索引覆盖，必要时读写分离。

## 10. 标识与归属

注册表不单独设置命名空间。归属由**业务线 ID** 表达，规则见《MA Agent 搭建映射规范（平台内部）》4.2。

| 项 | 规则 |
|---|---|
| `atomic_id` 前缀 | 必须是已分配的**业务线 ID**，或中台保留标识 `platform` |
| 登记权限 | `POST /capabilities` 时，调用方必须被授权操作 `atomic_id` 前缀对应的业务线（`platform` 仅中台管理员）；`team` 须与该业务线的归属团队一致 |
| 业务线 ID 的来源 | 由中台统一分配，全局唯一，分配后不可变更，回收后永久保留、不再分配；分配与回收的台账由中台维护，**当前不在注册表中建表**（业务线数量少、变更不频繁） |
| 不存在的前缀 | 前缀不是已分配的业务线 ID 时，登记返回 422 |
| 引用约束 | 业务线可以引用本业务线或 `platform` 的能力；**引用其他业务线的能力**须该能力的提供方业务线同意（记录在 `capability_agent_ref` 之外的授权表，当前阶段不实现，默认拒绝） |

> 如果以后业务线数量增多、需要注册表自己校验"前缀是否已分配"，再增加一张业务线台账表即可，不影响现有结构。
