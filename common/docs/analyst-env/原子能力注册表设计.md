# 原子能力注册表设计

> 版本：v1.5 · **平台内部文档**，面向中台研发
> **定位：** 注册表是"团队 - 原子能力 - 描述 - 版本 - 被谁引用 - 地址"的**唯一事实源**。可复用的最小能力（Skill、工具、MCP、业务知识、模板）以及**智能体包**（`agent`）统一在这里登记，业务线按版本引用。**以《MA Agent 搭建交付规范》v1.4 为准**：交付规范第 6 章定义业务方如何登记、查询、引用，本文是它的平台侧实现。
> **当前实现：** MVP 使用飞书多维表格（Bitable），正式版本将迁移至 MySQL + API。**查询对业务方与分析师研发环境开放（只读），写入仅限平台。当前不开放 API：分析师研发环境（bot）直接读取多维表格。**
> **适用场景：** 基于火山方舟 Managed Agents（MA）底座搭建数字员工时，可复用能力的注册、引用、升级与下线。
> **配套文档：**
> - 《MA Agent 搭建映射规范（平台内部）》：业务交付物如何落到 MA、业务线标识与多业务方区分、构建与升级流程。本文由它的原第 5 章拆出，成为独立文档。
> - `registry/atomic-registry.schema.sql`：MySQL 建表脚本（正式版），与第 2 节一致，改动须同步。
> **业务方不需要阅读本文。** 业务方只需在《MA Agent 搭建交付规范》第 6 章了解如何登记、查询和引用；智能体包的角色与引用见该规范第 2 章。

### 0.5 Agent 使用方式

**分析师研发环境对注册表只读，不写入。** 它在研发阶段检索已有能力，把选定能力的 `id`、`range` 写进**使用它的智能体所在的包**（`registry/skills.json`、`registry/tools.json`；`main` 引用子智能体写 `registry/agents.json`，格式同构），见交付规范 6.3、6.4；引用与锁定由中台在构建/升级时写入，并生成锁定清单（见《MA Agent 搭建映射规范（平台内部）》第 5.0、7.5 节）。

| 角色 | 权限 | 动作 |
|---|---|---|
| 分析师研发环境 / 业务方 | **只读** | 查询能力与版本，写资源包里的引用声明 |
| 平台同学 / 构建流水线 | 读写 | 登记能力与版本；写入引用与锁定 |

分析师研发环境读取的字段与展示规则：

| 读取 | 用途 | 规则 |
|---|---|---|
| 能力：`atomic_id`、`type`、`display_name`、`description`、`team`、负责人，以及适用领域/阶段/条件/不承接范围（MVP 业务字段，见 0.3；**这些字段目前只在飞书多维表格里，`atomic-registry.schema.sql` 与 `openapi.yaml` 尚未包含，迁移 MySQL 时需补齐，否则正式版读取不到**） | 判断"该不该用" | 全部可读 |
| 版本：`version`、`status`、`depends_on`、`credentials`、`input_spec`、`output_spec`、`changelog`、`replaced_by` | 判断选哪个版本、需要什么凭证、依赖什么 | **只展示 `released` 为可选**；`candidate` 标注"仅 dev/staging"；`deprecated` 标注替代版本；`draft`、`retired` 不展示 |
| 引用：本数字员工当前的引用与锁定 | 增量研发时核对"已经引用了什么" | 只读自己业务线、自己数字员工 |
| `address` | 由构建环节使用 | 分析师研发环境不需要展示 |

写入的声明格式（`registry/skills.json`、`tools.json`、`registry/agents.json`）：`{ "id", "range" }`（`agents.json` 另有 `alias`），其中 `id` 必须取自注册表，**不得自拟**；引用哪个智能体用到，由声明所在的包决定。

业务流程：
0. **分析师研发环境查询**：按需求检索已有能力，选定后写入包里的引用声明（只读）
1. **登记能力**：业务方把能力信息提供给平台，由平台录入（交付规范 6.0）；**`agent` 类型不需要业务方登记，智能体包交付发布时由平台自动录入**（见 3.1）
2. **声明引用**：业务方在包里写引用声明（`id` + `range`）；构建时平台把它展开为每个智能体的引用记录并写入"引用"表
3. **中台构建时查询**：读取该智能体的引用记录，生成锁定清单（`locked_capabilities.yaml`），映射到 MA 资源（Skill/MCP/Knowledge）
4. **Agent 运行时**：MA 按锁定清单挂载对应资源，Agent 无感知注册表，只知道"我有哪些 Skill/工具"

**迁移到 MySQL 版后**，步骤 1-3 改为 API 调用，步骤 4 不变。

## 1. 原子能力的分类（MySQL 正式版）

注册表是**唯一**记录"团队 - 原子能力 - 描述 - 版本 - 被谁引用 - 地址"的事实源，正式版用 **MySQL** 存储，通过 **API** 登记、读写和维护版本。建表脚本见 `registry/atomic-registry.schema.sql`。

## 1. 原子能力的分类

可被多个业务线复用的最小能力单元。**当前分类够用，后续按场景扩展**：

| 类型 | 含义 | 承载形式 |
|---|---|---|
| `skill` | 可执行的封装能力 | MA Skill |
| `tool` | 外部能力契约 | `tools/` 契约文档；实际执行靠 MCP 服务或 Skill 脚本 |
| `mcp` | 远端 MCP 服务 | Agent 的 `mcp_servers` |
| `knowledge` | 成套业务知识（需多位员工或多个业务线统一维护时登记） | 业务知识目录；引用方在 `registry/knowledge.json` 里用 `id`+`range`+`as` 引用，**构建器把该版本内容写入引用方这位数字员工自己的知识记忆库**（只读、不跨员工共享、占 L3 名额），之后提示词用 `{{knowledge:<as>/路径}}` 引用（交付规范 6.3） |
| `template` | 业务内容模板 | 业务知识目录中的模板文件；引用与加载方式同 `knowledge` |
| `agent` | **智能体包**：独立交付、独立发布、独立验证的智能体（`main` 或 `sub`，同构）；`main` 通过 `registry/agents.json` 按版本引用 `sub` | 智能体包（仓库路径 + 提交）；在 MA 上对应一个独立的 Agent 资源（见映射规范 6.2.2） |

> **类型取值与交付规范一致：** `skill`、`tool`、`mcp`、`knowledge`、`template`、`agent` 共六类。此前的 `prompt`（可复用提示词片段）已移除——交付规范中提示词是智能体包的一部分（`identity/`），不能单独登记、引用；`script` 同理（脚本归属于 Skill、知识或 pip 包，见交付规范 6.6）。已登记过这两类的历史数据，迁移时需改类型或下线。

**扩展方式**：`type` 是字符串字段，新增分类不需要改表结构。新增时只需：① 在 API 的允许值列表里增加该类型；② 在第 3 节补充该类型的 `address` 结构；③ 在《MA Agent 搭建映射规范（平台内部）》第 6 章补充该类型如何映射到 MA 资源。已有数据不受影响。

## 2. 表结构

**MVP 共 4 张表**（审计表为可选，MVP 不建）。关系如下：

```text
atomic_capability (1) ──< (N) atomic_capability_version
        │                          ▲
        └──< capability_agent_ref ─┘   (pinned_version_id)
                    │
                    └──< capability_agent_ref_history
registry_audit_log   （可选，MVP 不建）
```

| 表 | 作用 | 关键约束 |
|---|---|---|
| `atomic_capability` | 原子能力身份：标识、名称、类型、团队、责任人、描述 | `atomic_id` 全局唯一 |
| `atomic_capability_version` | **独立的版本记录表**：每个版本一行，含语义化版本、内容指纹、地址、依赖、兼容性、凭证类型、变更说明、状态 | `(capability_id, version)` 唯一；released 后内容字段不可变 |
| `capability_agent_ref` | **原子能力与 Agent 的关联表**：哪个智能体引用哪个能力、版本范围、当前锁定版本、该智能体的 MA Agent ID | `(capability_id, business_line_id, employee, agent, stage)` 唯一 |
| `capability_agent_ref_history` | 引用锁定的变更历史（声明、锁定、升级、回滚、移除） | 只追加 |
| `registry_audit_log` | **可选，MVP 不建**：全部变更的审计日志（前后内容、操作人、请求 ID）。建表脚本见 `registry/atomic-registry.optional-audit.sql` | 只追加 |

### 2.1 `atomic_capability`（身份，不随版本变化）

| 字段 | 含义 | 规则 |
|---|---|---|
| `atomic_id` | 业务标识 | 普通能力：`<owner_topic>.<name>`；`agent` 类型：`<业务线ID>.<数字员工ID>.<智能体ID>`（交付规范 2.1）。全局唯一，创建后**不可变**；`<name>` 为小写字母、数字、连字符，3 到 48 位；数字员工 ID、智能体 ID 各 3 到 24 位 |
| `owner_topic` | 提供方 | 提供该能力的**业务线 ID**，或中台保留标识 `platform`；与 `atomic_id` 前缀一致，冗余存储便于按提供方查询 |
| `name` | 名称（人读） | |
| `type` | 类型 | 见 第 1 节 |
| `team` | 提供团队 | 必须真实可联系 |
| `owner_primary` / `owner_backup` | 主责任人 / 备份责任人 | 各一名 |
| `description` | 描述 | 写"何时用、做什么、输入输出"，面向选用者 |
| `status` | 能力整体状态 | `active` / `archived` |
| `latest_released_version_id` | 当前最新的 released 版本 | 冗余字段，加速查询 |

### 2.2 `atomic_capability_version`（版本，内容不可变）

| 字段 | 含义 | 规则 |
|---|---|---|
| `capability_id` | 所属能力 | |
| `version` / `ver_major` / `ver_minor` / `ver_patch` | 语义化版本 | 三段数字冗余存储，用于排序与范围匹配 |
| `fingerprint` | 内容指纹 | SHA-256；内容不变则指纹不变 |
| `address` | 能力地址 | JSON，结构随类型不同，见 第 3 节 |
| `depends_on` | 依赖的其他原子能力 | `[{atomic_id, range}]`，用于计算影响面。**`agent` 类型的版本发布时，需在每项里补 `pin`（锁定的确切版本）**：子智能体引用的 Skill、MCP 在它发布时锁定，固定在这个版本里，引用它的数字员工不能改动 |
| `compat` | 兼容性声明 | 所需 MA 工具集类型、模型要求、文档快照日期 |
| `credentials` | 所需凭证类型 | 只写类型与用途，**不含值** |
| `changelog` | 本版本变更说明 | 面向使用方 |
| `status` | 版本状态 | 见 第 4 节 |
| `deprecated_at` / `retire_after` / `replaced_by_version_id` | 下线信息 | 即将下线时必填替代版本与计划下线时间 |
| `created_by` | 登记人 | |

**不可变规则**：`status` 为 `released` 及之后的版本，`address`、`fingerprint`、`depends_on`、`compat`、`credentials` 不得修改；只能修改状态与下线信息。需要修改内容必须发布新版本。该规则由 API 层强制，同时在数据库层可用触发器兜底（上线前评估）。

### 2.3 `capability_agent_ref`（被谁引用）

引用关系在**智能体**这一层发生。**每个智能体包（`main`、`sub` 同构）各自独立构建、独立引用能力**，所以本表按**引用方智能体 ID** 记录：一位数字员工下的每个智能体，对它引用的每个能力各一行。

- `main` 引用 `sub`（`agent` 类型的能力）同样是一行：被引用的 `sub` 是 `capability`，引用方是 `main`（对应交付规范 `registry/agents.json`）；
- `sub` 自己引用的 Skill、MCP，也记在本表（引用方是该 `sub`）；同时在 `sub` 发布时，把当时锁定的版本写入该 `agent` 版本的 `depends_on`（含 `pin`），随 `sub` 的版本固定；
- 智能体**不跨数字员工引用**（交付规范 2.2、2.3），所以 `agent` 类型能力的引用方与被引用方必然在同一个 `(business_line_id, employee)` 下；
- **层数校验**（对应接收校验 12，写入层再做一道）：`PUT /refs` 当被引用的能力 `type=agent` 时，必须同时满足：① 引用方 `agent` 对应的智能体，其 `role` 为 `main`；② 被引用的智能体 `role` 为 `sub`；③ 两者的 `(business_line_id, employee)` 相同；④ 引用方与被引用方不是同一个智能体。违反返回 422，错误码见 openapi 的 `Error.code`；
- 智能体自己的 `role`（`main`/`sub`）、`visibility`（`public`/`internal`）记在 `agent` 类型能力的**版本**里（见第 3 节 `agent` 的 `address`：`role`、`visibility`），不放在引用表。

| 字段 | 含义 | 规则 |
|---|---|---|
| `capability_id` | 被引用的能力 | |
| `business_line_id` / `employee` | 引用方业务线 ID / 数字员工（**`business_line_id` 是引用方**，与能力表 `owner_topic` 的提供方区分） | |
| `agent` | 引用方智能体 ID | 同一位数字员工内唯一的智能体 ID（交付规范 2.1），如 `pm`、`hotspot`；**取代此前的 `agent_role`**（`main`/`subagent:<名称>`）。多维表格已同步改名为 `agent`（见 0.1） |
| `stage` | 环境阶段 | `dev` / `staging` / `prod`；同一智能体在不同阶段可锁定不同版本 |
| `version_range` | 业务方声明的可接受范围 | 如 `^1.2.0` |
| `pinned_version_id` | 当前锁定的版本 | 声明后尚未发布时为空；同一能力在不同智能体上可锁定在不同版本 |
| `ma_agent_id` | 引用方智能体在 MA 上的 Agent ID | 锁定后回填，用于升级时定位 |
| `status` | `active` / `removed` | 移除时置 `removed`，不物理删除，以保留历史 |

### 2.3.1 读取权限（分析师研发环境）

**当前（MVP）：不开放 API，分析师研发环境（bot）直接读取飞书多维表格。**

- 只读权限在表格层面配置：只授予查看，不授予编辑；可读范围限定为"能力""版本"两张表，以及"引用"表中本数字员工所属业务线的记录；
- "引用"表和"引用历史"表里有其他业务线的引用记录，**bot 不应读到它们**：若多维表格无法按业务线做行级授权，则不给 bot 开放这两张表，"本数字员工已引用了什么"改由资源包自己的 `registry/skills.json`、`agents.json` 提供；
- 状态过滤由 bot 按 0.5 的展示规则执行（只提供 `released`，`draft`、`retired` 不展示）。

**后续（正式版）：** 上线 API 后，改为调用读取接口（`GET /capabilities`、`GET /capabilities/{atomic_id}`、`GET /capabilities/{atomic_id}/versions[/{version}]`、`GET /refs`），使用只读身份。鉴权不在 MVP 内（6.6），上线前须补上：只读身份不得调用任何写接口，`GET /refs` 默认只返回其所属业务线的引用。

### 2.4 查询示例

| 问题 | 查询思路 |
|---|---|
| 某能力某版本被哪些智能体锁定（升级影响面） | `GET /refs?atomic_id=…&pinned_version=…`；底层是 `capability_agent_ref` 按 `pinned_version_id` 关联版本表，限定 `status=active` |
| 某智能体用了哪些能力（含引用了哪些 `sub`）、各是什么版本 | 按 `(business_line_id, employee, agent, stage)` 查 `capability_agent_ref` |
| 某数字员工整体引用了什么 | 按 `(business_line_id, employee, stage)` 查，不带 `agent` |
| 某个 Skill 的某版本被哪些子智能体使用（升级影响面的另一半） | 查 `agent` 类型版本的 `depends_on` 中含该能力与 `pin` 的版本，再用 `GET /refs` 找引用这些子智能体版本的数字员工 |
| 某能力下一个满足 `^1.x` 的最新 released 版本 | 版本表按 `ver_major=1` 且 `status=released`，三段版本倒序取第一 |
| 某团队提供了哪些能力 | `atomic_capability` 按 `team` |
| 哪些能力即将下线、还有谁在用 | 版本表 `status=deprecated` 关联引用表 |

## 3. 能力地址

`address` 必须能让中台**自动取回该版本的确切内容**，不依赖人工转交：

| 类型 | `address` 结构 |
|---|---|
| `skill` | `{"repo": "...", "path": "...", "commit": "...", "ma_skill_id": "skill-…", "ma_skill_version": "1"}`；**MVP 仅支持仓库形式**。另预留 `market_skill_id`、`market_version` 两个可选字段（MVP 忽略），见第 11 节 |
| `tool` / `template` | `{"repo": "...", "path": "...", "commit": "..."}` 或 `{"bucket": "...", "key": "...", "sha256": "..."}` |
| `knowledge` | 同上，指向知识目录 |
| `mcp` | `{"url": "...", "credential_name": "..."}`；`url` 对应 Agent 的 `mcp_servers[].url`（MA 的 MCP 声明只有 `type: url`、`name`、`url`，**没有协议字段**，故地址里不记协议）；`credential_name` 只写凭证名称，不含值 |
| `agent` | `{"package_url": "https://…/<业务线>-<数字员工>-<智能体ID>-<版本>.zip", "sha256": "…", "role": "main\|sub", "visibility": "public\|internal", "ma_agent_id": "agent-…", "ma_agent_version": "5"}`；`role`、`visibility` 来自包的 `registry/agent.json`；`ma_agent_id`、`ma_agent_version` 在智能体发布时回填，`main` 据此写入 `multiagent.agents[]`。字段映射见 3.1 |

同一版本发布后**内容不可变**，修改必须发布新版本。

### 3.1 `agent` 类型：交付即登记，字段自动映射

交付规范 2.3 规定"智能体包的交付即登记"。**业务方不单独填写注册表**，智能体包通过接收校验、发布后，平台从包里自动录入：

| 注册表字段 | 来源（智能体包 `registry/agent.json` 等） |
|---|---|
| `atomic_id` | `id`（`<业务线ID>.<数字员工ID>.<智能体ID>`，与路径一致） |
| `owner_topic` | `id` 的第一段（业务线 ID） |
| `name` | 智能体 ID |
| `type` | 固定 `agent` |
| `team`、`owner_primary`、`owner_backup` | `owner.team`、`owner.primary`、`owner.backup` |
| `description` | `description` |
| 版本 `version` | `version` |
| 版本 `address` | `{package_url, sha256}` 为交付的压缩包链接与内容摘要（交付规范 2.6；以后有包管理平台可改为 `{repo, path, commit}`）；`role`、`visibility` 取自 `agent.json`；`ma_agent_id`、`ma_agent_version` 在构建后回填 |
| 版本 `fingerprint` | 压缩包的 SHA-256（即提交的 `sha256`） |
| 版本 `depends_on` | 该智能体**自己包内**引用的 Skill、工具（`registry/skills.json`、`tools.json`）在**该智能体发布时**解析出的确切版本：`[{atomic_id, range, pin}]`。**不含 `main` 对 `sub` 的引用**（那在"引用"表里） |
| 版本 `credentials` | 该智能体 `connections.yaml` 声明的凭证类型与用途，只写类型，不含值 |
| 版本 `changelog` | `registry/version_mapping.md` 中该版本的变更说明 |
| 版本 `status` | 通过接收校验后 `candidate`；经 `plan` 到 `staging`、验收通过后 `released`（见第 4 节） |

- 以上字段**不能在注册表里手改**，改动一律通过发布智能体包的新版本；注册表的写入来源只有构建流水线，避免与包内容不一致；
- `main` 与 `sub` 同构，都登记为 `agent` 类型；`role` 区分它们；
- **`depends_on` 的含义随类型不同**：普通能力的 `depends_on` 是它依赖的其他能力；`agent` 的 `depends_on` 是它**自己包内**引用的能力（带 `pin`）。

## 4. 状态与生命周期

版本状态机：

```text
draft ──→ candidate ──→ released ──→ deprecated ──→ retired
  │            │            ▲             │
  │            └────────────┘             └──→ released（撤销下线）
  └───────────────────────→ released（审核未启用时可直接发布）

预留（当前不启用）：draft / candidate ──→ in_review ──→ released
                                              └──→ rejected ──→ draft
```

| 状态 | 含义 | 规则 |
|---|---|---|
| `draft` | 草稿 | 内容可修改；不可被引用 |
| `candidate` | 候选 | 内容可修改；仅可被 `dev`、`staging` 阶段的引用锁定，**不得进入 `prod`** |
| `released` | 已发布 | 内容**不可变**；可被所有阶段引用 |
| `deprecated` | 即将下线 | 必须写明 `retire_after` 与替代版本；仍可被引用，新增引用需告警 |
| `retired` | 已下线 | 不可再被新引用；`referenced_by` 必须为空才能进入 |
| `in_review` / `rejected` | **预留** | 当前阶段**不做审核**，状态已在设计中预留；启用后 `draft`/`candidate` → `in_review` → `released`，不通过则 `rejected` |

**`agent` 类型的状态与阶段对应**（交付规范 2.3 的开发流程）：

| 智能体版本状态 | 谁能引用 |
|---|---|
| `candidate` | 同一位数字员工的 `main` 在 `dev`、`staging` 引用它，用于联调；**不得进 `prod`** |
| `released` | `main` 可在 `prod` 引用（需 `main` 自己也通过验收） |
| `deprecated` | 仍可被引用，新增引用告警 |
| `retired` | 要求没有任何 `main` 还在引用它（`active` 引用为空） |

**`agent` 版本发布到 `prod` 前**，还要通过接收校验 17：`visibility: internal` 的智能体，其渠道可用范围白名单非空。注册表不存渠道配置，该校验由构建流水线做，结果不写回注册表。

**审核的预留方式**：状态字段与状态机已包含 `in_review`、`rejected`，API 层有一个开关（默认关闭）。关闭时，这两个状态不可达，`draft` / `candidate` 可直接发布；启用后发布必须先经过 `in_review`，并需要补充"审核人、审核时间、审核意见"字段（届时再加表，不影响现有结构）。

## 5. 引用声明与锁定

业务方在使用该能力的**智能体所在的包**里声明引用，**写法完全一致**：

| 引用的是 | 声明在 | 示例 |
|---|---|---|
| Skill | 该智能体包的 `registry/skills.json` | `{ "id": "platform.report-cover", "range": "^1.2.0" }` |
| 外部工具 | 该智能体包的 `registry/tools.json` | `{ "id": "platform.search", "range": "^1.0.0" }` |
| 共享知识 / 模板 | 该智能体包的 `registry/knowledge.json`（另带 `as`：在本数字员工里的目录名） | `{ "id": "platform.report-glossary", "range": "^1.0.0", "as": "共享术语" }` |
| 子智能体（仅 `main`） | `main` 的 `registry/agents.json` | `{ "id": "hotspot", "range": "^1.0.0", "alias": "hotspot" }`（`id` 可简写为同一位数字员工内的智能体 ID，注册表里对应 `<业务线>.<数字员工>.hotspot`） |

- 引用它的智能体由它所在的包决定（交付规范 2.3）：构建时为该智能体写一条 `capability_agent_ref`；若该智能体是 `sub`，发布时还要把锁定版本写入它自己 `agent` 版本的 `depends_on`；
- `range`：业务方声明可接受的版本范围；
- 构建时中台为每个 `(智能体, 阶段)` 解析 `range`，在 `capability_agent_ref` 中写入 `pinned_version_id`，同时更新 `ma_agent_id`，并写入 `capability_agent_ref_history`；
- `pin` 是**按智能体分别**锁定的确切版本，同时写入映射规范的资源锁定清单（7.5）；
- **增量交付**（交付规范 2.4）里的 `add / update / remove_entries`（类型 `skills`、`tools`、`agents`）对应到这里：新增是新建引用记录，修改版本范围是 `PUT /refs` 更新 `version_range`（并按规则重新锁定），移除是 `DELETE /refs`（软删除，保留历史）；
- `referenced_by` 不单独存储，由 `capability_agent_ref` **实时查询得到**，保证"被谁引用"始终准确：

```json
{
  "id": "platform.report-cover",
  "referenced_by": [
    { "business_line_id": "sales", "employee": "assistant", "agent": "pm", "stage": "prod", "range": "^1.2.0", "pin": "1.2.3" },
    { "business_line_id": "sales", "employee": "assistant", "agent": "cleaner", "stage": "prod", "range": "^1.0.0", "pin": "1.0.5" }
  ]
}
```

- 业务线不得复制原子能力内容到资源包。

## 6. API（MVP）

**MVP 范围**：先回答三个问题——有哪些能力、各有哪些版本、哪个智能体用了哪个版本。共 **11 个接口**。鉴权、流水线对接、审核、自动解析版本范围等**不在 MVP 内**，见 6.6。

### 6.1 通用约定

| 项 | 约定 |
|---|---|
| 风格 | REST，JSON，路径前缀 `/registry/v1` |
| 错误 | 统一 `{code, message, details}`；业务校验失败 422，冲突 409，不存在 404 |
| 分页 | 列表接口 `page`、`page_size`（默认 20，最大 100）；返回总数 |
| 凭证 | 请求与响应中**不得出现凭证值**，字段里只写类型与用途 |
| 操作人 | 写接口请求头 `X-Operator` 必填，记入历史与日志；**MVP 不校验其真实性** |
| 并发 | 修改类接口带 `If-Match: <updated_at>`，不匹配返回 409，防止覆盖 |

### 6.2 原子能力（4 个）

| 方法与路径 | 作用 | 关键规则 |
|---|---|---|
| `POST /capabilities` | 登记原子能力 | `atomic_id` 唯一；`type` 必须在允许值内（`skill`、`tool`、`mcp`、`knowledge`、`template`、`agent`）；`team`、责任人必填；`atomic_id` 前缀须与 `owner_topic` 一致；**`type=agent` 时 `atomic_id` 须为三段 `<业务线>.<数字员工>.<智能体ID>`，且仅构建流水线可写入（3.1）** |
| `GET /capabilities` | 列表查询 | 过滤：`team`、`type`、`status`、`owner_topic`、`q`（名称/描述关键词） |
| `GET /capabilities/{atomic_id}` | 详情 | 含最新 released 版本摘要 |
| `PATCH /capabilities/{atomic_id}` | 修改团队、责任人、描述 | `atomic_id`、`type` 不可改；**`type=agent` 的这些字段来自 `registry/agent.json`，不允许手改**（3.1） |

### 6.3 版本（4 个）

| 方法与路径 | 作用 | 关键规则 |
|---|---|---|
| `POST /capabilities/{atomic_id}/versions` | 新增版本，初始 `draft` | 版本号唯一且大于已有最高版本；`address`、`fingerprint` 必填；校验 `depends_on` 引用的能力存在。**内容一旦写入不再原地修改，需要改就新增版本** |
| `GET /capabilities/{atomic_id}/versions` | 版本列表 | 过滤 `status`；按语义化版本倒序 |
| `GET /capabilities/{atomic_id}/versions/{version}` | 版本详情 | 含引用数 |
| `POST /capabilities/{atomic_id}/versions/{version}/transition` | 状态变更 | 请求体 `{to, reason}`；按第 4 节状态机校验；`released`→`deprecated` 必须带 `retire_after`、`replaced_by`；→`retired` 要求无 `active` 引用 |

### 6.4 引用（3 个）

引用接口同时承担"声明、锁定、升级、回滚"：它们都是对同一条引用记录的写入，区别只是 `pinned_version` 变不变。

| 方法与路径 | 作用 | 关键规则 |
|---|---|---|
| `PUT /refs` | 声明或更新引用，并指定锁定版本 | 请求体：`atomic_id`、`business_line_id`、`employee`、`agent`、`stage`、`version_range`、`pinned_version`（可选）、`ma_agent_id`（可选）、`reason`。按 `(atomic_id, business_line_id, employee, agent, stage)` 幂等。`pinned_version` 变化时自动写入引用历史；`candidate` 版本不得锁定到 `prod`；`retired` 版本不得被新锁定；`draft` 版本不可被引用；**被引用的能力 `type=agent` 时做层数校验：引用方 `role=main`、被引用方 `role=sub`、`(business_line_id, employee)` 相同、不是同一个智能体（2.3），违反 422** |

`PUT /refs` 的行为规则（实现须一致）：

| 情形 | 处理 | 历史动作 |
|---|---|---|
| 唯一键不存在 | 新建引用；未带 `pinned_version` 时只声明范围 | `declare`（未锁定）/ `pin`（已锁定） |
| 唯一键已存在，`pinned_version` 不变 | 只更新 `version_range` 等字段，**幂等，不写历史** | — |
| 唯一键已存在，`pinned_version` 变大 | 更新锁定版本 | `upgrade` |
| 唯一键已存在，`pinned_version` 变小 | 更新锁定版本；`reason` 必填 | `rollback` |
| 被 `DELETE` 软删除的引用再次 `PUT` | 恢复为 `active` | 按上面规则判断 |
| 引用的能力不存在、锁定版本不存在 | 422 | — |
| `type=agent` 且违反层数校验（引用方不是 `main`、被引用方不是 `sub`、跨数字员工、自引用） | 422（`AGENT_REF_INVALID`） | — |

版本的"大小"按语义化版本三段数字比较，与字符串顺序无关。
| `DELETE /refs/{ref_id}` | 移除引用 | 软删除，置 `status=removed`，写入历史 |
| `GET /refs` | 查询引用 | 过滤：`atomic_id`、`pinned_version`、`business_line_id`、`employee`、`agent`、`stage`、`status`。**同时用于"被谁引用"、"某智能体用了哪些能力"、"升级影响面"三种场景** |

三种典型用法：

| 想知道 | 调用 |
|---|---|
| 某能力的 1.2.3 版本被哪些智能体锁定（影响面） | `GET /refs?atomic_id=sales.report-cover&pinned_version=1.2.3&status=active` |
| 某智能体用了哪些能力、各是什么版本 | `GET /refs?business_line_id=sales&employee=assistant&agent=pm&stage=prod` |
| 把某智能体回滚到旧版本 | `PUT /refs`，`pinned_version` 填旧版本，`reason` 写原因 |

### 6.5 接口定义

完整的请求、响应字段与示例见 **`registry/openapi.yaml`**（OpenAPI 3.0，已通过标准校验器）。几点说明：

- 版本号写在路径里（`/versions/{version}`），状态变更使用独立路径段 `/transition`，不使用 `:transition` 这类冒号后缀（Go 标准库路由不支持）；
- 版本号 MVP 只支持 `主.次.修订`，**不支持预发布与构建元数据后缀**（如 `1.2.3-rc1`）；
- `address` 的必填字段随能力 `type` 不同，**由服务端按 `type` 校验**，schema 层面只做结构约束；
- 业务错误码共 13 个（含新增的 `AGENT_REF_INVALID`；此前为 12 个），见 OpenAPI 的 `Error.code`；

### 6.6 不在 MVP 内（后续按需加）

| 项 | 为什么先不做 | 以后怎么加 |
|---|---|---|
| 鉴权与团队授权 | 先在内网小范围使用 | 在网关或框架层加，写接口按 `owner_topic` 授权；`X-Operator` 已预留 |
| 按版本范围自动解析并锁定（`:resolve`） | 流水线对接暂不考虑 | 新增一个接口，读取 `version_range` 选最高合法版本，内部复用 `PUT /refs` 的写入逻辑 |
| 修改版本内容（`PATCH` 版本） | MVP 要改就新发版本 | 仅 `draft`/`candidate` 开放 |
| 归档能力（`:archive`） | 无归档需求 | 新增，仅无 `active` 引用时允许 |
| 审核（`in_review`、`rejected`） | 当前阶段不做审核 | 状态已预留，加开关和审核字段 |
| 幂等键（`Idempotency-Key`） | MVP 调用量小，`PUT /refs` 已按唯一键幂等 | 加在创建类接口上 |
| 审计日志表 `registry_audit_log` | 引用历史表加应用日志已够用 | 后续补表，历史版本变更再回填 |

## 7. 使用与升级

| 场景 | 处理 |
|---|---|
| 新增引用 | `PUT /refs` 声明并写入锁定版本；`candidate` 不得进入 `prod`，`retired` 不得被新锁定；兼容性与凭证的核对 MVP 阶段由调用方负责 |
| 发布修订版本 | 兼容修复。落在引用方 `version_range` 内的，用 `GET /refs` 找到引用方并通知，由其用 `PUT /refs` 更新锁定版本；**`agent` 类型**：落在 `main` 的 `range` 内的，平台重新构建 `main` 并在回执里请业务方确认（交付规范 2.4），`main` 的包不需要交付文件 |
| 发布次要版本 | 向后兼容的新增。引用方按 `version_range` 决定是否纳入 |
| 发布主要版本 | 不兼容变更。**不自动纳入任何引用方**，逐个业务线评审、灰度、改 `version_range` 后升级；**`agent` 类型**：`main` 的负责人评审后，在 `registry/agents.json` 改该条引用的 `range`（增量登记 `update_entries: ["agents:<子智能体ID>"]`），作为 `main` 自己的一次变更 |
| 影响面评估 | 发布前调用 `GET /refs?atomic_id=…&pinned_version=…&status=active`，得到受影响的业务线、数字员工、**具体智能体（含子智能体）**；验证范围精确到这些智能体；再结合 `depends_on` 人工评估间接影响（MVP 不自动计算依赖传递） |
| 紧急修复 | 可标记强制升级，中台逐个 `PUT /refs` 更新锁定版本并通知；仍走映射规范第 9 章灰度，不得跳过冒烟 |
| 下线 | 先 `transition` 到 `deprecated`（带计划下线时间与替代版本），通知所有引用方，迁移完成且过保留期后 `retired`；**`agent` 类型**：`main` 移除对某 `sub` 的引用（`remove_entries: ["agents:…"]`）只是移除引用，**`sub` 的包和注册记录保留**；`sub` 本身下线要求没有任何 `main` 还在引用它 |
| 回滚 | `PUT /refs` 将 `pinned_version` 改回旧版本（`reason` 写明原因），系统自动记入引用历史；已发布内容不可变，回滚总是安全 |

升级只影响新建的会话与按映射规范第 9 章升级的存量会话；运行中的会话保持原版本。

## 8. 与构建流程的衔接

- **MVP 阶段流水线暂不对接注册表**。业务线构建发布时，由调用方直接用 `PUT /refs` 写入锁定版本；锁定清单（映射规范 7.5）与 `capability_agent_ref` 应保持一致，MVP 阶段靠人工核对，流水线对接后改为 `plan` 阶段自动检查漂移；
- 引用的能力在注册表中不存在、状态不允许当前阶段、或兼容性不满足时，`plan` 失败；
- 平台升级时，按映射规范 9.4 通过 `compat` 字段在注册表里筛选受影响的版本，再用 `GET /refs` 找到受影响的智能体。

## 9. 注册表自身的运维要求

- MySQL 使用 InnoDB、`utf8mb4`；时间统一存 UTC；
- **服务需支持分布式部署**：注册表服务无状态，可多实例；乐观锁（`If-Match`）与引用的唯一键幂等都落在 MySQL，不依赖实例内存；
- 迁移脚本版本化，变更表结构走评审；
- 每日备份；`capability_agent_ref_history` 只追加，不做物理删除（审计表启用后同理）；
- 读多写少，列表接口加上述索引覆盖，必要时读写分离。

## 10. 标识与归属

注册表不单独设置命名空间。归属由**业务线 ID** 表达，规则见《MA Agent 搭建映射规范（平台内部）》4.2。`agent` 类型的 `atomic_id` 为 `<业务线ID>.<数字员工ID>.<智能体ID>`（交付规范 2.1）。**注意：这与普通能力的 `<owner_topic>.<name>` 两段式不同，多了一层数字员工 ID；`atomic_id` 的格式校验对 `agent` 类型需单独处理（前缀仍是业务线 ID，第二段起是数字员工与智能体）。`agent` 类型的引用约束比普通能力更严：只能被同一位数字员工内的 `main` 引用，不存在"其他业务线同意"的路径**

| 项 | 规则 |
|---|---|
| `atomic_id` 前缀 | 必须是已分配的**业务线 ID**，或中台保留标识 `platform` |
| 登记权限 | `POST /capabilities` 时，调用方必须被授权操作 `atomic_id` 前缀对应的业务线（`platform` 仅中台管理员）；`team` 须与该业务线的归属团队一致 |
| 业务线 ID 的来源 | 由中台统一分配，全局唯一，分配后不可变更，回收后永久保留、不再分配；分配与回收的台账由中台维护，**当前不在注册表中建表**（业务线数量少、变更不频繁） |
| 不存在的前缀 | 前缀不是已分配的业务线 ID 时，登记返回 422 |
| 引用约束 | 业务线可以引用本业务线或 `platform` 的能力（`agent` 类型不适用，见上）；**引用其他业务线的能力**须该能力的提供方业务线同意（记录在 `capability_agent_ref` 之外的授权表，当前阶段不实现，默认拒绝） |

> 如果以后业务线数量增多、需要注册表自己校验"前缀是否已分配"，再增加一张业务线台账表即可，不影响现有结构。

## 11. 与 Skill 市场的关系（预留，MVP 不打通）

公司已有独立部署的 Skill 市场（`bmc_skills_market`，BlueFlare 通过代理路由对接）。它是 Skill 的发布与分发平台，已具备：版本历史、审核（待审、通过、驳回）、私有/公共/团队发布范围、向 agent 安装并检查更新。

**MVP 决策：先不打通，后面再接。** 打通与否的成本对比见下，结论是后补几乎不返工，前提是现在预留好扩展点。

### 11.1 两者的分工（打通后）

| 内容 | 谁管 |
|---|---|
| Skill 的**内容（ZIP）**、审核、发布范围 | Skill 市场 |
| Skill 的**版本台账**与"哪个 MA 智能体锁定哪个版本" | 注册表（`capability_agent_ref` 精确到主/子智能体和阶段，市场的"安装"记录不覆盖它） |
| tool、mcp、knowledge、template、agent 五类 | 注册表直接登记，市场不管 |

注册表**不存内容，只存地址**。打通后，Skill 的地址可以指向市场。

### 11.2 现在预留了什么

| 预留项 | 位置 | 说明 |
|---|---|---|
| `address.market_skill_id`、`address.market_version` | `registry/openapi.yaml` 的 `Address` | 可选字段，**MVP 服务端忽略**，允许携带 |
| 版本号格式 | **部分对齐，待验证** | BlueFlare 的技能发布表单对版本号做了前端校验，要求 `主.次.修订`（正则 `^\d+\.\d+\.\d+$`），与注册表一致。**但这只是 BlueFlare 客户端的校验，Skill 市场服务端是否允许预发布后缀（如 `1.0.0-rc1`）未验证**；若服务端允许、且有人绕过 BlueFlare 直接发布，同步时会遇到注册表不支持的版本号 |
| 状态映射 | 设计上已兼容 | 市场的待审、通过可对应注册表的 `candidate`、`released`，**走现有 `/transition` 接口**，不需新增状态 |

### 11.3 后续打通要做什么（纯增量，不改表、不改现有接口语义）

| # | 工作 | 说明 |
|---|---|---|
| 1 | `skill` 类地址放开「市场形式」 | `market_skill_id` + `market_version` 可作为仓库形式之外的另一种必填组合；这是向后兼容的放宽 |
| 2 | 登记时校验市场里存在该技能与版本 | 需要调用市场的查询接口 |
| 3（可选）| 版本同步 | 定时读取市场技能的版本，把已通过审核的版本登记为注册表的 `released` |
| 4 | 内容指纹校验 | 取回市场 ZIP 后与登记的 `fingerprint` 比对 |

### 11.4 暂不打通的原因，以及打通前需要拿到什么

| 原因 | 打通前需要 |
|---|---|
| 目前只看到 BlueFlare 的**客户端代理层**，没有 Skill 市场服务端的真实接口契约 | 接口文档（Apifox 项目 8215769）或测试用的访问凭证；确认鉴权方式（BlueFlare 用 unionId 签发短期 JWT，管理 CLI 用 API Key） |
| 没有发现 Skill 市场与 MA 对接的现成做法 | 明确 **MA 上的智能体如何使用市场里的 Skill**：市场里是 ZIP，MA 的 Skill 需要上传到 MA，这中间由谁下载、谁上传 |
| 市场服务端对版本号格式的约束未验证（仅见 BlueFlare 前端校验） | 确认服务端是否允许预发布与构建元数据后缀；若允许，需决定同步时跳过、映射或扩展注册表版本号格式 |
| 市场是否允许改写已发布版本的内容未验证 | 注册表依赖"released 后内容不可变"；BlueFlare 文档说已存在的版本号会返回冲突，是好信号，但需要实测 |

### 11.5 成本对比

| | 现在打通（含自动同步） | 只打通"引用"（登记时校验存在） | 先不打通，后面再接（本期选择） |

### 11.6 对交付规范的影响（提示）

给业务方的《MA Agent 搭建交付规范》第 6 章（6.1）目前把 Skill 的登记地址描述为"仓库路径加提交"。**打通后，业务方登记 Skill 的方式会变**（改为在市场发布，再引用市场的技能与版本）。交付规范 v1.4 当前用于与业务对齐，打通时需由负责人决策是否修改并同步业务，本期不涉及。
