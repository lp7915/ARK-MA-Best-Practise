# MA Agent 搭建交付规范

> 版本：v1.5 · **面向业务方及其研发**（相对上一版的变化见文末"修订记录"）
> **适用范围：** 基于火山方舟 Managed Agents（MA）底座搭建数字员工（Agent）。本文规定：为了让平台在 MA 底座上为你们搭建数字员工，你们需要交付什么、格式是什么、可复用的能力怎么登记、后续如何增量更新。
> **你们交付的是什么：** 一个或多个"智能体包"——每个智能体的岗位提示词、业务知识、可执行能力、外部系统声明、长期记忆。同一位数字员工的多个智能体里，有一个对外的入口（`main`），其余是被它引用的子智能体（`sub`）；**每个智能体都是独立交付、独立发布、独立验证的单元，所有智能体包结构相同**（见第 2 章）。平台据此在 MA 上创建并运行对应的 Agent。后续更新可以只交付变化的部分（见 2.4）。
> 平台如何在 MA 上落地，不是业务方需要关心的内容，见平台内部的《MA Agent 搭建映射规范》。
> 配套：《能力需求收集表》（收集这份交付规范里需要业务方提供的内容）。

## 0. 开发前：先明确你的业务架构

本规范只规定**交付格式**——你交什么、放哪里、怎么写。它**不规定**"你的数字员工该有几个智能体、谁当入口、谁负责什么"：这些由**你这条业务线的业务架构**决定，规范的目录结构只是承载它的容器。

动手交付前，先准备/确认本业务线的一份**业务架构背景**（每条业务线各自一份，例如 ADA 的《ADA 设计目标与架构》）。它至少讲清四件事：

| 要讲清什么 | 落点 |
|---|---|
| 1. 设计目标 | 这个数字员工要为谁解决什么问题 |
| 2. 角色分工 | 谁是入口（`main`）、哪些是被它引用的子智能体（`sub`）、各自职责与边界 |
| 3. 执行能力层 | 哪些是可复用 Skill、哪些是外部工具 / 服务 / 脚本 |
| 4. 数据供应链 | 接哪些数据源、研究或企业资源，怎么接入 |

落地到智能体包只有一条规则：**业务架构里的每个角色 = 一个智能体包**——入口角色 `role: main`、被引用角色 `role: sub`（`sub` 不能再引用别人）；跨角色都要用的公共能力，登记为可复用能力去引用，或各包各存一份副本（见 2.2、第 6 章）。

> **示例（ADA）**：ADA 的架构背景（《ADA 设计目标与架构》v0.7.20，全文见随规范提供的示例 `examples/ADA-ARCHITECTURE-AI-v0.7.20.md`）把数字员工定为"客户统一面对 ADA；PM 是主 Agent；领域 / 策略 / 通用三类分析师是同级子 Agent；Validator 是 Skill"。对应到智能体包：

| ADA 架构里的角色 | 智能体包（`role`） |
|---|---|
| PM / Project Agent（主 Agent） | `pm`（`main`） |
| 领域分析师（Topic / T） | `t`（`sub`） |
| 通用数据分析（G） | `g`（`sub`） |
| 策略（S） | `s`（`sub`） |
| Validator（关键门禁） | **不建 Agent**，登记为可复用 **Skill** |

架构背景由业务线自行维护、随交付一并提供，平台据此核对角色分工是否与交付一致；平台不改写你们的业务设计。

## 1. 你需要交付什么

在 MA 底座上搭建一位数字员工，需要你们交付它的各个**智能体包**（一个业务线下可以有多位数字员工，一位数字员工有一个或多个智能体），保存可以跨项目、跨任务复用的稳定内容：业务知识、岗位提示词、可执行能力、外部系统契约、输入输出结构。

智能体包**不包含**：密钥与密码、某次任务产生的数据、会话与运行记录。

平台会在你们交付的基础上补全模型选型、资源命名、依赖版本、存储规划等需要全局视野的部分，并把结果回给你们确认。

### 1.1 三条基本原则

| 原则 | 含义 |
|---|---|
| 信息唯一归属 | 每类信息只放在一个位置，别处只引用、不复制 |
| 稳定与实例分离 | 资源包只放稳定内容；任务、运行、会话产生的信息不放进来 |
| 密钥不入包 | 资源包里只写凭证的名称、类型、用途、提供人，不写值 |

## 2. 智能体包

**交付的基本单位是"智能体包"。** 一位**数字员工**由一个或多个智能体组成：对外有一个入口智能体（`main`），背后可以有若干被它引用的子智能体（`sub`）。每个智能体各交付一个独立的包；同一位数字员工的多个包放在同一个数字员工目录下：

```text
<业务线ID>/
└── <数字员工ID>/                       # 同一位数字员工的所有智能体
    ├── <智能体ID>/                    # 一个智能体包（可以是 main，也可以是 sub）
    │   ├── identity/
    │   │   ├── identity.md            #   角色、职责、边界（必须）
    │   │   ├── orchestration.md       #   工作流程与分工（可选）
    │   │   └── handoff.md             #   交接规则（可选）
    │   ├── knowledge/                 #   业务知识（目录名与内部结构为建议，可自定义，见 5.2）
    │   │   ├── standards/             #     生产与验收口径
    │   │   ├── templates/             #     业务内容模板
    │   │   ├── examples/              #     可复用案例（标准、边界、错误、回归）
    │   │   └── glossary.md            #     术语表
    │   ├── tools/                     #   外部能力契约：只写接口、用途、所需凭证类型
    │   ├── skills/                    #   可直接执行的封装能力
    │   │   └── <能力名>/
    │   │       ├── SKILL.md
    │   │       ├── prompts/
    │   │       ├── scripts/
    │   │       └── references/
    │   ├── io/                        #   输入输出契约（见 5.6）
    │   │   ├── README.md
    │   │   └── contracts/
    │   ├── memory/                    #   长期记忆（仅需要时设置，见 5.5）
    │   │   ├── stores.yaml
    │   │   └── <路径>/*.md
    │   ├── acceptance/                #   验收用例（见 9.2）
    │   │   └── cases.yaml
    │   ├── knowledge.yaml             #   声明哪些目录属于业务知识（见 5.2）
    │   ├── connections.yaml           #   外部系统与凭证声明（见 5.4），不含凭证值
    │   ├── change-set.yaml            #   仅增量交付时提供（见 2.4）
    │   └── registry/
    │       ├── agent.json             #   身份、版本、角色、可见范围（见 2.3）
    │       ├── agents.json            #   引用的子智能体，仅 role=main 才有（见 2.3）
    │       ├── skills.json            #   引用的可复用能力（见第 6 章）
    │       ├── knowledge.json         #   引用的共享知识与模板，有则放（见 6.3）
    │       ├── tools.json
    │       ├── environment.json       #   运行环境需求（见 5.3）
    │       └── version_mapping.md     #   人可读的版本说明
    └── <另一个智能体ID>/               # 同一位数字员工的其他智能体，结构相同
```

不适用的目录可以省略，但 `identity/identity.md` 与 `registry/agent.json` 必须存在。**所有智能体包结构完全相同**，没有"数字员工包"和"子智能体包"之分，区别只在 `registry/agent.json` 里的 `role` 和是否引用了别的智能体。

### 目标态：你交付的这套目录，最终长成什么

一位数字员工交付后，在 MA 上运行时是"一个入口 + 若干子智能体 + 一套共享资源"。这里先给一张整体示意（不涉及 MA 内部细节，那些见平台内部规范）：

```text
用户 ──飞书 / 网关──▶ ┌───────────────┐
                      │  main（入口）   │
                      └───────┬───────┘
      ┌───────────┬───────────┼───────────┬───────────┐
      ▼           ▼           ▼           ▼           ▼
   sub A       sub B       sub C       sub D       sub E
      └───────────┴───────────┴───────────┴───────────┘
   共享层：业务知识 · 长期记忆 · 外部凭证 · 运行环境（整位数字员工共享）
```

- 用户永远只和 `main` 对话；`sub` 由 `main` 按提示词分派（见 2.3、5.1），用户不直接触达；
- `main` 和每个 `sub` 各是一个独立交付、独立发布、独立验收的智能体包；
- 业务知识、长期记忆、凭证、运行环境不跟着某个智能体走，而是**一次会话、整位数字员工共享**（见 2.3「资源怎么在运行时生效」）。

### 2.1 标识规则

| 标识 | 规则 |
|---|---|
| 业务线 ID | 小写字母、数字、连字符，3 到 24 位；**由平台统一分配，全局唯一**（不同业务方之间不会重复），业务方提出建议、平台确认；`platform` 为平台保留，不能使用 |
| 数字员工 ID | 小写字母、数字、连字符，3 到 24 位；在业务线内唯一；由业务方提出、平台确认 |
| 智能体 ID | 小写字母、数字、连字符，3 到 24 位；**在同一位数字员工内唯一**；由业务方提出、平台确认 |
| 智能体完整标识 | `<业务线ID>.<数字员工ID>.<智能体ID>`，也是它在原子能力注册表里的能力标识（类型 `agent`）；引用时在同一位数字员工内可简写为 `<智能体ID>` |

以上 ID 确认后**不可变更**。路径中的三级 ID 必须与 `registry/agent.json` 一致。

### 2.2 不同数字员工之间

- 不同数字员工的包**完全独立**，**智能体不能被其他数字员工引用**；
- 多位数字员工都需要的内容（例如同一套口径），**各存一份副本**，副本以各自的包为准，修改一方不会影响另一方；
- 如果某项内容确实需要多位数字员工、甚至多个业务线**统一维护、统一升级**，应把它登记为可复用能力（见第 6 章：Skill、工具、知识、模板等），通过引用使用，而不是复制。

### 2.3 智能体的角色与引用

一位数字员工对外只有一个入口。每个智能体包在 `registry/agent.json` 里声明自己的**身份、角色**和**可见范围**：

```json
{
  "id": "zhilan.hotspot-team.pm",
  "version": "1.2.0",
  "role": "main",
  "visibility": "public",
  "owner": { "team": "智蓝数据服务部", "primary": "张三", "backup": "李四" },
  "description": "面向用户的入口：理解需求、分派任务、汇总结果"
}
```

| 字段 | 取值与规则 |
|---|---|
| `id` | 智能体完整标识（2.1），必须与路径一致 |
| `version` | 语义化版本，规则见 7.1；每个智能体包**独立版本** |
| `role` | `main`：数字员工的入口，**可以引用子智能体**，**不能被别的智能体引用**；`sub`：被引用的子智能体，**不能再引用别的智能体** |
| `visibility` | `public`：生产环境可以面向所有用户；`internal`：**生产环境只对内部指定范围开放**，不得配置成"不限使用范围"（见下）。**`role: sub` 必须是 `internal`**（子智能体在线上一定是内部的）；`role: main` 可以是 `public`，也可以是 `internal`（例如只面向内部员工的数字员工） |

#### 引用子智能体：`registry/agents.json`（仅 `main`）

`main` 引用哪些子智能体，写在 `registry/agents.json` 里。**它和引用 Skill 的 `registry/skills.json` 是同一种写法：指明引用谁、接受哪个版本范围**，只是多了一个别名：

```json
[
  { "id": "hotspot", "range": "^1.0.0", "alias": "hotspot" },
  { "id": "insight", "range": "^2.0.0", "alias": "insight" }
]
```

| 字段 | 说明 |
|---|---|
| `id` | 被引用的子智能体，同一位数字员工内的智能体 ID（2.1）；必须是 `role: sub` |
| `range` | 接受的版本范围，具体锁定到哪个版本由平台在发布时决定（与 6.3 的 Skill 引用一致） |
| `alias` | `main` 在 `orchestration.md` 里称呼它的名字 |

- 只有 `role: main` 的包才有这个文件；`sub` 不得有（不能再引用别人）；
- 对 Skill 和对子智能体的引用，增量时用同一套登记方式（见 2.4）：新增、修改版本范围、移除，都按"记录"处理；
- **`registry/agent.json` 只放身份信息**（`id`、`version`、`role`、`visibility`、`owner`、`description`），不放任何引用。

**一位数字员工里有且仅有一个 `role: main` 的智能体**（有多个对外入口的，请拆成多位数字员工）。

`role` 与 `visibility` 是两个独立的字段：

| | `visibility: public` | `visibility: internal` |
|---|---|---|
| `role: main` | 面向所有用户的数字员工 | 只面向内部指定人群的数字员工 |
| `role: sub` | **不允许** | 子智能体（线上一定是这一种） |

#### 为什么要显式声明 role 和 visibility

- **层数不会超限**：MA 的多智能体只展开一层。`main` 只能引用 `sub`、`sub` 不能再引用别的智能体，平台在**交付阶段**就能检查，不需要等到运行时出问题；
- **子智能体可以独立开发、调试**：`sub` 也是完整的智能体，可以单独配置一个 bot 用于对话和任务调试，验证没问题后，再被 `main` 引用并生效；
- **线上不暴露子智能体**：`sub` 的 `visibility` 固定为 `internal`，平台在交付阶段检查。用户只通过 `main` 触达 `sub`；
- **`internal` 在生产环境不得"不限使用范围"**：不论 `main` 还是 `sub`，`internal` 的智能体发布到生产前，平台检查它的 bot 可用范围（白名单）**不为空**，不满足则不予发布。`sub` 的 bot 只能面向研发人员，或者干脆不配对话入口；`internal` 的 `main` 则限定在内部指定的人群或部门；
- 开发和测试环境不受此限制，方便你们调试。

#### 开发流程

```text
sub 智能体：独立开发 → 用自己的 bot 调试 → 单独验收 → 发布（得到一个版本）
                                                         ↓
main 智能体：在 registry/agents.json 里引用这个版本 → 集成验收 → 发布 → 线上用户只通过 main 触达 sub
```

- 子智能体发布前，在 dev、staging 阶段可以被 main 引用它的"候选"版本，用于联调；**生产环境只能引用"已发布"的版本**（见 6.2、7.3）；
- main 引用子智能体时**固定版本**：子智能体之后发布新版本，不会自动改变已经发布的 main。要纳入新版本，按 2.4 的规则处理。

#### 资源怎么在运行时生效

资源按平台层级分两类，**构建时的处理不同**：

| 资源 | 属于哪一层 | 平台怎么处理 |
|---|---|---|
| Skill、外部工具（MCP）、提示词 | **智能体自己** | 各智能体各用各的，互不合并 |
| 业务知识、长期记忆库、外部系统凭证、运行环境 | **一次会话，整位数字员工共享** | 构建时，把 main 和它引用的全部 sub（已锁定版本）声明的这些资源**合并**到同一次会话里 |

合并规则：

- **并集，同名不覆盖**：不同包里同名的知识目录或记忆库各自独立，平台自动加所属智能体的前缀以区分；
- **凭证**：凭证值由提供人单独交给平台，存入这位数字员工自己的凭证库；包里只声明。同一个 `secret_name`、同样的域名在多个包里声明的，合并为一条；`secret_name` 相同但域名或类型不同，构建失败并指出冲突来源。**子智能体单独调试时用自己的凭证**，被 main 引用后用这位数字员工的凭证库，所以凭证值在 main 引用时需要确认一次；
- **运行环境**：各包的依赖合并成一份，合并后必须自洽（不能同时要求 `numpy<2` 与 `numpy>=2`），冲突时构建失败，并指出是哪两个包冲突；
- **容量**：合并后的总数计入平台限制（见《MA Agent 搭建容量限制说明》）。引用的子智能体越多，知识目录和记忆库的总数越容易触及上限，请在规划时一起计算；
- **不做按智能体的隔离**：知识、记忆库、凭证、文件系统属于整次会话，main 和 sub 都能访问；长期记忆库的读写权限对所有智能体一致。需要严格隔离的敏感内容，请拆成独立的数字员工；
- **提示词各自独立**：每个智能体的提示词单独拼接（见 5.1），不互相合并；子智能体的占位符只能引用**自己包里**声明的资源（见 5.7）。

### 2.4 增量交付：基线与最小增量

智能体上线后，业务会持续演进：新增一个子智能体、只调整某一个智能体的提示词、补几个知识文件。这类变更**不需要重新交付完整的包**，可以只交付变化的部分。首次交付必须是完整包。

**所有智能体包的增量机制相同，各自独立版本。** 改哪个智能体，就在哪个智能体的包里交付增量：

| 你想改的 | 在哪个包里交付增量 |
|---|---|
| 某个智能体（main 或 sub）自己的提示词、Skill、知识、记忆、连接、运行环境 | **该智能体的包** |
| main 引用了哪些子智能体、引用哪个版本范围 | **main 的包**的 `registry/agents.json` |
| 新增一个子智能体 | ① 先交付并发布新智能体的完整包（`role: sub`）；② main 的包里增加对它的引用 |

#### 增量包是什么

增量包使用与完整包相同的目录结构，**只包含本次新增、修改的内容**，另在根目录提供 `change-set.yaml`。**`change-set.yaml` 是本次变更的唯一清单：新增、修改、删除了什么，都要在这里显式登记**，不能靠"文件出现在包里"来暗示：

```yaml
# change-set.yaml：给 main 智能体 pm 新增引用子智能体 hotspot（版本范围 ^1.0.0），并更新提示词
change_id: 20261110-add-hotspot        # 本次变更的唯一编号，由业务方生成
base_version: 1.2.0                    # 本次变更基于的、平台已发布的版本
new_version: 1.3.0                     # 变更后的版本号，按 7.1 规则确定
note: 新增引用热点分析子智能体，并让主智能体分派热点类需求

add_entries:                           # 新增的记录
  - "agents:hotspot"                   # 新增引用子智能体 hotspot
update_entries:                        # 修改的记录（整条替换）
  - "prompt:identity"                  # 提示词有改动
remove_entries: []                     # 删除的记录

add_files: []                          # 新增的文件（相对包根的路径）
update_files:                          # 修改的文件
  - acceptance/cases.yaml
remove_files: []                       # 删除的文件
```

三类各有对应的"新增 / 修改 / 删除"，没有就写 `[]` 或省略。

#### 记录与文件怎么登记

**记录**：指一类内容里的一条条声明。写法是 `<类型>:<名称>`：

| 类型 | 对应的文件与键 | 说明 |
|---|---|---|
| `skills` | `registry/skills.json`，按能力 `id` | 引用的 Skill，要指明版本范围 |
| `tools` | `registry/tools.json`，按能力 `id` | 引用的外部工具，要指明版本范围 |
| `agents` | `registry/agents.json`，按子智能体 `id`（仅 `main`） | **引用的子智能体，要指明版本范围，和 `skills` 是同一种写法** |
| `knowledge` | `knowledge.yaml`，按 `path` | 自有知识目录 |
| `shared_knowledge` | `registry/knowledge.json`，按 `as` | 引用注册表里的共享知识、模板（6.3），要指明版本范围 |
| `connections` | `connections.yaml`，按连接 `name` | 外部连接 |
| `memory` | `memory/stores.yaml`，按记忆库 `name` | 长期记忆库 |
| `prompt` | `identity/` 下的提示词文件，**一个包只有一条**，名称固定为 `identity` | 提示词是一个整体，见下方说明 |

- `add_entries`：基线里**没有**的记录，增量里要写出这一条的完整内容；
- `update_entries`：基线里**已有**的记录，增量里写**整条**新内容，整条替换基线里那一条（不是只改其中一个字段）；
- `remove_entries`：删除基线里的记录，增量里不需要再写。

**提示词（`prompt:identity`）要特别注意：三个文件必须成套给出。** 提示词由 `identity.md`、`orchestration.md`、`handoff.md` 按固定顺序拼接成一份系统提示词（见 5.1），拼接时某一部分缺失，那一段就会消失。所以只要登记了 `prompt:identity`（不论新增还是修改），**增量里就要把包里存在的全部提示词文件一并给出，没有改动的文件也要原样给出**，不能只给改了的那一个。平台是用你们给出的这一套重新拼接，不会拿基线里的旧文件补进去。

- 原来没有 `handoff.md`、本次新增了：登记 `update_entries: ["prompt:identity"]`，并给出 `identity.md`、`orchestration.md`、`handoff.md` 三个文件；
- 原来有 `handoff.md`、本次要去掉：登记 `update_entries: ["prompt:identity"]`，只给 `identity.md`、`orchestration.md`，**缺了的 `handoff.md` 视为被删除**；
- `identity.md` 是必须的，不能缺。

**文件**：指除提示词、清单类内容以外的文件——知识文件、Skill 目录下的文件、`acceptance/cases.yaml`、`registry/environment.json`、`registry/agent.json` 等。上表里各类记录（含提示词）的变化已经由 `*_entries` 表达，**不需要再在 `*_files` 里登记**：

- `add_files`：基线里没有的文件，写出完整内容；
- `update_files`：基线里已有的文件，写**改动后的完整文件**，整个替换；
- `remove_files`：删除基线里的文件。

`registry/agent.json` 只放身份信息（`id`、`version`、`role`、`visibility`、`owner`、`description`），改它就是普通的 `update_files`，**不含任何引用**；引用都在 `registry/skills.json`、`registry/tools.json`、`registry/agents.json` 里，由 `*_entries` 登记。

增量包里的实际内容必须与这份登记**完全一致**：登记了但包里没有、包里有但没登记、登记的是新增而基线里已存在（或登记的是修改而基线里不存在），一律退回。

#### 规则

1. **省略不是删除**。增量里没有出现的文件、记录，沿用 `base_version` 的内容；**提示词除外**——提示词按套给出，没给出的提示词文件视为被删除（见上）；
2. **新增、修改、删除都要显式登记**，登记与增量包里的实际内容必须一致（见上）。移除子智能体引用（`remove_entries` 里有 `agents:<子智能体ID>`）时，必须同时更新 main 的提示词，去掉对它的分派说明（平台只检查提示词里是否还出现该别名，仍出现则退回）；新增子智能体引用时，同样必须在提示词里加上分派说明；
3. **删除资源声明时，用到它的地方要一并处理**：`remove_entries` 删掉一个 Skill、连接、知识目录或记忆库，而包里的提示词（占位符）或其他声明仍在使用它，则退回；
4. **基线必须是最新的已发布版本**。`base_version` 与该包当前最新已发布版本不一致（别人先发布了新版本），退回，请基于最新版本重新交付；平台会告知差异；
5. **同一次变更只生效一次**。`change_id` 相同、内容也相同的重复提交视为同一次变更，不会重复生效；`change_id` 相同但内容不同，退回；
6. **`role` 和 `visibility` 的变更要显式**：它们在 `registry/agent.json` 里，登记 `update_files: [registry/agent.json]`；修改 `role` 或 `visibility` 视为不兼容变更（升主版本），并须重新通过 2.3 的引用检查（尤其 `sub` 必须是 `internal`）；
7. **子智能体自己的变更不在 main 的增量里**：子智能体的内容（提示词、Skill、知识、连接等）变化，走**它自己包的增量**，发布后得到新版本；main 只通过 `agents.json` 的版本范围去引用它，不重复交付它的内容（见下）；
8. **影响范围由平台核算**：
   - 改了 **sub 智能体**：发布该智能体的新版本，然后找出引用它的 main，逐个评估；
   - 改了 **main 智能体**自己：只更新这个智能体；
   - 环境、凭证、知识、记忆库属于会话级资源，变化会影响整位数字员工（含它引用的全部 sub），平台会在回执中写明；
9. **提交、构建、接受、发布是四个动作**。提交增量不等于发布；发布沿用第 7.3 节的灰度流程，进行中的任务保持原版本。

#### 子智能体发布新版本后，main 怎么办

**子智能体自己的变更，永远走它自己包的增量**，发布后得到一个新版本。main 引用子智能体和引用 Skill 一样，是"引用谁 + 接受哪个版本范围"（`registry/agents.json`），main 的包里不会出现子智能体的内容。

main 引用时**固定了版本**，子智能体发布新版本不会自动影响已发布的 main。是否纳入新版本，按版本规则（同 6.2）：

| 子智能体的变更 | 对引用它的 main |
|---|---|
| 修订（行为兼容的修复） | 在 `range` 范围内，平台评估后可重新构建并锁定新版本，在回执中请你们确认；main 的包**不需要交付任何文件** |
| 次要（向后兼容的新增） | 在 `range` 范围内的，同上；是否纳入由你们在回执中决定 |
| 主要（不兼容） | **不会自动纳入**。main 的负责人评审后，把 `registry/agents.json` 里这条引用的版本范围改掉（登记 `update_entries: ["agents:<子智能体ID>"]`），作为 main 自己的一次增量交付 |

main 的版本随之变化，规则见 7.1。

#### 常见变更需要交付什么

每一行都写明**增量包里放什么**，以及 **`change-set.yaml` 里怎么登记**。下面以子智能体 `hotspot`、主智能体 `pm` 为例（`pm` 的提示词有 `identity.md`、`orchestration.md`、`handoff.md` 三个文件）：

| 你想做的事 | 在哪个包 | 增量包里放 | `change-set.yaml` 登记 |
|---|---|---|---|
| 改 `hotspot` 的提示词 | `hotspot` 的包 | `identity/` 下**全部**提示词文件（`identity.md` 等，没改的也原样给出） | `update_entries: ["prompt:identity"]` |
| 给 `hotspot` **新增**引用一个 Skill | `hotspot` 的包 | `registry/skills.json` 里这条新记录（含版本范围） | `add_entries: ["skills:platform.chart"]` |
| 给 `hotspot` **新增**一个自有 Skill | `hotspot` 的包 | `skills/<名>/` 下的全部文件；`registry/skills.json` 里这条新记录 | `add_entries: ["skills:<名>"]`；`add_files: [skills/<名>/SKILL.md, …]` |
| 改 `hotspot` 自有 Skill 的脚本 | `hotspot` 的包 | `skills/<名>/scripts/xxx.py`（完整文件） | `update_files: [skills/<名>/scripts/xxx.py]` |
| 调整 Skill 的版本范围 | 引用它的那个包 | `registry/skills.json` 里这条记录（整条） | `update_entries: ["skills:platform.chart"]` |
| **删除**一个 Skill 引用 | 引用它的那个包 | 不需要放文件 | `remove_entries: ["skills:old-skill"]`（自有 Skill 的文件另在 `remove_files` 列出） |
| **新增**一个连接 | 用它的那个包 | `connections.yaml` 里这条新记录 | `add_entries: ["connections:crm-api"]` |
| 改一个连接（如换域名） | 用它的那个包 | `connections.yaml` 里这条记录（整条） | `update_entries: ["connections:crm-api"]` |
| 改运行环境依赖 | 对应的包 | `registry/environment.json`（完整文件） | `update_files: [registry/environment.json]` |
| **新增**一个知识目录 | 对应的包 | 目录里的知识文件；`knowledge.yaml` 里这条新记录 | `add_entries: ["knowledge:业务口径"]`；`add_files: [业务口径/统计口径.md, …]` |
| 改一个知识文件 | 对应的包 | 该文件（完整文件） | `update_files: [业务口径/统计口径.md]` |
| 改 `pm` 的提示词 | `pm` 的包 | `identity/` 下**全部**提示词文件（三个都给，没改的原样给） | `update_entries: ["prompt:identity"]` |
| **新增**引用一个子智能体 | `pm` 的包 | ① 先交付并发布该子智能体的完整包；② `registry/agents.json` 里这条新记录（含版本范围）；**全部**提示词文件（加分派说明）；`acceptance/cases.yaml` | `add_entries: ["agents:insight"]`；`update_entries: ["prompt:identity"]`；`update_files: [acceptance/cases.yaml]` |
| **移除**一个子智能体引用 | `pm` 的包 | **全部**提示词文件（去掉分派说明）；`acceptance/cases.yaml`（去掉相关用例）；子智能体的包本身保留 | `remove_entries: ["agents:hotspot"]`；`update_entries: ["prompt:identity"]`；`update_files: [acceptance/cases.yaml]` |
| 让 `pm` 改用某子智能体的另一个版本范围 | `pm` 的包 | `registry/agents.json` 里这条记录（整条） | `update_entries: ["agents:hotspot"]` |
| 改 `role` 或 `visibility` | 对应的包 | `registry/agent.json`（完整文件） | `update_files: [registry/agent.json]`；升主版本 |

> 各类**记录**（含提示词）只用 `*_entries` 登记，不用重复写 `*_files`；`registry/agent.json` 只放身份信息，改它就是普通的 `update_files`。

**完整例子一：给子智能体 `hotspot` 新增引用 Skill `platform.chart`，同时调整另一个 Skill 的版本范围、并删除一个不再用的连接**

这是 `hotspot` **自己包**的增量，只有两个文件（删除 `old-crm` 连接不需要放内容，只在 `change-set.yaml` 里登记）：

```text
change-set.yaml
registry/skills.json        # 含 platform.chart（新增）和 platform.report-cover（修改）两条记录
```

```yaml
# change-set.yaml（hotspot 的包）
change_id: 20261112-hotspot-chart
base_version: 1.0.0
new_version: 1.1.0                     # 新增能力，次版本
note: 引用 platform.chart；report-cover 升级到 ^1.3.0；去掉不再使用的 old-crm 连接

add_entries:
  - "skills:platform.chart"            # 新增
update_entries:
  - "skills:platform.report-cover"     # 修改：版本范围 ^1.2.0 → ^1.3.0
remove_entries:
  - "connections:old-crm"              # 删除

add_files: []
update_files: []
remove_files: []
```

```json
// registry/skills.json —— 只写本次变化的两条记录，每条写完整
[
  { "id": "platform.chart",        "range": "^1.0.0" },
  { "id": "platform.report-cover", "range": "^1.3.0" }
]
```

这一次变更只动了记录（`registry/skills.json`、`connections.yaml` 里的条目），它们由 `*_entries` 覆盖，所以 `add_files`、`update_files`、`remove_files` 都是空的。具体来说：新增了 `platform.chart`（基线里不能已有）；修改了 `platform.report-cover`（基线里必须已有）；删除了 `old-crm`（基线里必须已有，且 `hotspot` 的提示词里不能还在使用它）。

发布后得到 `hotspot` 1.1.0。引用它的 `pm` 的 `range` 是 `^1.0.0`，在范围内，所以平台评估后重新构建并在回执里请你们确认，`pm` 的包不用交付文件。

**完整例子二：给主智能体 `pm` 新增引用一个子智能体 `insight`**

这个变更要分**两步**，涉及两个包：

**第 1 步：先交付并发布 `insight` 自己的完整包**（`insight` 是首次交付，不是增量，没有 `change-set.yaml`）。它的 `registry/agent.json`：

```json
{
  "id": "zhilan.hotspot-team.insight",
  "version": "1.0.0",
  "role": "sub",
  "visibility": "internal",
  "owner": { "team": "智蓝数据服务部", "primary": "张三", "backup": "李四" },
  "description": "洞察生成。适用：…；不适用：…"
}
```

`insight` 发布后，得到 `1.0.0`（`role: sub`，`visibility: internal`，没有 `registry/agents.json`，因为 `sub` 不能再引用别人）。

**第 2 步：在 `pm` 的包里增量交付**，让 `pm` 引用它。增量包有六个文件：

```text
change-set.yaml
registry/agents.json           # 只写新增的这一条引用记录
identity/identity.md           # 提示词三件套：没有改动，但必须原样给出
identity/orchestration.md      # 提示词：加了对 insight 的分派说明
identity/handoff.md            # 提示词三件套：没有改动，但必须原样给出
acceptance/cases.yaml          # 完整文件，加了分派到 insight 的用例
```

```yaml
# change-set.yaml（pm 的包）
change_id: 20261115-add-insight
base_version: 1.3.0
new_version: 1.4.0                     # 新增子智能体引用，次版本
note: 新增引用洞察生成子智能体 insight，并让 pm 分派洞察类需求

add_entries:
  - "agents:insight"                   # 新增：基线里 pm 还没有引用 insight
update_entries:
  - "prompt:identity"                  # 提示词整套更新（orchestration.md 有改动，另外两个原样带上）
remove_entries: []

add_files: []
update_files:
  - acceptance/cases.yaml              # 加分派用例
remove_files: []
```

`registry/agents.json` 里新增的这条记录，**指明引用谁、接受哪个版本范围**，和引用 Skill 的写法一致：

```json
[ { "id": "insight", "range": "^1.0.0", "alias": "insight" } ]
```

`identity/orchestration.md` 里要加上分派说明，平台会检查是否提到了别名 `insight`：

```text
## 分派规则
- 用户要生成洞察报告时，交给 insight；
```

**提示词三个文件都要给**：`identity.md` 和 `handoff.md` 这次没有改动，也必须原样放进增量包。平台是用你们给出的这一套重新拼接成系统提示词的，缺了哪一个，那一段就会从系统提示词里消失。

平台会检查：`insight` 存在、已发布、`role` 是 `sub`、范围内有已发布的版本；`pm` 的提示词里提到了 `insight`；`insight` 自己没有再引用别人。通过后 `pm` 发布 1.4.0，生产环境用户仍然只通过 `pm` 对话。

**完整例子三：给主智能体 `pm` 移除对子智能体 `hotspot` 的引用**

增量包在 `pm` 的包里，有五个文件：

```text
change-set.yaml
identity/identity.md           # 提示词三件套：没有改动，原样给出
identity/orchestration.md      # 提示词：去掉了对 hotspot 的分派说明
identity/handoff.md            # 提示词三件套：没有改动，原样给出
acceptance/cases.yaml          # 完整文件，去掉了分派到 hotspot 的用例
```

```yaml
# change-set.yaml（pm 的包）
change_id: 20261120-remove-hotspot
base_version: 1.4.0
new_version: 2.0.0                     # 移除子智能体引用，不兼容变更，主版本
note: 热点分析业务下线，移除对 hotspot 的引用

add_entries: []
update_entries:
  - "prompt:identity"                  # 提示词整套更新
remove_entries:
  - "agents:hotspot"                   # 删除：基线里 pm 已引用 hotspot；registry/agents.json 里不需要再写

add_files: []
update_files:
  - acceptance/cases.yaml              # 去掉分派到 hotspot 的用例
remove_files: []
```

平台会检查：提示词里**不能再出现** `hotspot` 这个别名，出现则退回（否则主智能体会继续把任务派给一个已经不引用的子智能体）。

另外，`acceptance/cases.yaml` 里 `agents` 写了 `hotspot` 的用例，**平台不会自动检查**，需要你们自己同步去掉，否则这些分派用例在验收时会失败。

注意几点：

- **移除的只是 `pm` 对 `hotspot` 的引用**。`hotspot` 自己的包和它在 MA 上的 Agent 都保留，不会被删除。想让 `hotspot` 彻底下线，要单独走"能力下线"流程（见 6.2），并且要求没有任何 `main` 还在引用它；
- 版本升**主版本**：因为 `pm` 对外能做的事变少了；
- `hotspot` 声明的知识、记忆库、连接、运行环境依赖，会随引用一起从这位数字员工的会话里移出，平台会在回执里列出。

### 2.5 平台的构建回执

每次构建（首次交付或增量）后，平台把结果回给你们确认。回执至少包含下面这些，**区分"你们写的"和"平台定的"**：

| 内容 | 说明 |
|---|---|
| 提交标识与版本 | 交付内容的摘要；增量的 `change_id`、`base_version`、`new_version`；提交的压缩包（链接、SHA-256 核对结果、解压与目录检查结果，见 2.6） |
| 智能体清单 | 数字员工的 `main` 与每个 `sub`（含它锁定的版本、`role`、`visibility`），以及各自的 Skill、工具；会话级的知识、记忆库、连接、运行环境按合并后的最终结果列出，并标明各自来自哪个包 |
| 完整系统提示词 | 每个智能体：你们写的原文、每个占位符替换后的结果、拼接后的完整提示词（见 5.7） |
| 依赖的实际版本 | `environment.json` 里的版本下限最终解析成的实际版本 |
| 可复用能力的锁定版本 | 每个智能体引用的每个能力（含子智能体）最终锁定到哪个版本 |
| 模型与环境 | 平台选定的模型、运行环境、任务时长与网络范围 |
| 知识与记忆库 | 各知识目录和记忆库的落地情况、读写权限 |
| 合并检查 | 会话级资源合并后的冲突检查结果（同名、凭证、依赖版本、容量） |
| 验收结果 | 每个用例的结论（见 9.2） |
| 状态 | 构建失败则给出失败原因和位置；成功则说明处于测试、灰度还是已发布 |

> 动态外部依赖（外部服务、可写记忆库、外部数据）无法完整冻结快照，回执会写明访问时点和限制，不保证事后可以完全重放同一次运行。

### 2.6 智能体包怎么交付：压缩包 + 公网链接

每个智能体包打成**一个压缩包**，把**公网可访问的下载链接**和它的 **SHA-256** 提交给平台。首次交付的完整包、增量交付的增量包（2.4）都一样。

#### 压缩包命名

```text
<业务线ID>-<数字员工ID>-<智能体ID>-<版本>.zip
例：zhilan-hotspot-team-pm-1.2.0.zip
```

- `<版本>` 是这次交付的版本：完整包取 `registry/agent.json` 的 `version`，增量包取 `change-set.yaml` 的 `new_version`；
- **一个版本只对应一个压缩包**。版本发布后内容不可变（6.2），要改就升版本、出新压缩包；
- ID 本身可以含连字符，平台**不靠文件名拆分**。完整包读取包内的 `registry/agent.json` 核对；增量包没有 `agent.json`（只交变化的文件），改为读取 `change-set.yaml` 并与基线核对（见下方"平台怎么处理"）。

#### 压缩包里是什么

解压后顶层是 `<业务线ID>/<数字员工ID>/<智能体ID>/` 三级目录，里面就是第 2 章描述的智能体包：

```text
zhilan-hotspot-team-pm-1.2.0.zip
└── zhilan/                          # 业务线 ID
    └── hotspot-team/                # 数字员工 ID
        └── pm/                      # 智能体 ID
            ├── identity/
            ├── registry/
            ├── knowledge/ …         # 其余内容见第 2 章
            └── change-set.yaml      # 仅增量包有（2.4）
```

- 压缩包里**只有这一个顶层目录**，三级目录名必须与 `registry/agent.json` 的 `id` 一致；
- **一个压缩包只放一个智能体**。同一位数字员工的多个智能体（`main` 和各 `sub`），各自一个压缩包、各自一个版本；
- 增量包的目录结构相同，只是里面只有本次变化的文件和 `change-set.yaml`；**增量包不需要包含 `registry/agent.json`**（没有改动身份信息时）；
- 不得包含：密钥与凭证、缓存与临时文件（如 `__pycache__`、`.DS_Store`、虚拟环境）、符号链接；
- 使用 ZIP 格式，文件名使用 UTF-8。

#### 提交什么

| 项 | 说明 |
|---|---|
| 压缩包的公网链接 | **不需要登录**就能下载，**永久有效**：不设有效期，也不要删除源文件 |
| SHA-256 | 压缩包的 SHA-256（十六进制）。生成方法：macOS 用 `shasum -a 256 <文件>`，Linux 用 `sha256sum <文件>` |

#### 平台怎么处理

检查分成两个阶段，**增量包和完整包的区别只在第二阶段**：

**第一阶段：形式检查**（对压缩包本身，完整包和增量包相同）

1. 按链接下载压缩包；
2. 核对 SHA-256，不一致则退回（说明下载内容与你们提交的不是同一份）；
3. 安全解压：不允许路径穿越（`..`）、绝对路径、符号链接，出现则退回；
4. 检查**压缩包文件名**与**顶层三级目录**是否一致，且文件名里的 `<业务线ID>-<数字员工ID>-<智能体ID>` 与三级目录拼起来相同；
5. 检查不含密钥、缓存与临时文件。

**第二阶段：内容检查**（对"完整的包"）

- **完整包**：直接对它做第 9 章的交付检查，其中 `registry/agent.json` 的 `id` 必须与三级目录一致，`version` 必须与文件名中的版本一致；
- **增量包**：先按 2.4 的规则与基线合并成**完整包**，**对合并后的完整包**做第 9 章的交付检查。增量包自己要核对的只有：`change-set.yaml` 存在，`base_version` 是该智能体最新已发布版本，`new_version` 与文件名中的版本一致，登记与包内内容一致（2.4）。

**版本号怎么回填**：增量包里的版本只写在 `change-set.yaml` 的 `new_version`。平台合并时**自动把合并后完整包的 `registry/agent.json` 里 `version` 更新为 `new_version`**，业务方不需要、也不应该手动改 `agent.json` 的 `version`。只有要改 `role`、`visibility`、`owner`、`description` 等其他字段时，才在增量包里带上 `registry/agent.json`（登记 `update_files`），此时包内的 `version` 字段如果写了，必须等于 `new_version`，不一致则退回。

任何一步失败都会退回并说明原因。通过后进入第 9 章的后续验收；平台会留存取回的压缩包（以及合并后的完整包），用于下一次增量交付时还原基线（2.4）。

同一个版本重复提交：该版本**已发布**的，内容必须与已发布的一致（SHA-256 相同），不一致则退回，请升版本；**尚未发布**的，以最新一次提交为准。

#### 暂时没有包管理平台时：用 Media Storage 生成公网链接

目前没有专门的包管理平台。可以先用中台的 **Media Storage** 能力把本地压缩包转成公网链接，对应的技能是 `blueai-media-storage-skill`（在技能市场里）：

1. 安装该技能，向平台申请 API Key（Key 只用于上传，**不要写进智能体包**）；
2. 用它的"本地文件上传"能力上传压缩包，返回结果里的 `file_url` 就是公网链接；
3. **上传后必须验证**：用不带任何登录信息的方式下载一次（例如浏览器无痕窗口，或 `curl -L -o test.zip "<链接>"`），确认能下载，并且下载文件的 SHA-256 与本地一致，再提交；
4. 链接的保留期以 Media Storage 团队的说明为准。**如果发现链接会过期，请联系平台，不要提交会过期的链接**。

> **注意：公网链接意味着知道链接的人都能下载。** 智能体包里有你们的提示词和业务知识，请不要把链接发到公开渠道；包里本来就不允许有密钥和凭证（第 8 章）。

以后有专门的包管理平台，会改成在平台上直接提交，命名规则不变，届时本节更新。

#### 其他需要公网链接的材料

除智能体包以外，如果还有材料**暂时没有平台管理、但需要先把本地文件转成公网链接**才能交给平台（例如较大的知识文件、验收样例附件），也可以暂时用同样的方式（Media Storage）转成公网链接，验证方法与注意事项同上。

## 3. 信息放在哪里（唯一归属）

| 信息类型 | 唯一存放位置 |
|---|---|
| 业务方法、口径、标准、模板、案例、术语 | 业务知识目录（默认 `knowledge/`，可自定义，由 `knowledge.yaml` 声明） |
| 智能体的角色、行为边界、提示词 | 该智能体包的 `identity/` |
| 智能体的角色、可见范围、引用的子智能体 | 该智能体包的 `registry/agent.json`（见 2.3） |
| 外部能力的接口与所需凭证类型 | `tools/` |
| 可执行的封装能力 | `skills/`（可复用的须登记，见第 6 章） |
| 输入输出的结构定义 | `io/contracts/` |
| 需要连接的外部系统与凭证声明 | `connections.yaml` |
| 跨任务共享的长期记忆 | `memory/` |
| 运行环境需求（依赖、网络、环境变量） | `registry/environment.json` |
| 密码、API Key、Token、Cookie、私钥 | **外部密钥存储**，不进入资源包 |

边界规则：

- 业务知识放在业务知识目录里；某次任务的原始材料、聊天记录、失败文件**不要**放进资源包。
- 提示词需要引用业务口径时，使用逻辑引用（见 5.2）指向业务知识目录中的文件，不要在提示词里复制一份。
- 业务内容模板放在业务知识目录里；可执行的提示词和脚本放在对应能力的目录下。
- 案例（标准、边界、错误、回归）也放在业务知识目录里。
- `registry/` 只放登记与版本信息，不放任务、会话、运行产生的编号。

## 4. 工作空间（运行时数据，不属于资源包）

以下是平台运行时的信息归属，**业务方不需要交付**，但需要理解信息如何流转，以便决定哪些内容该放进资源包、哪些不该。

**两个相互独立的目标：** 工作材料与知识组织是两件事。

| 目标 | 由谁承载 | 内容 |
|---|---|---|
| 文件与共享协作位置 | **Workspace**（工作空间） | 工作材料、任务过程、成果，以及团队、项目的共享与共同编辑 |
| 知识、记忆、索引与读取规范 | **知识与记忆库**（对应本规范 5.2、5.5） | 业务知识、长期记忆 |

两者可以使用共同的底层存储，但职责保持独立：Workspace 里的材料**不会自动变成业务知识**，业务知识要进入资源包（5.2）。

**三类默认空间：**

| 默认空间 | 主要用途 | 访问边界 |
|---|---|---|
| Agent Workspace | 数字员工个人的工作材料、任务过程和成果；**Task 工作空间归入它的根范围** | 由该数字员工与获授权的管理者使用，不向协作者默认开放全部内容 |
| Team Workspace | 团队材料共享与共同编辑 | 按团队任职及授权提供；放入共享空间意味着遵守该空间的共享范围 |
| Project Workspace | 项目材料共享与共同编辑 | 有项目任职或相应授权时提供；项目之间相互隔离 |

下面是**逻辑结构**，用目录、数据库记录或对象元数据承载均可；对象存储里的物理路径由平台生成，不要求与此一致：

```text
Agent Workspace/{数字员工}/                  # 员工个人工作材料、任务过程和成果
├── personal/{user_id}/                     #   私聊：某个用户与该员工的个人上下文
│   ├── context/                            #     个人偏好、局部上下文（不公开到项目）
│   └── connections/                        #     个人连接（只存凭证引用，不存值）
├── groups/{chat_id}/                       #   群聊：该群的局部上下文与交流习惯
│   └── context/
└── tasks/{task_id}/                        #   Task 工作空间（归入 Agent Workspace，不放进项目目录）
    ├── task.json                           #     任务目标与交付要求；发起人、来源通道、
    │                                       #     所属项目（如有）、本任务采用的材料与资源包版本
    ├── context/                            #     本任务采用的上下文（采用的版本，不取代原始来源）
    ├── inputs/                             #     本任务的输入材料
    └── runs/{run_id}/                      #     一次运行
        ├── run.json                        #       本次运行冻结的资源包版本、模型、参数
        ├── attempts/                       #       每次执行或重试，真实回执与日志
        ├── artifacts/                      #       正式产物与产物清单
        ├── validation/                     #       针对某个明确产物的检查结果
        └── delivery/                       #       从产物导出、交付给使用方的版本

Team Workspace/{team_id}/                   # 团队材料共享与共同编辑
├── sources/                                #   团队共享材料
└── connections/                            #   团队连接（只存凭证引用）

Project Workspace/{project_id}/             # 项目材料共享与共同编辑，项目间隔离
├── project.json                            #   项目信息
├── context/                                #   项目事实与口径（项目内共享）
├── sources/                                #   项目原始资料
├── connections/                            #   项目连接（只存凭证引用）
└── registry/                               #   本项目采用的资源包版本等登记
```

私聊和群聊是**通道**：私聊里的偏好与局部上下文留在 `personal/`，群聊的留在 `groups/`，不会因此公开到项目。项目事实和口径默认在项目内共享，放在 Project Workspace。任务不论在私聊还是群聊发起，都归入 Agent Workspace，通过 `task.json` 关联发起人、通道和项目。

| 概念 | 含义 | 与资源包的关系 |
|---|---|---|
| 任务 | 一项有目标和交付要求的工作，其工作空间归入 Agent Workspace | 引用资源包的版本 |
| 运行 | 一次实际执行；记录采用的全部版本与参数 | 冻结引用的资源包版本 |
| 执行记录 | 运行下的每次执行或重试，过程文件在此 | 不是交付源 |
| 产物 | 正式、可引用、可送检、可交付的结果 | 由任务产生，不回写资源包 |
| 质检 | 对明确产物的检查记录 | 引用资源包中的验收口径 |
| 交付 | 从产物导出、打包给使用方的版本 | 不是后续编辑的源文件 |

流转原则：

1. 任务采用的材料来自用户输入，或 Agent、Team、Project 各空间；任务里记录的是"本任务采用的版本"，不取代原始来源；
2. 运行开始时冻结所采用的全部版本，任务后续变化不影响已有运行；
3. 过程文件不是交付源；需要保留、复用、送检、交付的结果才固化为产物；
4. 质检、交付都必须指向明确的产物，不以文件名或"最新"推断；
5. 交付件不是源文件，修改应回到产物重新生成；
6. **放入共享空间意味着遵守该空间的共享范围**：Team Workspace 的内容对团队授权成员可见，Project Workspace 的内容只对项目成员可见，Agent Workspace 的内容不默认对协作者开放；
7. 反馈按影响范围沉淀：只影响本次的保留在任务；对团队或项目后续有价值的放入对应的 Team、Project Workspace；可跨项目复用的方法、标准、案例，作为业务知识更新提交给平台评审，进入资源包的业务知识目录。

### 4.1 运行追溯的最低关联信息

上面的目录是逻辑结构，不要求每一层都建文件。运行下的各类记录至少要能追溯到唯一对象：

| 记录 | 最低要关联的信息 |
|---|---|
| 运行 | 数字员工、任务、运行编号（有项目的加项目）；采用的资源包版本（含各智能体版本）；实际使用的模型与环境 |
| 执行记录 | 属于哪个运行；第几次执行或重试；真实回执 |
| 产物 | 产物编号、版本、内容摘要、来源（由哪个运行、哪个智能体产生） |
| 质检 | 被检的产物、依据的规则版本、执行者、结论、证据位置 |
| 交付 | 来源产物、交付回执 |

运行记录**不回写**资源包。运行中产生的、值得沉淀的内容（新的口径、案例、提示词改进），经评审后作为资源包的新版本提交，原始日志仍留在运行空间，资源包的变更记录只引用证据位置（对应第 7.2 节）。

### 4.2 持久化、接续与多人协作

**哪些内容会被保留**，业务方需要分开看待，不要推定"整个工作目录都会保留"：

| 内容 | 保留方式 |
|---|---|
| 资源包（提示词、知识、能力声明等） | 由平台按版本保存，见第 7 章 |
| 任务产物 | 只有放入产物输出位置、且平台已为你们配置了产物存储的，才长期保留；否则按平台的默认保留期清理。需要长期保存的产物，请向平台说明 |
| 会话内的临时文件、中间结果 | **不承诺保留**，会话结束或沙箱重建后可能丢失 |
| 执行日志、验证证据 | 保留位置与期限由平台在回执中说明 |

**长任务的接续**：

- 阶段结束或中断前，把目标、采用的资源包版本、已有产物、已完成与未完成的检查、未决问题和下一步写入产物或任务记录；恢复时先核对这份记录与实际文件，再继续；
- 同一会话内继续、新会话接手是不同的情形，验收时分别验证。**不要假定新会话能看到上一个会话的临时文件**，需要接续的内容必须落在产物里；
- 已经发生、但结果未知的外部动作（发送消息、写外部系统等），先查回执确认结果，不要直接重放；

**多人协作**：

- 同一数字员工的资源包由多人修改时，各自基于明确的版本（`base_version`，见 2.4）修改，平台接收时检查冲突，不会覆盖他人已发布的内容；
- 材料在 Agent、Team、Project 三类空间之间的共享与隔离，由平台按团队任职、项目任职与授权配置，**不能由目录名或群聊名称推定**；需要共享或隔离的范围请向平台说明。

## 5. 各类内容的格式要求

### 5.1 智能体身份（`identity/`）

| 文件 | 内容 | 要求 |
|---|---|---|
| `identity.md` | 角色、职责范围、适用场景、能力边界、可交付成果与格式 | 必须提供；写清"能做什么、不能承诺什么" |
| `orchestration.md` | 工作流程、各步骤用到的能力、质量标准 | 描述流程，不写一次性任务的具体数据 |
| `handoff.md` | 与其他角色交接的条件与内容 | 写明触发条件、交接信息、接收方 |

**这三个文件共同组成该智能体的系统提示词。平台严格按下面的固定顺序和格式拼接，不改写、不增删、不调整你们写的文字（仅替换占位符，见 5.7）：**

```text
# 身份
<identity.md 全文>

# 编排
<orchestration.md 全文>

# 交接
<handoff.md 全文>
```

- 顺序固定：**身份 → 编排 → 交接**；
- `# 身份`、`# 编排`、`# 交接` 三个标题由平台插入，文件内容原样放在对应标题下；
- 某个文件不存在时，对应的标题和内容整段省略，其余顺序不变；
- 文件内部的标题**从二级（`##`）开始**，不要使用一级标题，以免与平台插入的标题冲突；
- 拼接得到的完整系统提示词会作为构建产物提供给你们确认。

因为是严格拼接，三个文件必须彼此一致：

- 同一条规则只写在一个文件里，不重复、不矛盾；
- `handoff.md` 中提到的角色，必须在 `identity.md` 或 `orchestration.md` 中有定义。

**每个智能体**（不论 `main` 还是 `sub`）在自己的包里按上面的方式拼接，各自生成独立的系统提示词，**不互相合并**。

**增量交付时提示词也要成套给出**：拼接是用你们给出的三个文件重新生成，所以只要改了其中任何一个，没改的那几个也要原样一并给出，否则那一段会从系统提示词里消失（见 2.4）。

其他要求：

- 不得包含密钥、令牌、个人账号；
- 业务口径、术语写在业务知识目录里，用逻辑引用（见 5.2），不要复制。

### 5.2 业务知识

业务知识指口径、标准、模板、案例、术语等供智能体查阅的稳定内容。

#### 目录与结构：可自定义

`knowledge/` 及其下的 `standards/`、`templates/`、`examples/`、`glossary.md` **只是建议的组织方式**，你们可以按业务习惯自行命名和组织，例如 `业务口径/`、`话术库/`、`docs/`。

唯一的要求是：**用 `knowledge.yaml` 声明哪些目录属于业务知识**，平台只会处理被声明的目录。

```yaml
# knowledge.yaml
roots:
  - path: knowledge              # 相对资源包根的目录；可声明多个
    description: 默认知识目录
  - path: 业务口径
    description: 各业务线统一口径
```

规则：

- `path` 是相对资源包根的目录，不能越出资源包，不能互相嵌套；
- 没有 `knowledge.yaml` 时，默认只处理 `knowledge/`；
- 没有声明的目录，平台**不会**作为业务知识处理，里面的内容智能体读不到；
- 目录内的文件使用 Markdown（`.md`）或纯文本（`.txt`）；
- 每个文件开头写明：名称、适用范围、版本、负责人；
- 案例中某次任务的原始错误材料不要放入知识目录。

#### 容量

按知识本身的粒度组织：一个知识目录是一组主题相关、内聚的知识（例如"统计口径"、"话术库"、"典型案例"），一个文件讲清一件事。**不需要为迁就平台而改变知识的组织方式。**

当前平台底座对文件大小、目录文件数、知识目录与长期记忆库的数量有一些上限，**这些限制目前都有效，构建时会校验**。具体数值、触及时的临时处理、平台的解决进度，见《MA Agent 搭建容量限制说明》（随本规范提供的附件，见附录）。超限时构建会直接失败并退回，错误里会指出超限项；平台不会自行切分文件或拆分目录。这些上限由平台逐项解决，解决后无需业务方改动。

建议的组织方式（可不采用）：

| 建议目录 / 文件 | 内容 |
|---|---|
| `standards/` | 生产口径与验收口径，每个标准一个文件，写明适用范围与版本 |
| `templates/` | 业务内容模板（报告结构、话术、表格） |
| `examples/` | 案例，按"标准 / 边界 / 错误 / 回归"分类 |
| `glossary.md` | 术语表，一个术语一条，写明定义与同义词 |

#### 引用写法

提示词（各智能体的 `identity/`）和知识文件里需要引用知识时，**使用占位符，不要写路径**（占位符清单见 5.7）：

```text
{{knowledge:标准/口径.md}}
```

- 冒号后面是**相对于某个已声明知识目录的路径**。只声明了一个知识目录时，直接写该目录下的相对路径；声明了多个时，写成 `目录名/相对路径`，例如 `{{knowledge:业务口径/统计口径.md}}`（长期记忆的 `{{memory:…}}` 写法与此一致，见 5.7）；
- 路径中的目录名、文件名以你们自己的为准，平台不要求使用 `standards/` 等固定名称；
- 平台把逻辑引用替换为智能体能够直接理解的指引，你们不需要也不应该知道知识存放在哪里；
- 被引用的文件必须存在于已声明的知识目录中（包括自有的 `knowledge.yaml` 目录，以及 `registry/knowledge.json` 里用 `as` 命名的共享知识，见 6.3），否则构建失败并退回；
- 同一个相对路径在多个知识目录里重复出现时，必须写成带目录名的形式，否则退回；
- 不要在提示词和知识文件里写运行环境的路径（例如以 `/mnt/`、`/workspace/` 开头），写了会被退回；
- 可复用能力自己的文件（`SKILL.md`、`scripts/` 等）按第 6.5 节的要求编写，不受本条限制。

> 知识具体存放在平台的哪里，业务方不需要关心，平台负责保持引用与实际位置一致。

### 5.3 运行环境需求（`registry/environment.json`）

只描述**需要什么**，具体如何搭建由平台决定。

```json
{
  "dependencies": {
    "python": ["pandas>=2.0", "openpyxl>=3.1"],
    "node": [],
    "system": []
  },
  "tools": [
    { "name": "<命令行工具>", "purpose": "<用途>", "source": "<来源或下载地址>" }
  ],
  "network": { "mode": "unrestricted", "allowed_hosts": [] },
  "env_vars": [
    { "name": "TZ", "value": "Asia/Shanghai", "purpose": "时区" }
  ],
  "runtime": { "max_task_minutes": 10, "notes": "" }
}
```

规则：

- 依赖**必须写明版本下限**，如 `pandas>=2.0`，不写版本的不予接收；
- `env_vars` **只放非敏感配置**（时区、开关、非密钥地址）；任何密钥一律放 `connections.yaml`；
- 需要限制外网访问的，在 `allowed_hosts` 列出域名；
- 每位数字员工有独立的运行环境，**不会与其他数字员工或业务线的依赖冲突**；但同一份依赖清单内部的版本要求必须自洽（例如不能同时要求 `numpy<2` 与 `numpy>=2`），不自洽时构建失败并退回；
- 一位数字员工的 `main` 和它引用的全部 `sub` **共用一个运行环境**：每个包各自声明依赖，构建时合并成一份，合并后必须自洽（见 2.3）；
- 上例中的 `max_task_minutes: 10` 和 `network.mode: unrestricted` 只是格式示例，不是平台默认值，也不代表对外网访问的授权；实际的任务时长上限、网络范围以平台回执为准。

### 5.4 外部连接与凭证声明（`connections.yaml`）

每个需要访问的外部系统一条。**只声明，不含凭证值。**

```yaml
connections:
  - name: <连接名>               # 业务内唯一，如 crm-api
    system: <目标系统名称>
    purpose: <用途，一句话>
    access: read | write         # 读写性质
    kind: api_key | mcp | oauth_token   # api_key：用密钥访问接口、命令行或 SDK；oauth_token：会过期、需要刷新的令牌
    hosts: [api.example.com]     # 会被访问的域名，必须逐个列出
    secret_name: CRM_API_KEY     # 在运行环境中以此变量名使用
    owner: <凭证提供人>
    rotation: <轮换周期，如 90d>
    notes: ""
```

规则：

- `hosts` 必须逐个列出被访问的域名，凭证只会被用于这些域名；
- 只写 `secret_name`（变量名），不写任何值；真实值由提供人交给平台存入密钥存储；
- `kind` 只有三种：`api_key`（用固定密钥访问接口、命令行工具或 SDK，不必区分是哪一种）、`oauth_token`（令牌会过期、需要刷新）、`mcp`（访问 MCP 服务，还需填写服务地址）；
- 需要 OAuth 并带自动刷新的，额外写明令牌端点、是否需要客户端密钥，**这些值同样不入包**；
- 一条连接对应一类用途，不要把多个系统共用一个条目；
- `kind: mcp` 时，在同一条目里补充 MCP 服务信息（见下）；"服务在哪里"和"用什么方式鉴权"是两件事，分别写；
- `kind: oauth_token` 时，补充令牌刷新信息（见下）；
- 凭证属于整次会话，数字员工内各智能体共享，不构成按智能体的访问隔离；`sub` 包里声明的凭证，在构建数字员工时与 `main` 的合并（见 2.3）。

**MCP 连接示例**（服务地址和鉴权方式是公开信息，可以写进资源包；密钥值不写）：

```yaml
  - name: datahub-mcp
    system: DataHub
    purpose: 查询热点数据
    access: read
    kind: mcp
    hosts: [mcp.datahub.example.com]
    mcp:
      url: https://mcp.datahub.example.com/mcp     # 服务地址，必须可从公网访问
      auth: api_key                                # 鉴权方式：api_key（固定密钥）| oauth（令牌，需要刷新）| none
      key_injection: header                        # auth 为 api_key 时：密钥怎么传给服务，bearer | header | query
      key_injection_name: X-API-Key                # key_injection 为 header 或 query 时必填：请求头名或参数名
    secret_name: DATAHUB_MCP_KEY                   # 变量名，不写值
    owner: 张三
    rotation: 90d
```

- 平台的 MCP 声明只有服务地址，没有单独的"协议"字段，所以这里不需要写协议；
- `key_injection` 为 `bearer` 时按 `Authorization: Bearer <密钥>` 传递，不要写 `injection_name`，密钥本身也不要带 `Bearer` 前缀；
- 同一个智能体里，同一个 MCP 服务地址不能重复声明。

**OAuth 令牌示例**（需要自动刷新时）：

```yaml
  - name: feishu-oauth
    system: 飞书开放平台
    purpose: 读取用户文档
    access: read
    kind: oauth_token
    hosts: [open.feishu.cn]
    secret_name: FEISHU_ACCESS_TOKEN
    oauth:
      token_endpoint: https://open.feishu.cn/open-apis/authen/v2/oauth/token   # 令牌刷新地址，公开信息
      client_auth: client_secret_post              # 刷新时的客户端认证方式：none | client_secret_basic | client_secret_post
    owner: 李四
    rotation: 30d
```

- `client_auth` 为 `none` 表示公共客户端，不需要客户端密钥；另外两种都需要客户端密钥，由提供人单独交给平台；
- 令牌刷新要求令牌端点返回 JSON，其中 `access_token` 为字符串、`expires_in` 为整数秒；不满足时刷新会失败，请提前确认；
- **只有敏感值不进资源包**：令牌本身、刷新令牌、客户端密钥、`client_id` 一律由提供人单独交给平台；服务地址、鉴权方式、令牌端点是公开信息，可以写；
- 创建 MCP 类凭证时，平台会立即与服务握手，服务不可达则创建失败。

### 5.5 长期记忆（`memory/`，需要时设置）

这里的"长期记忆"指智能体在工作中积累、可能被修改的内容。**稳定的业务知识（口径、标准、模板、案例、术语）请放在业务知识目录里（见 5.2），不要放在长期记忆里**——两者由平台分别管理，权限也不同：业务知识始终只读。知识目录与长期记忆库的数量受平台当前上限约束，见《MA Agent 搭建容量限制说明》。

是否设置长期记忆、每个记忆库是否允许智能体修改，**由业务方决策**。

```yaml
# memory/stores.yaml
stores:
  - name: <记忆库用途，如 playbook>
    access: read_only            # read_only | read_write；不写则按 read_only
    purpose: <存什么>
    maintainer: <谁维护>
    # 选 read_write 时必填：
    allowed_content: <允许智能体写入哪类内容>
    inspector: <谁负责事后巡检>
    inspect_cadence: <多久巡检一次>
    backup_source: <内容的备份或可重建来源，丢失后怎么恢复>
```

规则：

- **每个记忆库单独决策**，没有说明的一律按只读；
- 记忆条目：一条一个文件，路径即记忆路径；单条大小和单个记忆库的条目数受平台当前上限约束，见《MA Agent 搭建容量限制说明》，超限时按记忆的自然分类拆成多个记忆库；
- 提示词里写"不要修改记忆"只是文字约束，**不具备强制力**，权限以 `access` 为准；
- 团队规范、术语口径等共享知识建议设为只读；
- 记忆库是数字员工级资源，同一次会话中 `main` 和 `sub` 看到同一批记忆库，读写权限对所有智能体一致（见 2.3）。

> **⚠ 选择「可修改」之前，请了解这些事实**
>
> | | 只读（`read_only`） | 可修改（`read_write`） |
> |---|---|---|
> | 智能体能做什么 | 浏览、读取、搜索 | 另外可以新增、修改、删除、移动记忆 |
> | 平台能否拦截 | **能，硬拦截**：智能体写不进去 | **不能**：平台没有任何机制按设定拦截或审批写入内容 |
> | 写入前有无审核 | 不涉及 | **没有**：智能体写了就生效，并立即影响此后所有任务 |
> | 写错或被污染后 | 智能体不会写坏，但既有内容仍可能本身有误，或被维护方改错 | **没有历史版本可回溯**，只能人工改回或从备份重建 |
>
> 因此，选「可修改」时：
>
> - `inspector`、`inspect_cadence` 指的是**事后巡检**（定期检查记忆库里有没有不该有的内容），不是写入前的审批；
> - 智能体处理的不可信内容（用户上传、网页、第三方工具返回）可能被写入，并在此后被当作可信信息读取，风险由你们承担；
> - 必须说明 `backup_source`：内容丢失、被污染后，能从哪里恢复；
> - 如果只是想沉淀固定的规范或口径，请放进业务知识目录（始终只读），不要用可修改的记忆库；
> - 如果记忆内容可以由你们自己的程序来写，**优先让程序写入、智能体只读**，这是最稳妥的做法。

### 5.6 输入输出契约（`io/`）

**它是干什么的：** 契约用机器可读的方式写明"这位数字员工**收什么、产什么**"的结构，让调用方、验收和下游系统有统一的依据，而不是靠人读文字。具体用途：

| 谁用 | 怎么用 | 现在由谁执行 |
|---|---|---|
| 验收 | 平台执行验收用例时（9.2），按契约检查用例的输入是否合法、产出是否符合产物契约 | **平台**：验收阶段执行 |
| 调用方（飞书入口、网关、上游系统） | 按"输入契约"检查用户或系统给的材料是否齐全、格式是否对，缺什么先要求补，不浪费一次运行 | **业务方自己的调用方**：平台**暂不在运行时执行**这项检查 |
| 运行时质检 | 按"产物契约"检查产出的文件、数据是否符合约定的字段和格式 | **业务方自己的质检**（例如由某个子智能体或 Skill 承担）：平台**暂不在运行时执行**，也不自动退回不合格的产物 |
| 下游系统 | 按"产物契约"读取产出，知道文件在哪、字段是什么含义 | 下游系统自己读取契约 |
| 智能体之间 | `main` 向 `sub` 交接的内容、`sub` 回传的内容，也可以写成契约，避免两边理解不一致 | 作为文档与验收依据；运行时由提示词约束，**平台不校验交接内容** |

> **请注意：平台目前只在验收阶段按契约检查，运行时不会自动拦截不符合契约的输入或产出。** 需要运行时检查的，请在你们的调用方，或在智能体的提示词、Skill 里实现；这部分后续如果平台提供运行时校验，会在本节更新。

契约**不会**交给智能体当提示词：智能体怎么做事写在 `identity/`，契约只用来检查输入输出。平台也不把它映射成 MA 里的任何资源。

**什么时候需要写：** 数字员工有明确的结构化输入或产物（表格、固定字段的 JSON、固定章节的报告）才需要；纯自由对话可以不写，省略 `io/`。

**怎么组织：**

```text
io/
├── README.md                   # 导航：有哪些输入、产物；每个由哪个智能体产生、给谁用
└── contracts/
    ├── input.report-request.json      # 输入契约，一个输入一个文件
    └── output.weekly-report.json      # 产物契约，一个产物一个文件
```

- 命名建议 `input.<名称>.json`、`output.<名称>.json`；智能体之间的交接契约用 `handoff.<发出方>-<接收方>.json`；
- 使用 JSON Schema 描述，须写明：字段、类型、是否必填、示例、版本；
- 契约里所有表示"文件位置"的字段（如 `path`、`report_file`、交接 Context 里的 `inputs[].path`、`upstream_artifacts[].path`），要写明是**相对工作空间的相对路径**还是**绝对路径**，且**产生方与消费方必须用同一种口径**——例如 `main` 生成交接 Context 时写入的 `path`，要和 `sub` 回传结果里的 `path` 写法一致（都相对工作空间，或都绝对），否则下游对不上会误判为不一致；
- **产物契约**还要写明：产物类型（文件、表格、消息）、内容在哪里能找到、由哪个智能体产生、依据哪些输入。

产物契约示例：

```json
{
  "$id": "output.weekly-report",
  "version": "1.0.0",
  "description": "热点周报：一份 Markdown 报告 + 一份数据表",
  "produced_by": "insight",
  "type": "object",
  "required": ["report_file", "data_file", "period"],
  "properties": {
    "report_file": { "type": "string", "description": "报告文件名，位于产物目录，.md" },
    "data_file":   { "type": "string", "description": "数据表文件名，位于产物目录，.xlsx" },
    "period":      { "type": "string", "description": "统计周期，如 2026-W45" }
  },
  "examples": [{ "report_file": "weekly.md", "data_file": "weekly.xlsx", "period": "2026-W45" }]
}
```

**改契约要小心，因为别人是照着它在用的。** 契约一旦发布，调用方的检查程序、下游系统的读取程序、质检规则都是按它写的。契约里的字段变了，这些依赖它的地方可能就不能用了。所以改契约时要判断"别人原来的用法还能不能用"，这决定了智能体包的版本号怎么升（规则见 7.1）：

| 契约怎么改 | 原来的用法还能用吗 | 版本怎么升 |
|---|---|---|
| 新增一个**非必填**字段 | 能，没用到新字段的人不受影响 | 次版本 |
| 修改字段的说明文字、补充示例 | 能，行为没变 | 修订版本 |
| 新增一个**必填**字段（输入契约） | **不能**，原来的调用方没有传这个字段，会被拒绝 | 主版本 |
| 删除字段、改字段名、改字段类型（如字符串改成数字） | **不能**，下游按原字段读取会读不到或读错 | 主版本 |
| 把非必填改成必填，或收紧取值范围 | **不能**，原来合法的输入现在不合法 | 主版本 |

判断的办法：**拿改之前的一份合法输入或产物，放到改之后的契约里检查，还能通过，就是兼容的**（升次版本或修订版本）；通不过，就是不兼容的（升主版本）。

契约属于智能体包，随包的版本一起发布；需要升主版本的，请提前告知依赖它的调用方和下游。

### 5.7 提示词中的占位符

提示词里需要让智能体知道"业务知识在哪、输入资料在哪、产物放哪"时，**不能写运行环境的真实路径或资源编号**（例如 `/mnt/...`、记忆库编号）——它们只在构建时才产生，写死后环境一变就失效。因此用**占位符**：你们写占位符，平台在构建时替换成智能体能直接理解的文字。

**目前可使用四个占位符，分两组：**

**第一组：知识与记忆（写法完全对称）**

| 占位符 | 写什么 | 构建时替换成 |
|---|---|---|
| `{{knowledge:目录名/相对路径}}` | 业务知识中的**一个文件**（见 5.2）：`目录名` 是 `knowledge.yaml` 里声明的目录，`相对路径` 是该目录下的文件 | 该文件的完整路径，如 `/<记忆库编号>/统计口径.md`，附"使用记忆工具读取"（只读） |
| `{{memory:记忆库名/条目路径}}` | 长期记忆中的**一条记忆**（见 5.5）：`记忆库名` 是 `memory/stores.yaml` 里的 `name`，`条目路径` 是该库内的相对路径 | 该条记忆的完整路径，如 `/<记忆库编号>/客户偏好/A.md`，附"使用记忆工具读取"（只读库）或"使用记忆工具读写"（可写库） |

两个占位符的规则**完全一致**：

- 冒号后面都是"**容器名/相对路径**"，指向容器里的一个条目：知识的容器是已声明的知识目录，记忆的容器是已声明的记忆库；
- **只声明了一个容器时，容器名可以省略**：只有一个知识目录，`{{knowledge:统计口径.md}}` 即可；只有一个记忆库，`{{memory:客户偏好/A.md}}` 即可；声明了多个时必须带容器名；
- 同一个相对路径在多个容器里重复出现时，必须写成带容器名的形式，否则退回；
- 被引用的容器必须在**同一个包**里已声明，否则构建失败并退回；
- 都只能指向**包里已经提供的条目**：知识文件放在知识目录里，长期记忆的初始条目放在 `memory/<库>/…` 里。**运行中才由智能体写入的记忆条目，包里没有，不能用占位符引用**，需要引导智能体使用它时，用自然语言说明（例如"遇到客户偏好问题，先查阅长期记忆"）；
- 想让智能体了解某个记忆库整体的用途，同样用自然语言写在提示词里，不需要占位符。

**为什么要用占位符：** 业务知识和长期记忆在平台上都存放在"记忆库"里，智能体运行时是通过路径找到它们的，而路径的第一段是记忆库编号。编号要等记忆库创建出来才有，你们写提示词时不可能知道，所以由你们写占位符，平台在构建时填入真实路径。两类的区别只在于：业务知识始终只读，长期记忆按你们声明的权限读写。

**第二组：输入与产物位置**

| 占位符 | 指什么 | 构建时替换成 |
|---|---|---|
| `{{input}}` | **输入资料所在的目录**：用户或上游系统在这次任务里提供给智能体的文件 | 输入目录的真实路径（只读）。真实路径由平台在构建时生成，你们不需要知道；智能体读取时用文件名接在后面 |
| `{{output}}` | **正式产物要放的目录** | 产物目录的真实路径（可写）。真实路径由平台在构建时生成，你们不需要知道；放在这里的文件才会被平台作为产物收取 |

- `{{input}}` 目录是**只读**的：不要让智能体往里写；需要加工输入，让它在 `{{output}}` 或临时目录下另存一份；
- 只有放进 `{{output}}` 的文件才算产物。智能体写在别处的临时文件**不会**被保留（见 4.2）；
- 这两个占位符的值对整位数字员工的会话是同一个，`main` 和各 `sub` 看到的是同一对目录，所以 `main` 和 `sub` 可以通过它们交接文件；
- 任务具体收到了哪些输入文件，由调用方在创建会话时提供；提示词里只需要说清"去 `{{input}}` 里找什么样的文件"（例如"读取 `{{input}}` 下用户上传的周报数据表"）。

Skill、外部工具、子智能体**暂时没有占位符**：提示词里用自然语言描述即可（例如"交给热点分析子智能体"），仍然不要写真实路径。后续如增加占位符，会在本节更新。

写法示例（`main` 的 `orchestration.md`）：

```text
## 报告口径
- 周报结构按 {{knowledge:业务口径/周报模板.md}} 编写；
- 写作风格参考 {{memory:playbook/写作风格.md}}；
- 数据表从 {{input}} 读取，写好的周报放到 {{output}}。
```

规则：

- 占位符可以写在各智能体 `identity/` 的提示词里；`{{knowledge:…}}` 和 `{{memory:…}}` 也可以写在知识文件里（`{{input}}`、`{{output}}` 只能写在提示词里）。可复用能力自己的文件（`SKILL.md`、`scripts/`）不处理占位符；
- `{{knowledge:…}}`、`{{memory:…}}` 引用的条目必须真实存在于**同一个包**已声明的知识目录或记忆库里，否则构建失败并退回；一个智能体的提示词不能引用别的智能体包里的资源；
- 除上面四个之外的 `{{…}}` 一律退回，不要自创占位符；替换后文本里不会再残留 `{{`；
- `{{input}}`、`{{output}}` **不带参数**，在提示词里直接写；知识、记忆的两个占位符要带"容器名/相对路径"；
- 提示词里仍然不要直接写运行环境路径（以 `/mnt/`、`/workspace/` 开头），写了会被退回；
- **你们写的文字，平台只做占位符替换，不做其他改写**（顺序、标题、规则一字不动）；
- 回执会分开列出：你们写的原文、每个占位符替换后的结果、拼接后的完整系统提示词，便于逐项核对。

> 不要为了使用占位符而删减或改写已经确认的行为规则（安全、调试、验证等要求），只需要把写死的路径或编号换成占位符。

## 6. 可复用能力的登记

**需要被多位数字员工或多个业务线共同使用、并希望统一维护和升级的能力**（Skill、工具、成套的业务知识、模板、外部服务，以及需要被引用的智能体），必须登记到平台的**原子能力注册表**，各数字员工通过引用使用，不得各自复制。仅一位数字员工使用的，不必登记；多位员工各自保留副本且不要求统一升级的，也不必登记（见 2.2）。

### 6.0 能力从哪里来

可复用能力的**唯一信息源是平台的原子能力注册表**，登记和查询都以它为准。能力有三种来源，用标识的前缀区分：

| 标识形式 | 来源 | 你们能不能引用 |
|---|---|---|
| `platform.<名称>` | 平台提供的公共能力 | 可以，所有业务线都能引用 |
| `<你们的业务线ID>.<名称>` | 你们自己登记的能力 | 可以，并由你们负责维护 |
| `<其他业务线ID>.<名称>` | 其他业务线登记的能力 | 默认不可以；确需使用，须该能力提供方同意，由平台办理 |

标识格式为 `<提供方>.<名称>`，名称为小写字母、数字、连字符，登记后不可变更。

**查询：** 当前注册表放在飞书多维表格《原子能力注册表》：https://bluefocus.feishu.cn/base/ZRg5bp8lZavDRPsq9eQcp32UniO （分"能力""版本"两张表，业务方只读，访问权限向平台申请）；分析师研发环境直接读取这张表；用法见 6.4。
**登记：** 把 6.1 的各项内容提供给平台，由平台录入注册表；你们不直接改注册表。

### 6.1 登记哪些信息

| 字段 | 内容 | 填写要求 |
|---|---|---|
| 团队 | 提供团队 | 真实可联系 |
| 原子能力 | 名称与类型 | 类型：skill / tool / mcp / knowledge / template / agent（智能体包，见 2.3）。`knowledge`、`template` 被引用后的加载方式见 6.3 |
| 描述 | 何时用、做什么、输入输出 | 一到三句话，面向选用者 |
| 版本 | 语义化版本 | 主.次.修订 |
| 被谁引用 | 引用它的业务线、数字员工、智能体 | **由平台自动生成**，不用填 |
| 地址 | 能取回该版本确切内容的位置 | 仓库路径加提交，或对象存储位置加内容摘要；MCP 写服务地址；智能体包写压缩包链接加 SHA-256（见 2.6） |
| 责任人 | 主责任人、备份 | 各一名 |
| 依赖 | 依赖的其他能力及版本范围 | 没有写"无" |
| 所需凭证 | 凭证类型与用途 | 只写类型，不写值 |
| 变更说明 | 本版本改了什么 | 面向使用方 |

### 6.2 版本规则

| 变更 | 升哪一位 | 对引用方的影响 |
|---|---|---|
| 修复缺陷，行为兼容 | 修订 | 在引用方允许范围内，可批量升级 |
| 新增能力，向后兼容 | 次要 | 引用方按自己的版本范围决定是否纳入 |
| 不兼容变更 | 主要 | **不会自动纳入任何引用方**，每个引用方需评审后升级 |

- 同一版本发布后**内容不可变**，修改必须发布新版本；
- 下线前先标记"即将下线"，写明时间与替代能力，所有引用方迁移完成后才能下线。

### 6.3 在业务线中引用

在 `registry/skills.json`、`tools.json` 中声明：

```json
[
  { "id": "<能力标识>", "range": "^1.2.0" }
]
```

- `id` 必须是注册表里已登记的能力标识（取值见 6.4），不得自拟；
- `range` 表示接受的版本范围；具体使用哪个版本由平台在发布时锁定；
- 写在哪个智能体的包里，就由哪个智能体使用（见 2.3）；同一个能力被不同智能体引用时，各自按自己的 `range` 分别锁定版本；
- 不得把能力的内容复制进资源包。

#### 引用共享的知识和模板：`registry/knowledge.json`

注册表里登记的 `knowledge`（成套业务知识）和 `template`（业务内容模板）类型，**不是放进 `skills.json`**，而是写在 `registry/knowledge.json`。写法与 `skills.json` 一致（`id` + `range`），另外要给它起一个**目录名**：

```json
[
  { "id": "platform.report-glossary", "range": "^1.0.0", "as": "共享术语" },
  { "id": "zhilan.report-templates",  "range": "^2.1.0", "as": "共享模板" }
]
```

| 字段 | 说明 |
|---|---|
| `id`、`range` | 同 `skills.json`：注册表里的能力标识和可接受的版本范围 |
| `as` | 这份共享知识在**你们这位数字员工里**叫什么，相当于一个"知识目录名"。在同一个智能体包内不得与 `knowledge.yaml` 里声明的自有目录同名，也不得与其他引用重名 |

**加载方式：构建时，平台把该版本的内容写入这位数字员工自己的知识记忆库**，作用和你们自己 `knowledge.yaml` 声明的目录完全一样：

- 提示词里仍然用 `{{knowledge:共享术语/某文件.md}}` 引用（`共享术语` 就是上面的 `as`），文件名就是共享知识里的相对路径；
- **只读**，不能被智能体修改；
- **不跨数字员工共享**：每位数字员工各有一份自己的副本，版本固定在发布时锁定的版本，共享知识后续发布新版本不会自动影响已发布的数字员工；
- **占用同样的容量**：每个引用占一个知识记忆库名额（计入《MA Agent 搭建容量限制说明》L3），文件大小、数量同样受 L1、L2 约束；
- 共享知识的内容由提供方统一维护，你们**不要把它的内容复制进自己的包**；需要修改，请联系提供方发布新版本。

增量交付时，这类引用用记录类型 `shared_knowledge`：`add_entries: ["shared_knowledge:共享术语"]`，规则同其他记录（2.4）。

### 6.4 查询注册表里已有的能力

写资源包之前，先到注册表（见 6.0）查有没有现成的能力可以引用，避免重复建设。注册表**对你们只读**：你们能查询，登记和锁定由平台完成。

| 你需要的信息 | 在注册表里看哪里 |
|---|---|
| 有哪些能力、做什么、适用范围 | "能力"表：标识、类型、名称、描述、提供团队、责任人，以及适用领域、适用条件、不承接范围 |
| 能引用哪些版本 | "版本"表：只选状态为"已发布"的；"候选"只能用于开发和预发，不能用于生产 |
| 输入输出是什么 | "版本"表：输入概要、输出概要 |
| 该版本需要什么凭证、依赖什么 | "版本"表：所需凭证类型、依赖的其他能力 |
| 它是否即将下线 | "版本"表：状态为"即将下线"的写明替代版本，新引用请选替代版本 |

选好之后：

1. 在对应包的 `registry/skills.json`、`registry/tools.json` 里写 `id` 和 `range`（见 6.3）；
2. 写在**使用它的智能体所在的包**里（`main` 用的写在 `main` 的包，`sub` 用的写在 `sub` 的包）。

分析师研发环境会替你们完成查询和这两步写入（同样适用于查询已登记的智能体），查询入口和权限由平台提供。引用关系（被谁引用、锁定到哪个版本）由平台在构建时写入注册表，你们不需要、也不能自己登记引用。

### 6.5 可复用能力（Skill）的内容要求

| 项 | 要求 |
|---|---|
| 目录 | 只有一个顶层目录 `<能力名>/`，其下直接包含且仅包含一个 `SKILL.md`；可选 `scripts/`、`references/` |
| `SKILL.md` | 写清何时触发、做什么、输入输出、限制；描述具体到能判断"该不该用我" |
| 通用性 | 定义可复用的能力，不写一次性任务的具体数据 |
| 体量 | 受平台当前上限约束，见《MA Agent 搭建容量限制说明》 |
| 禁止项 | 密钥、令牌、个人账号；缓存与临时文件 |
| 运行自包含 | 脚本只能读本 Skill 自己 `scripts/`、`references/` 里的以及 `SKILL.md` 里写明的文件；**不得**依赖资源包的相对布局（如 `../registry/`、`../io/`、`../knowledge/`、`../skills/<其他 skill>/`），不得读 `registry/`、`io/contracts/`、`memory/` 这些平台**不会挂载进 Skill 运行沙箱**的内容。定位 Skill 内文件用「相对本 Skill 根」的路径；平台运行时把每个 Skill 独立挂载，不保留资源包布局 |
| 依赖 | 需要的包与工具写入 `registry/environment.json`，不得用脆弱的绕法掩盖环境缺失 |
| 自检 | 打包后重新解压并实际运行一遍，保留输出。**这只针对 Skill 包本身**，不能代替智能体包的验收（9.2） |

### 6.6 脚本怎么放（建议）

脚本不是单独的资源类型，也不单独登记。按**职能和粒度**决定它的归属，下面是建议：

| 脚本的情形 | 建议的做法 |
|---|---|
| 完成一项明确任务，有输入输出，或围绕一个任务的一组脚本 | 做成 **Skill**：脚本放在 `skills/<能力名>/scripts/`，`SKILL.md` 写清何时用。需要多个员工或业务线复用的，按第 6 章登记 |
| 只服务某个 Skill 的辅助脚本 | 留在该 Skill 的 `scripts/` 里，不单独登记 |
| 多个 Skill 共用的小工具函数 | 抽成一个"工具库 Skill"（`SKILL.md` 加 `scripts/`），各 Skill 引用它；不要在各 Skill 里各复制一份 |
| 通用、稳定、被多处导入的代码库 | 作为 **pip（或 npm）包**发布，在 `registry/environment.json` 的 `dependencies` 里声明版本下限，在运行环境初始化时安装。**内部镜像或自建包源能否在运行环境中使用，待平台确认**，确认前请先按"工具库 Skill"处理 |
| 本质是数据、口径、规则表（词典、映射表、正则清单） | 放进**业务知识**，不要写成脚本 |
| 只为某一次任务写的一次性脚本 | 不进入资源包，留在任务工作空间（第 4 章） |

**脚本文件命名与版本：**

- **文件名里不带版本或状态后缀**，如 `_v1`、`_v2`、`-v2`、`_old`、`_new`、`_copy`、`_final`、`_bak`；
- 版本只由所属 Skill（或包）的版本号和提交记录体现，包内每个脚本**只保留当前这一个版本**；
- 迭代中的草稿放在研发工作区，不放进交付的包；
- 确实需要两种行为并存时，**按行为命名**，如 `clean_strict.py`、`clean_loose.py`，不要用版本号区分；
- 行为不兼容的升级，通过 Skill 的主版本表达（见 6.2），不通过复制出 `xxx_v2.py`。

平台在接收时检查脚本文件名，出现上述后缀的退回。

## 7. 版本与变更

### 7.1 版本号

每个智能体包**各自**使用语义化版本（`主.次.修订`，如 `1.2.3`），增量交付沿用各自的版本号（见 2.4）：

| 变更 | 升哪一位 | 判断标准 |
|---|---|---|
| 提示词的职责边界改变、输入输出契约不兼容地改变（见 5.6）、移除能力 | **主版本** | 原来依赖它的人（调用方、下游、引用它的 `main`）可能不能照原样继续用 |
| 新增能力、新增知识、契约新增非必填字段 | **次版本** | 原来的用法不受影响，只是多了新东西 |
| 文案、案例、修复缺陷 | **修订版本** | 行为没变，只是更正确或更清楚 |

`main` 的版本还要反映它引用的 `sub` 的变化：

- **新增** `sub` 引用：次版本；**移除** `sub` 引用：主版本；修改 `role` 或 `visibility`：主版本；
- 纳入引用的 `sub` 的新版本：与该 `sub` 这次变更的级别相同（修订→修订，次要→次要，主要→主要）。

每个智能体的版本发布后**内容不可变**，规则同 6.2。

### 7.2 变更说明

每次交付更新，在 `registry/version_mapping.md` 记录：

```markdown
## 1.1.0 — YYYY-MM-DD
- 变更：<做了什么>
- 影响：<影响哪些任务、哪些使用方>
- 引用的可复用能力：<能力标识 旧版本 → 新版本>
- 验证：<跑了哪些用例，结果>
```

### 7.3 变更生效

业务线更新后，平台会评估影响并分阶段上线：先在测试环境验证，再灰度，最后全量。**进行中的任务保持原版本不变**，新任务使用新版本。

**三种"运行"不要混为一谈：**

| 运行 | 在哪里、由谁做 | 结论能用来说明什么 |
|---|---|---|
| Skill 打包自检（6.5） | 你们自己的沙箱或本地，解压后实际跑一遍 | 这个 Skill 包能跑通 |
| 智能体包验收（9.2） | **平台**在构建并映射到 MA 之后执行 | 这套 Agent 配置在真实环境里符合用例预期 |
| 生产灰度与全量（本节） | 平台按阶段上线 | 在真实用户下稳定 |

## 8. 安全要求

1. 资源包、登记信息、变更记录、日志、截图中**不得出现任何密钥明文**，只写名称、类型、引用；

### 9.2 验收用例

验收用例写在 `acceptance/cases.yaml`，**每个智能体包各自提供，各至少 3 个**，由业务方描述、业务方验收人判断是否合格。

> **验收的对象是"构建并映射到 MA 之后的环境"，不是你们本地的目录。** 你们**只负责写用例**；用例由平台在包被接收、构建、部署到 MA 之后执行，用的是真实的 Agent、真实的模型、真实的运行环境。所以：
>
> - **不需要**为验收另外做演示程序、演示页面、可视化脚本，也不要在本地手工"演一遍"业务流程；
> - 你们在本地能做的只有静态检查（目录、命名、引用是否合法，见 9.1）和 Skill 自己的打包自检（6.5），这两件事的结论不能当作验收结果；
> - 用例里的"预期结果"按**平台构建后会看到的**效果来写（例如"用户发一句话，pm 分派给 hotspot，返回一份报告"），不要写成"运行某个本地脚本的输出"。

```yaml
# acceptance/cases.yaml
cases:
  - id: AC-01
    title: 热点周报（正常流程）
    category: 正常                  # 正常 | 边界 | 失败 | 接续
    route: dispatch                 # direct：主智能体自己完成；dispatch：分派给子智能体并汇总
    agents: [pm, hotspot]           # 预期参与的智能体
    input: 提供 50 条样本数据文件，并发消息"出一份本周热点周报"
    expected: 在产物目录（`{{output}}`）产出 weekly.md 与 weekly.xlsx，字段符合 io/contracts/output.weekly-report.json；热点不少于 5 条，每条带数据来源
    acceptor: 张三（业务负责人）
  - id: AC-02
    title: 材料缺失时追问
    category: 失败
    route: direct
    agents: [pm]
    input: 只发消息"出一份周报"，不提供数据
    expected: 不分派、不产出报告，明确说明缺什么材料并请求补充
    acceptor: 张三
  - id: AC-03
    title: 容易误路由的需求
    category: 边界
    route: direct
    agents: [pm]
    input: "帮我写一段热点话术"（属于话术需求，不是热点分析）
    expected: 不分派给 hotspot，按话术口径直接回答或转给对应智能体
    acceptor: 李四
```

每个用例写明：

| 项 | 内容 |
|---|---|
| `title` | 一个具体、可重复的业务场景 |
| `category` | 正常、边界、失败、接续（长任务中断后恢复）之一 |
| `route`、`agents` | 这个用例走主智能体直接完成，还是分派给哪些子智能体 |
| `input` | 提供什么材料、说什么话 |
| `expected` | 期望的产物与质量要求，尽量写成可检查的条件 |
| `acceptor` | 谁来判断是否合格 |

**覆盖要求：**

- 至少覆盖正常、边界、失败（或接续）各一类，优先使用你们已有的业务样例；
- **`sub` 的用例单独执行**：平台把它当作独立智能体直接调用（用它自己的调试 bot），验证它自己的职责，不依赖任何 `main`；它的 `route` 一律写 `direct`，`agents` 写它自己；
- **`main` 的用例覆盖集成**：有引用子智能体的，至少有一个**分派给子智能体并汇总回来**的用例，以及一个**容易被误分派、实际应由主智能体或另一个智能体处理**的反例；
- **`route: dispatch` 的用例，验证的是"分层 agent 架构"在真实环境里成立**：入口智能体把任务分派给它引用的子智能体、子智能体完成自己的部分、结果回到入口智能体并汇总给用户。这要求**入口智能体与它引用的子智能体同时在同一个 MA 环境里可用**——这正是平台构建后才有、你们在本地无法复现的形态，所以这类用例**必须交给平台执行**，不要用本地脚本或页面模拟分派；
- 增量交付改动了某个智能体的，用例需覆盖被改动的智能体；改动的是 `sub` 并被 `main` 纳入新版本时，`main` 的集成用例要重新执行，并抽查一个未改动的场景确认没有退化；
- 修复 Skill 的，至少包含原来失败的用例和一个正常用例。

**执行与结论：** 平台执行用例；**有输入、产物契约的（5.6），平台会按契约检查用例的输入和产出是否符合**，并把检查结果写进回执。每个用例的结果包括：受检版本、实际使用的模型与环境、输入、预期、真实输出、执行时间、结论、证据位置。结论只有四种：**通过、失败、无结论、未执行**；没有实际运行过的用例必须写"未执行"，不能写"通过"。最终是否合格，由 `acceptor` 在回执上给出接受结论。

平台另行执行通用的冒烟检查（对话、命令执行、读取资料、产出文件、越界拒绝等）。
