# 业务运行时构建规范（Spec）

> 版本：v2.0 · 适用对象：中台研发、各业务方的接入研发
> 要回答的问题：**一个业务方的信息怎么组织？怎么映射到 MA 上？多个业务方共用同一个 MA 项目时如何互不干扰？可复用的原子能力怎么注册、被谁引用、怎么升级？**
> 配套文档：《能力需求收集表》（业务方填写）。

---

## 1. 定位与原则

### 1.1 这份规范解决什么cc c

中台在方舟 Managed Agents（MA）上同时承载多个业务方。规范要保证：

1. **业务方视角完整**：业务方只需要说清"信息归谁、怎么流转、用什么能力"，不需要了解 MA 的资源模型；
2. **映射可追溯**：业务信息落到 MA 的哪类资源、哪个字段，有唯一对应；
3. **多业务方互不干扰**：同名、同类资源、共用能力，在一个 MA 项目内能被区分、被治理；
4. **原子能力可复用**：可复用的最小能力（Skill、工具、知识、模板）统一注册，被谁引用、什么版本、怎么升级都可查；
5. **升级可控**：业务变化与 MA 平台升级，都能定位影响面并回滚。

### 1.2 分层

```text
┌─────────────────────────────────────────────────────────────────┐
│ 第一层  业务信息层   资源包 · 工作空间 · 信息归属 · 信息流转     （第 2、3 章）│
├─────────────────────────────────────────────────────────────────┤
│ 第二层  中台治理层   命名空间 · 原子能力注册表 · 引用与升级      （第 4、5 章）│
├─────────────────────────────────────────────────────────────────┤
│ 第三层  MA 映射层    信息 → MA 资源与字段 · 区分与定位          （第 6、7 章）│
├─────────────────────────────────────────────────────────────────┤
│ 第四层  运行与变更   版本 · 灰度 · 升级 · 安全 · 验收          （第 8 至 10 章）│
└─────────────────────────────────────────────────────────────────┘
```

业务方对接第一层；中台负责第二至四层。业务方不需要理解 MA 资源，但要接受中台第二层的命名与登记要求。

### 1.3 原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | 业务信息先行 | 先定义信息归属与流转，再映射到 MA 资源；MA 是承载，不是起点 |
| P2 | 信息唯一归属 | 每类信息只有一个事实源，其他位置只引用、不复制 |
| P3 | 稳定资源与运行实例分离 | 资源包只保存可复用的稳定内容；会话、任务、运行产生的实例信息不进资源包 |
| P4 | 命名空间隔离 | 每个业务方有唯一的命名空间，所有资源携带它，不依赖名称的偶然唯一 |
| P5 | 原子能力集中注册 | 可复用能力只在注册表登记一次，业务方按版本引用，不各自复制 |
| P6 | 以标识定位，不以名称定位 | MA 多数资源允许同名，一律靠元数据标识与注册表中的 ID 定位 |
| P7 | 密钥与配置分离 | 资源包与注册表只出现凭证的名称、类型、引用，不出现值 |
| P8 | 只读优先、变更可归因 | 初始化与启动阶段不修改既有资源；所有写入经评审、有版本、有记录 |
| P9 | 平台漂移显式化 | 记录依赖的 MA 版本，平台升级时靠比对发现差异 |

## 2. 业务信息层：资源包

每个业务方在每个业务线（Topic）下交付一个**资源包**，保存可跨项目、跨会话复用的稳定内容。

### 2.1 资源包目录

```text
<system-root>/
├── ma-resources-<TopicID>/            # 每个业务线一个资源包
│   ├── identity/                      # Agent 与内部子 Agent 的身份、编排、交接
│   │   ├── coordinator/               #   主 Agent
│   │   │   ├── identity.md
│   │   │   ├── orchestration.md
│   │   │   └── handoff.md
│   │   └── subagents/                 #   内部专业子 Agent
│   │       └── <name>.identity.md
│   ├── knowledge/                     # 业务知识：口径、标准、模板、案例、基准
│   │   ├── standards/                 #   生产与验收口径
│   │   ├── templates/                 #   业务内容模板
│   │   ├── examples/                  #   可复用案例（标准、边界、错误、回归）
│   │   └── glossary.md                #   术语表
│   ├── tools/                         # 外部能力契约：只写接口、用途、所需凭证类型
│   │   ├── _overview.md
│   │   └── <tool-name>.md
│   ├── skills/                        # 可直接执行的封装能力
│   │   └── <skill-name>/
│   │       ├── SKILL.md
│   │       ├── prompts/
│   │       ├── scripts/
│   │       └── references/
│   ├── io/                            # 输入输出契约
│   │   ├── README.md
│   │   └── contracts/                 #   机器可读的信息结构定义
│   └── registry/                      # 本资源包的登记与版本
│       ├── topic.json                 #   业务线 ID、版本、资源入口
│       ├── agents.json
│       ├── skills.json                #   引用的原子能力（格式见 5.5）
│       ├── tools.json
│       ├── environment.json           #   环境与凭证类型声明
│       ├── resources.lock.json        #   当前版本的资源锁定清单（7.5）
│       └── version_mapping.md         #   人可读的版本映射
├── ma-resources-ProjectAgent/         # 项目管家资源（统筹多个业务线时使用）
├── ma-resources-Validator/            # 独立质检资源
└── ma-workspaces/                     # 实际生产空间（2.3）
```

资源包之间在物理目录上相互并列，不互相包含。项目管家只登记各资源包的 ID、路径和版本引用。

规则：

- 业务线是否设置长期记忆由业务决策。需要的，在资源包中增加 `memory/` 并登记记忆库及读写权限（6.5）；不需要的不设置。
- `knowledge/templates/` 保存业务内容模板；可执行的提示词和脚本随具体 Skill 保存。
- `knowledge/examples/` 可包含标准、边界、错误、回归案例；某次任务的原始错误材料不直接进入这里。
- `registry/` 只保存资源登记与版本引用，不保存任务、运行或工具调用产生的实例 ID。
- 提示词引用知识时引用 `knowledge/` 中的文件，不在提示词里复制一份。

### 2.2 信息唯一归属

| 信息类型 | 唯一事实源 |
|---|---|
| 业务通用方法、字段、标准、模板、案例 | `ma-resources-<TopicID>/knowledge/` |
| Agent 与内部子 Agent 的定义 | `ma-resources-<TopicID>/identity/` |
| 质检定义与通用质检方法 | `ma-resources-Validator/` |
| 输入输出信息结构 | `ma-resources-<TopicID>/io/contracts/` |
| 外部能力的接口与所需凭证类型 | `ma-resources-<TopicID>/tools/` |
| 可复用的原子能力（Skill、工具、知识、模板） | **原子能力注册表**（第 5 章），资源包只引用 |
| 用户跨项目有效的个人上下文 | `personal/{user_id}/context/` |
| 个人连接信息与凭证引用 | `personal/{user_id}/connections/` |
| 项目事实、决定、长期记忆 | `projects/{project_id}/context/` |
| 项目长期原始资料与数据源 | `projects/{project_id}/sources/` |
| 项目连接信息与凭证引用 | `projects/{project_id}/connections/` |
| 密码、API Key、Token、Cookie、私钥等真实凭证 | 外部密钥存储，**不进入任何文件目录** |
| 任务实际采用的上下文 | `tasks/{task_id}/context/` |
| 任务明确绑定的输入 | `tasks/{task_id}/inputs/` |
| 任务目标、交付要求、当前有效结果 | `tasks/{task_id}/task.json` |
| 一次运行实际采用的输入、上下文、参数、资源版本 | `runs/{run_id}/run.json` |
| 一次执行或重试形成的过程文件、回执、日志 | `runs/{run_id}/attempts/` |
| 可引用、送检、交付的正式产物 | `runs/{run_id}/artifacts/` |
| 质检的送检信息、依据、证据、结果 | `runs/{run_id}/validation/` |
| 对外使用的导出、打包、发布内容 | `runs/{run_id}/delivery/` |

### 2.3 生产空间

```text
ma-workspaces/
├── personal/{user_id}/
│   ├── context/
│   ├── connections/                   # 只存连接名称、用途、目标系统、connection_id、secret_ref、连接版本
│   └── tasks/
└── projects/{project_id}/
    ├── project.json
    ├── context/                       # 项目事实与长期记忆
    ├── sources/                       # 项目原始资料
    ├── connections/
    ├── registry/
    └── tasks/{task_id}/
        ├── task.json
        ├── context/                   # 本任务采用的上下文
        ├── inputs/                    # 本任务绑定的输入
        └── runs/{run_id}/
            ├── run.json               # 本次执行的冻结清单
            ├── attempts/              # 执行过程、回执、日志
            ├── artifacts/             # 正式产物事实源
            ├── validation/            # 产物质检信息
            └── delivery/              # 产物交付版本
```

`connections/` 不得保存密码、API Key、Token、Cookie、私钥等可直接使用的凭证值。运行只在 `run.json` 中记录采用的 `connection_id` 与连接版本。

### 2.4 信息流转

```text
业务线稳定资源 ──────────────────────────────┐
个人上下文 ─┐                                 │
项目上下文 ─┼─→ Task Context                  │
项目资料 ───┘                                 │
                                              ↓
用户提交 + 项目资料 ─→ Task Inputs ────→ Run Specification
个人/项目连接引用 ──────────────────────→ Run Specification
                                              │
外部密钥存储 ──运行时解析真实凭证──→ Attempt    ↓
                                              ↓
                                           Artifact
                                   ┌──────────┴──────────┐
                                   ↓                     ↓
                              Validation             Delivery
                                   └──────────┬──────────┘
                                              ↓
                                       Task 当前结果索引
                                              ↓
                                       用户反馈与任务经验
                               ┌──────────────┴──────────────┐
                               ↓                             ↓
                         项目上下文                   业务知识更新候选
```

1. **项目登记**：基础信息写入 `project.json`；可跨任务复用的事实与决定归入 `context/`；原始资料归入 `sources/`。项目上下文不保存业务知识的副本，项目资料不保存某次任务的派生数据。
2. **任务归集**：`task.json` 保存目标、交付要求、所用业务线、当前有效运行的引用。任务实际采用的上下文与输入分别形成带来源与版本的集合。任务上下文是"本任务采用的版本"，不取代个人或项目上下文的事实源地位。
3. **运行冻结**：每次运行通过 `run.json` 固化采用的信息：任务、上下文集、输入集、业务线版本、资源锁定清单、参数、连接引用，以及 Agent、Skill、工具、模型、环境版本。任务后续变化不影响既有运行对原版本的引用。
4. **过程沉淀**：同一运行下每次真实执行或重试形成独立的执行记录，不覆盖此前记录。过程文件不是交付源；需要保留、复用、送检、交付的结果固化为产物。
5. **产物固化**：产物是运行的正式产物事实源，有唯一 ID，记录类型与内容定位、内容摘要、来源运行与执行记录、上游引用、所用业务线与契约版本。标准化、清洗、标注结果默认属于过程信息，只有需要跨阶段引用、质检、复用或交付时才固化为产物。
6. **质检**：以明确的产物 ID 与内容摘要为送检对象，不以文件名或"最新"推断。质检不复制、不修改业务产物。
7. **交付**：交付版本从已明确的产物集合中选择、导出、打包，并能回指 产物 → 质检结果 → 运行 → 任务 → 项目。交付件不是后续编辑的源文件，修改应回到产物重新生成。
8. **反馈沉淀**：只影响本次任务的保留在任务上下文；对同一项目后续任务有价值的，整理后进入项目上下文；可跨项目复用的方法、标准、案例，形成业务知识更新候选，走第 9 章变更流程。原始聊天、日志、失败文件、项目敏感材料不直接进入业务线资源包。

### 2.5 最小生产清单

| 清单 | 作用 |
|---|---|
| 业务线登记 / 资源锁定清单 | 确定业务线版本及稳定资源组合 |
| 任务记录 | 确定任务目标、要求、当前有效结果 |
| 上下文集 | 确定任务实际采用的上下文及来源 |
| 输入集 | 确定任务实际采用的输入及来源 |
| 连接绑定 | 确定本次采用的连接及外部凭证引用，不含凭证值 |
| 运行记录 | 冻结某次执行采用的全部版本与参数 |
| 执行记录 | 区分每次真实执行与重试产生的信息 |
| 产物清单 | 标识正式产物及来源关系 |
| 质检记录 | 关联被检产物、标准、证据、结果 |
| 交付清单 | 关联交付文件、来源产物、质检结果 |

这些清单可由 JSON、数据库记录或对象存储元数据承载；本规范只规定逻辑归属，不限定存储实现。

## 3. 业务方与中台的分工

业务方不具备中台的全局视角，因此规范把"需要全局视野的决定"划给中台，把"只有业务方知道的内容"划给业务方：

| 事项 | 业务方 | 中台 |
|---|---|---|
| 业务目标、使用对象、验收用例 | **提供并确认** | 汇总 |
| 业务知识：口径、标准、模板、案例、术语 | **提供并维护** | 审核结构与完整性 |
| 提示词的业务内容（角色、边界、方法） | **提供** | 审核并补充平台约束 |
| 需要访问的外部系统与凭证提供人 | **提供** | 判断凭证类型、登记、存入密钥存储 |
| 记忆库内容与读写权限 | **决策** | 提示风险、显式落地 |
| 命名空间、资源命名、元数据 | 使用中台分配的值 | **分配、校验、强制** |
| 模型、上下文长度、压缩策略 | 提出效果要求 | **选型并配置**（含成本与合规） |
| 沙箱依赖与资源规格 | 提出需要什么 | **评估冲突、锁定版本** |
| 可复用能力（Skill、工具） | 提出需求、贡献实现 | **统一登记、版本管理、引用治理** |
| 对象存储挂载与产物存储 | 提出需要保留什么 | **统一规划桶、前缀、保留期** |
| 平台版本、升级、灰度 | 被通知、配合验收 | **主导** |
| 额度、成本、监控 | 被告知 | **主导** |

收集表只向业务方收集"业务方知道的内容"。其余由中台按本规范补全，并写入业务方可见的清单，供确认。

## 4. 中台治理层：命名空间与多业务方兼容

### 4.1 为什么必须有命名空间

同一个 MA 项目内，各资源对"同名"的处理并不一致，因此**不能靠名称区分业务方**：

| 资源 | 同名再建 | 元数据 | 标签 | 按名称服务端过滤 |
|---|---|---|---|---|
| Agent | 允许，得到不同 ID | 支持 | 支持（`[{key, value}]`） | 支持 |
| Environment | **拒绝**（项目内名称唯一，返回冲突） | 支持 | — | **不支持** |
| Vault | 允许 | 支持 | — | **不支持** |
| Memory Store | 允许 | 支持 | — | 支持 |
| Skill | 以内容指纹区分版本 | — | — | — |

由此得到三条硬约束：

1. **Environment 的名称必须全项目唯一**，因此名称必须带命名空间前缀；
2. **Agent、Vault、Memory Store 允许重复，同名会造成静默混淆**（两个业务方各建一个同名 Agent，系统不会报错），因此**不得以名称作为定位依据**；
3. **列表接口不是可靠的查找手段**（部分资源不支持过滤；一个项目内资源数量已较多；列表也没有完整的分页标记），定位必须依赖注册表中记录的 ID。

### 4.2 命名空间

每个业务方由中台分配一个**命名空间** `<ns>`：

- 格式：小写字母、数字、连字符，3 到 24 位，全局唯一，分配后不可变更；
- 分配与回收由中台记录在注册表（第 5 章）；
- 业务线标识 `<business-line-id>` 在命名空间内唯一，资源完整标识为 `<ns>.<business-line-id>.<role>`。

### 4.3 资源命名

| 资源 | 名称规则 | 示例 |
|---|---|---|
| Agent | `<ns>-<business-line-id>-agent` | `acme-sales-agent` |
| Environment | `<ns>-<business-line-id>-env`（**必须唯一**） | `acme-sales-env` |
| Vault | `<ns>-<business-line-id>-vault` | `acme-sales-vault` |
| Memory Store | `<ns>-<business-line-id>-mem-<purpose>` | `acme-sales-mem-playbook` |
| Skill 展示名 | `<atomic-id>@<内容指纹前 12 位>` | `acme.sales-report@3a9c1e0b77d2` |
| Session 标题 | `<ns>/<business-line-id>/<task_id>` | `acme/sales/T-1024` |

名称仅用于人读。**程序定位一律使用元数据标识加注册表 ID。**

### 4.4 元数据与标签

所有顶层资源创建时必须携带以下元数据，值均为字符串：

| 键 | 含义 | 示例 |
|---|---|---|
| `ma-registry.namespace` | 命名空间 | `acme` |
| `ma-registry.business-line-id` | 业务线 ID（与注册表 `business_line_id` 一致） | `sales` |
| `ma-registry.role` | 资源角色：`agent` / `environment` / `vault` / `memory` / `skill` | `agent` |
| `ma-registry.owner` | 责任团队（与注册表一致） | `acme-data` |
| `ma-registry.managed-by` | 创建与维护它的工具或流水线 | `ma-build` |
| `ma-registry.spec` | 遵循的本规范版本 | `2.0` |
| `ma-registry.version` | 该资源对应的业务线发布版本 | `1.2.0` |
| `ma-registry.stage` | 环境阶段：`dev` / `staging` / `prod` | `prod` |

规则：

- Agent 同时写入标签 `[{"key":"ns","value":"<ns>"},{"key":"business-line-id","value":"<business-line-id>"}]`，用于 Agent 列表的快速检索；
- **更新元数据必须先读后合并**：更新是整体替换，只传部分键会丢失其余键；
- 描述（`description`）写人读说明与责任人联系方式，不承载程序依赖的信息；
- 元数据不得包含凭证、个人信息、业务敏感内容；
- 缺少任一必填元数据的资源视为"无主资源"，中台巡检时标记并通知责任团队。

### 4.5 定位与防误操作

资源查找的顺序：

1. 注册表中记录的资源 ID（主）；
2. ID 缺失或失效时，按元数据 `namespace` + `business-line-id` + `role` 筛选：Agent、Memory Store 可先用名称服务端过滤缩小范围，其余资源在客户端过滤全量列表；
3. 命中多个时**停止并报告冲突**，不得自行择一。

写入前必须校验目标资源的元数据命名空间与调用方一致，不一致一律拒绝。**不得按名称删除或覆盖资源**，只能按 ID 且校验命名空间后操作。

### 4.6 项目级与跨业务方共享资源

| 类别 | 处理 |
|---|---|
| 同一业务方多个业务线共用的资源 | 放入该命名空间的共享业务线 `<ns>.shared`，由业务线引用 |
| 跨业务方共用的能力 | 登记为原子能力（第 5 章），由中台持有，业务方按版本引用，不复制 |
| Memory Store 跨业务方共享 | **默认不允许**；确需共享的，由中台创建只读共享库，命名空间为 `platform`，业务方只能以只读方式挂载 |
| Vault 与凭证 | 永远按命名空间隔离，不跨业务方共享 |
| Environment | 一个业务线一个，不跨业务方共用 |
| 额度与并发 | 按命名空间统计；超限由中台限流 |

## 5. 中台治理层：原子能力注册表

### 5.1 什么是原子能力

可被多个业务线复用的最小能力单元：

| 类型 | 含义 | 承载形式 |
|---|---|---|
| `skill` | 可执行的封装能力（说明、提示词、脚本、参考资料） | MA Skill |
| `tool` | 外部能力契约（接口、用途、所需凭证类型） | `tools/` 契约文档，实际执行靠 MCP 服务或 Skill 脚本 |
| `mcp` | 远端 MCP 服务 | Agent 的 `mcp_servers` |
| `knowledge` | 业务知识包（标准、口径、模板、案例） | `knowledge/` 目录包 |
| `template` | 业务内容模板 | `knowledge/templates/` |
| `prompt` | 可复用的提示词片段 | 文本 |

业务线独有、不打算复用的内容不必登记，仍遵守第 2 章。

### 5.2 注册表字段

注册表是**唯一**记录"谁提供了什么能力、什么版本、被谁使用、在哪里"的事实源。每条原子能力版本一条记录：

| 字段 | 含义 | 规则 |
|---|---|---|
| `team` | 提供团队 | 责任团队，必须真实可联系 |
| `atomic_id` | 原子能力标识 | `<ns>.<name>`，全局唯一，创建后不可变 |
| `name` / `description` | 名称与描述 | 描述用一到三句话写"何时用、做什么、输入输出"，面向选用者 |
| `type` | 类型 | 见 5.1 |
| `version` | 版本 | 语义化版本 `主.次.修订` |
| `fingerprint` | 内容指纹 | 内容摘要，内容不变则指纹不变 |
| `address` | 能力地址 | 见 5.3 |
| `referenced_by` | 被谁引用 | 由中台自动维护，见 5.5，不由人工填写 |
| `owner` | 责任人 | 至少一名主责任人、一名备份 |
| `status` | 状态 | `draft` / `candidate` / `released` / `deprecated` / `retired` |
| `depends_on` | 依赖的其他原子能力及版本范围 | 用于计算影响面 |
| `compat` | 兼容性声明 | 所需 MA 版本、工具集类型、模型要求 |
| `credentials` | 所需凭证类型 | 只写类型与用途，不写值 |
| `changelog` | 本版本变更说明 | 面向使用方的升级说明 |
| `created_at` / `updated_at` | 时间 | 由系统记录 |

### 5.3 能力地址

`address` 必须能让中台**自动取回该版本的确切内容**，不依赖人工转交：

| 类型 | 地址形式 |
|---|---|
| `skill` | 源码仓库路径加提交；以及已上传到 MA 的 `skill_id` 与版本 |
| `tool` / `knowledge` / `template` / `prompt` | 仓库路径加提交，或对象存储的 `bucket` + `key` + 内容摘要 |
| `mcp` | 服务地址加协议版本；鉴权引用凭证名称，不含值 |

同一能力版本发布后**内容不可变**：修改内容必须发布新版本。

### 5.4 状态与生命周期

```text
draft ──提交评审──→ candidate ──验收通过──→ released ──计划下线──→ deprecated ──无引用且过保留期──→ retired
```

- `candidate` 仅用于 `dev`、`staging` 的业务线引用，不进入 `prod`；
- `released` 之后内容不可变；
- `deprecated` 必须写明下线时间与替代能力，并保留到所有引用方迁移完成；
- `retired` 前必须确认 `referenced_by` 为空。

### 5.5 引用关系

业务线通过 `registry/skills.json`、`tools.json` 等清单**声明引用**：

```json
{ "atomic_id": "platform.report-cover", "range": "^1.2.0", "pin": "1.2.3" }
```

- `range`：可接受的版本范围，决定哪些升级可以自动纳入；
- `pin`：当前实际使用的确切版本，写入资源锁定清单；
- 中台根据所有业务线的引用声明**自动反向生成** `referenced_by`，保证"被谁引用"实时准确；
- 业务线不得复制原子能力内容到自己的资源包，只能引用。

### 5.6 使用与升级

| 场景 | 处理 |
|---|---|
| 新增引用 | 在业务线清单声明 `atomic_id` 与 `range`；`plan` 校验兼容性、状态、凭证；`candidate` 不得进入 `prod` |
| 发布修订版本 | 兼容修复。落在引用方 `range` 内的，中台通知引用方，可批量升级 |
| 发布次要版本 | 向后兼容的新增。引用方按 `range` 决定是否纳入 |
| 发布主要版本 | 不兼容变更。**不会自动纳入任何引用方**，必须逐个业务线评审、灰度、改 `range` 后升级 |
| 影响面评估 | 发布前由中台基于 `referenced_by` 与 `depends_on` 计算受影响的业务线、Agent、会话 |
| 紧急修复 | 可标记强制升级，由中台批量更新并通知；仍沿用第 9 章灰度，不得跳过冒烟 |
| 下线 | 先 `deprecated`，通知所有引用方，迁移完成且过保留期后 `retired` |
| 回滚 | 引用方将 `pin` 回退到上一版本；已发布版本内容不可变，因此回滚总是安全的 |

升级只影响新建的会话与按第 9 章升级的存量会话；运行中的会话保持原版本。

### 5.7 注册表的承载

注册表可由数据库、配置仓库或平台服务承载，本规范只规定字段与规则。无论承载方式，必须满足：

- 字段完整（5.2）；
- 变更留痕：谁、何时、改了什么、为什么；
- 可按 `team`、`atomic_id`、`status`、被引用方检索；
- 业务线构建时可程序化读取。

## 6. MA 映射层：信息到资源

### 6.1 总映射

| 业务信息（第 2 章） | MA 资源 | 字段 / 落点 |
|---|---|---|
| `identity/`：角色、行为边界、提示词 | Agent | `system` |
| `identity/subagents/` | Agent（子 Agent） | 独立 Agent，或编排字段 |
| 模型选型 | Agent | `model.*` |
| `skills/`、引用的 `skill` 类原子能力 | Skill → Agent | Skill 版本 + `skills[]` |
| 引用的 `mcp` 类原子能力 | Agent | `mcp_servers[]` 与 `tools[] mcp_toolset` |
| `tools/` 契约 | 文档；实际执行由 MCP / Skill 脚本 | — |
| `knowledge/` | 不直接映射 | 被 Skill、提示词引用；需常驻的稳定知识可写入 Memory Store |
| `registry/environment.json` | Environment | `config.networking` / `packages` / `env` / `setup_script` |
| 凭证类型声明、`connections/` | Vault / Credential | 凭证（类型、`secret_name` 或 MCP 地址） |
| 记忆（如设置） | Memory Store | 记忆库 + 条目 |
| 任务输入、共享数据 | 会话资源 | `file`、`tos` |
| 产物存储 | Environment 或会话覆写 | `config.tos` |
| 运行冻结（`run.json`） | 会话 | 固定的 Agent 版本、资源挂载 |
| 个人 / 项目上下文 | 会话创建参数、消息 | 由网关装配，不直接映射资源 |

### 6.2 Agent

| 要点 | 规则 |
|---|---|
| 名称与元数据 | 按 4.3、4.4 |
| 模型 | 见下表 |
| 压缩策略 | `context_management`，创建会话时固定，修改只对新建会话生效 |
| 提示词 | `identity/` 的正文；摘要哈希写入锁定清单；不含密钥 |
| Skill 列表 | 整体替换语义，必须写完整数组；单个 Agent 最多 50 个 |
| MCP | 整体替换语义；鉴权走 Vault |
| 工具与权限 | 工具集类型以 `ma_runtime.toolset_type` 为准；逐项登记权限策略 |
| 更新 | 必须带当前 `version`；遇版本冲突须重新查询并合并，不得只自增版本号重试 |

**模型字段：**

| 字段 | 方舟模型 | 自带模型（BYOK Direct） |
|---|---|---|
| `id` | 方舟模型目录 ID | 客户模型的实际模型 ID |
| `provider` | — | 必填，网关名称 |
| `base_url` | — | 必填，完整服务地址（到 `/v1/chat/completions`），公网可达 |
| `protocol` | — | 必填，仅 `openai_chat_completions` 或 `anthropic_messages` |
| `token_limits` | — | 必填，三个值均为大于 0 的整数，按模型真实能力填写 |
| 鉴权 | 方舟 Key | 请求级：每次发送事件携带 `X-User-Model-Header-<原始 Header 名>`，不写入 Agent、Session 或清单 |

### 6.3 Environment

| 要点 | 规则 |
|---|---|
| 名称 | `<ns>-<business-line-id>-env`，**项目内唯一**，重复创建会被拒绝 |
| 依赖 | 必须显式锁定版本下限；未指定版本会装最新，构建不可重现 |
| 初始化脚本 | 以 `set -e` 开头；下载二进制必须校验 sha256；注明来源；多段用子 shell 隔离 |
| 环境变量 | 只放非敏感配置：时区、模型 ID、开关、非密钥地址 |
| 多业务方 | **一个业务线一个 Environment，不跨业务方共用**；依赖冲突不通过合并解决 |

**Key、Secret、Token、密码一律禁止放在 `env`**，应放 Vault 或由网关按请求注入。

### 6.4 Vault 与凭证

| 类型 | 适用 | 特点 |
|---|---|---|
| `mcp_oauth`、`static_bearer`、`mcp_static` | 访问 MCP 服务 | 创建时立即与 MCP 服务握手，服务不可达则创建失败 |
| `environment_variable` | 命令行、SDK、直接 API 调用 | 沙箱内是不透明占位符，出口处替换为真实值，Agent 看不到密钥 |
| `env_oauth` | 环境变量型 OAuth | 同上，按 `secret_name` 注入 |

- 同一 Vault 内，`mcp_server_url`（MCP 类）与 `secret_name`（环境变量类）必须唯一，重复创建返回冲突；
- 凭证密钥只写不读，创建后无法读回；认证类型创建后不可修改；
- 已挂载 Vault 的既有会话感知不到之后新增的凭证，新增后必须新建会话；
- Vault 按命名空间隔离，不跨业务方共用。

### 6.5 Memory Store

| 要点 | 规则 |
|---|---|
| 是否设置 | 业务决策 |
| 命名与元数据 | `<ns>-<business-line-id>-mem-<purpose>`，按 4.4 |
| 读写权限 | **逐个记忆库配置**，`read_only` 或 `read_write`；未配置的一律按 `read_only` |
| 下发方式 | 平台挂载时缺省为读写，因此**挂载时必须显式下发权限**，不得省略 |
| 选读写的 | 须登记写入内容类型与审核人、审核频率，因为 Agent 处理的不可信内容可能被写入，并在后续会话中被当作可信信息读取 |
| 提示词约束 | "不要写入"只是文字约束，**平台不会据此拦截**，权限以挂载设置为准 |
| 条目 | 一条一个文件，路径即记忆路径；单条不超过 100 KiB；单个库不超过 2,000 条 |
| 数量 | 单个会话最多挂载 10 个库 |
| 跨业务方 | 默认禁止，见 4.6 |

### 6.6 会话创建参数

| 要点 | 规则 |
|---|---|
| 记忆库 | `type: memory_store`，显式 `access` |
| TOS 目录 | `type: tos`：`tos_bucket` + `tos_key`，沙箱路径 `/mnt/session/storage/`，只读 |
| 输入文件 | `type: file`，单个会话最多 10 个，运行中可追加 |
| Vault | `vault_ids` |
| Agent 版本 | 灰度、复现、审计时固定版本 |
| 产物存储 | 创建会话时通过环境覆写 `config.tos` |
| 标题 | `<ns>/<business-line-id>/<task_id>`，便于检索与审计 |

**TOS 挂载与产物存储是两个独立配置：**

| | 配置位置 | 沙箱路径 | 用途 |
|---|---|---|---|
| TOS 资源挂载 | 会话 `resources[] type: tos` | `/mnt/session/storage/` | 输入或共享数据 |
| 产物存储 | `config.tos`：`bucket`、`prefix` | `/mnt/session/outputs/` | 交付物的持久位置 |

TOS 挂载规则：

- 一个会话可挂载多个 TOS 目录，完全相同的目录不能重复；
- `tos_key` 必须是以 `/` 结尾的目录，且该前缀下已存在对象，否则创建会话失败；
- 桶必须与 MA 服务同地域，并已在方舟项目中完成授权；
- 预检逐个目录进行，任一目录不可用，整个创建请求失败；
- `memory_store` 与 `tos` 只能在创建会话时挂载。

产物存储规则：

- 交付物需要长期保存的，**必须配置产物存储**；否则落在平台公共存储，到期被清理；
- 优先在创建会话时覆写，不修改可复用的 Environment；
- `bucket` 与 `prefix` 必须同时提供，`prefix` 以 `/` 结尾；
- **多业务方共用同一个桶时，前缀必须包含命名空间**：`<ns>/<business-line-id>/`，由中台统一规划；
- 写入前缀为 `{prefix}outputs/{env-id}/{session-id}/`；删除会话不会删除桶中对象，生命周期在对象存储中管理。

### 6.7 网关与渠道（MA 之外）

| 要点 | 规则 |
|---|---|
| 入口 | 单聊、群聊（群聊须 @ 机器人） |
| 可用范围 | 白名单，留空表示不限 |
| 飞书应用 | 一个业务线一个应用；权限与事件订阅登记在渠道清单；需订阅长连接接收消息事件，创建版本并发布后生效 |
| 模型鉴权 | 只登记 Header 名与持有人 |
| 会话映射 | 以（会话域、话题、用户）为键，保存会话 ID 与所用版本快照，不含凭证 |

## 7. 构建产物与定位

### 7.1 构建目录

资源包（第 2 章）是**业务信息**；构建产物是**把它编译成 MA 资源所需的声明**。

```text
ma-build/<ns>/<business-line-id>/
├── README.md
├── registry/
│   ├── manifest.yaml             # 主清单
│   ├── resources.lock.json       # 资源锁定清单（7.5）
│   ├── version_mapping.md
│   └── CHANGELOG.md
├── identity/                     # 从资源包 identity/ 编译
│   ├── agent.json
│   └── system.md
├── environment/
│   ├── environment.json
│   └── setup.sh
├── vault/
│   └── credentials.spec.yaml     # 名称、类型、用途、提供人、secret_ref；无值
├── memory/                       # 设置记忆时才有
│   ├── memory-store.json
│   └── <路径>/*.md
├── session/
│   └── session.yaml              # 挂载、权限、产物存储
├── channel/
│   ├── channels.yaml
│   └── gateway.env.example
└── verification/
    ├── smoke.md
    └── acceptance.md
```

### 7.2 主清单

```yaml
spec_version: 2
namespace: <ns>
business_line_id: <business-line-id>
version: 1.0.0
owner: { team: "", primary: "", backup: "" }

ma_runtime:
  docs_snapshot: "YYYY-MM-DD"
  toolset_type: agent_toolset_20260916
  base_agent: ark_agent_preview
  api_base: https://ark.cn-beijing.volces.com/api/v3
  region: cn-beijing

stage: dev                        # dev | staging | prod

resources:
  agent:       { name: <ns>-<business-line-id>-agent,  file: identity/agent.json }
  environment: { name: <ns>-<business-line-id>-env,    file: environment/environment.json }
  vault:       { name: <ns>-<business-line-id>-vault,  spec: vault/credentials.spec.yaml }
  memory:      []                  # 例：[{ name: <ns>-<business-line-id>-mem-<purpose>, access: read_only }]
  session:     { file: session/session.yaml }

atomic_refs:                      # 引用的原子能力，格式见 5.5
  - { atomic_id: platform.report-cover, range: "^1.2.0" }
```

### 7.3 编译与校验

`plan` 阶段必须通过以下校验，任一失败即阻断：

1. **命名空间**：所有资源名称、元数据、标题与 `<ns>` 一致；
2. **唯一性**：Environment 名称在项目内无冲突；元数据标识下同角色资源无多个命中；
3. **引用**：每个 `atomic_id` 存在、状态允许当前 `stage`、版本在 `range` 内、依赖可满足、所需凭证已在 Vault 声明；
4. **兼容**：原子能力的 `compat` 与当前 `ma_runtime` 相符；
5. **凭证**：清单与环境变量中无密钥明文；
6. **记忆**：每个挂载的记忆库权限已显式声明；
7. **数量**：未超平台上限（Skill 50、工具 128、环境变量 64、会话记忆库 10、会话文件 10）。

### 7.4 版本固定

业务线发布时，原子能力引用的 `range` 解析为确切的 `pin`，写入锁定清单。**没有锁定清单的业务线不得发布到 `prod`。**

### 7.5 资源锁定清单

锁定清单记录当前发布版本各资源的确切身份，是升级、回滚、`plan` 比对的依据：

```json
{
  "namespace": "<ns>", "business_line_id": "<business-line-id>", "version": "1.0.0", "stage": "prod",
  "ma_runtime": { "docs_snapshot": "YYYY-MM-DD", "toolset_type": "agent_toolset_20260916" },
  "agent":       { "id": "agent-…", "version": 3, "system_sha256": "…", "model_fp": "…" },
  "environment": { "id": "env-…", "config_sha256": "…" },
  "vault":       { "id": "vlt-…", "credentials": ["<name>"] },
  "memory":      [ { "id": "memstore-…", "access": "read_only", "entries_sha256": "…" } ],
  "atomic":      [ { "atomic_id": "platform.report-cover", "pin": "1.2.3", "fingerprint": "…", "skill_id": "skill-…" } ]
}
```

- 由 `apply` 生成并随发布提交，**不得手工编辑**；
- `plan` 将清单、锁定清单、平台现状三方对照；
- 资源 ID 只允许出现在锁定清单中，不出现在其他文件。

### 7.6 会话版本快照

灰度、复现问题、事后审计时，需要知道某个会话按什么版本运行。创建会话时固定 Agent 版本，并在网关侧记录：

```text
会话 = Agent 版本 + Environment + Vault + 记忆库及权限 + TOS 挂载 + 产物存储 + 原子能力 pin 列表 + 模型鉴权 Header 名称
```

该记录保存在网关侧，不写入资源包，不含凭证值。

## 8. 原子能力交付规范（Skill）

| 项 | 要求 |
|---|---|
| 目录 | ZIP 内只有一个顶层目录 `<skill_name>/`，目录下直接包含且仅包含 1 个 `SKILL.md`；可选 `scripts/`、`references/` |
| `SKILL.md` | 写清何时触发、做什么、输入输出、限制；描述具体到模型能判断"该不该用我" |
| 通用性 | 定义可复用能力，不写一次性任务的具体数据 |
| 体量 | 不超过 500 个文件；上传原始总大小不超过 30 MiB；解压后单文件不超过 30 MiB、总计不超过 120 MiB |
| 版本指纹 | 内容变化即新版本；重新打包同样内容不得产生新版本 |
| 禁止项 | 硬编码密钥、令牌、个人账号；缓存与临时文件 |
| 依赖声明 | Skill 需要的包与工具登记在 `compat` 与业务线 Environment，不得用脆弱的绕法掩盖环境缺失 |
| 自检 | 打包后重新解压并实际运行 |
| 登记 | 发布前必须在注册表登记（第 5 章），业务线通过引用使用 |

## 9. 变更、版本与升级

### 9.1 变更类别与对已有会话的影响

| 类别 | 变更内容 | 对已有会话的影响 | 上线方式 |
|---|---|---|---|
| A | Agent：模型、提示词、工具、MCP、Skill 引用 | 不自动切换。须对处于空闲且上一轮正常结束的会话调用升级，或新建会话 | 新建会话固定新版本灰度，再升级存量 |
| B | Environment：依赖、脚本、环境变量、网络、产物存储 | 同 A | 同 A |
| C | Vault：新增或修改凭证 | 既有会话感知不到新增凭证 | 新建会话 |
| D | 会话资源：记忆库、TOS（含权限） | 只能在创建时挂载 | 新建会话 |
| E | 文件资源 | 运行中可追加 | 即时 |
| F | 原子能力版本 | 不直接影响；须更新引用并随 A 上线 | 随 A |
| G | 网关配置 | 不影响 MA 资源 | 重启网关 |
| H | 模型请求鉴权 | 不影响 MA 资源 | 重启网关 |
| I | 飞书应用权限与事件订阅 | 无 | 创建版本并发布后生效 |
| J | 注册表：原子能力状态、引用关系 | 无直接影响 | 按 5.6 |

补充约束：

- 升级会话不能换绑其他 Agent 或 Environment；同一会话不能同时存在多个升级请求，且须先处于空闲；
- 不再使用的 Agent、Environment、会话优先归档，归档后保留配置与历史，已有会话继续使用创建时的快照；删除前必须确认无关联会话。

### 9.2 变更流程

1. **变更说明**：写明类别（A 至 J）、涉及的清单与原子能力、预期影响面；
2. **`plan`（只读）**：把清单、锁定清单、平台现状三方对照，并执行 7.3 校验；差异须与变更说明一致；
3. **评审**：至少一名非作者；涉及密钥、网络、外发、产物存储、跨业务方共享的须安全评审；
4. **`apply` 到 `dev`**，通过后晋级 `staging`，再到 `prod`，不得跳级；
5. **冒烟**：执行 `verification/smoke.md`，保留真实输出；
6. **灰度**：新建会话固定新版本验证，再升级存量空闲会话；运行中的会话记入待升级清单，不强行中断；
7. **回写**：`apply` 重新生成锁定清单，更新 `CHANGELOG.md`、`version_mapping.md`、注册表。

**回滚：** 以上一发布版本的锁定清单为目标：Agent 回退到其记录的版本；原子能力将 `pin` 回退；Environment 用上一版清单重新 `apply`。回滚同样走灰度。

### 9.3 版本与指纹

- 业务线版本语义化：A、B、C 类不兼容变更升主版本；新增能力升次版本；仅文案、记忆、修复升修订版本；
- 指纹：Agent 模型配置指纹、原子能力内容指纹、提示词摘要，均写入锁定清单，`plan` 时比对；
- 变更记录条目：

```markdown
## 1.1.0 — YYYY-MM-DD
- 类别：A, F
- 变更：<做了什么>
- 原子能力：platform.report-cover 1.2.3 → 1.3.0
- 影响面：存量空闲会话需升级；运行中会话记入待升级
- 验证：smoke.md 用例 1-8 通过
- 回滚：Agent 回退到上一版本；pin 回退
```

### 9.4 MA 平台升级

平台升级（文档合集变化、接口、字段、工具集类型、术语）时，不等故障出现：

1. **同步文档**：执行文档同步脚本，贴出标题、类型、字段名的变化；
2. **比对**：核对 `ma_runtime` 与各清单、各原子能力 `compat` 中的类型、字段、接口路径，是否仍出现在最新文档中；
3. **分级**：
   - **兼容**：一致，只更新 `docs_snapshot`；
   - **漂移**：使用的类型或字段已不在最新文档中。在 `dev` 新建会话验证旧值是否仍可用、行为是否一致，再决定升级时机，不得凭文档推断；
   - **破坏**：旧值被拒绝或行为改变。按 A、B 类走完整流程，并通过 `referenced_by` 找出所有受影响的业务线与原子能力；
4. 更新 `ma_runtime`，执行 9.2；
5. 评估架构图谱文档是否需要同步。

## 10. 安全红线与验收

### 10.1 安全红线（违反即驳回）

1. 资源包、清单、注册表、PR、日志、产出文件中不得出现任何密钥明文，只写名称、类型、引用；
2. Environment 的 `env` 不得存放密钥；
3. 初始化与启动阶段只读：不得更新、删除、重建已存在的资源；
4. 不得按名称删除或覆盖资源；写入前必须校验命名空间；
5. 不得对生产资源先删后建；需要重建时先归档、再新建、再切换；
6. 记忆库的读写权限逐个声明、默认只读，挂载时显式下发；
7. 跨业务方不得共享 Vault、Environment、可写记忆库；
8. 测试资源使用独立阶段标识并登记，仅按精确 ID 清理；正式资源不进入清理范围；
9. 业务数据进入模型的范围必须与业务方确认的结论一致；
10. 文档与脚本里的启动命令必须写明解释器与环境，不得依赖全局安装的同名命令。

### 10.2 `plan` 报告必含

- 清单与平台现状的差异，按资源、字段列出；
- 7.3 校验结果；
- 漂移项（平台上有、清单里没有）与无主资源；
- 缺失的凭证与待补充项，标记待补，对应项不创建，不得用占位值替代；
- 对存量会话的影响：可升级、需新建、待升级；
- 受影响的引用方（来自注册表）。

### 10.3 冒烟用例最低要求

| # | 用例 | 通过标准 |
|---|---|---|
| 1 | 单聊发一句话 | 收到回复，会话创建成功 |
| 2 | 触发一次沙箱命令 | 真实命令输出，不是文字复述 |
| 3 | 读取 TOS 挂载目录 | `/mnt/session/storage/` 下能列出预期文件 |
| 4 | 读取记忆库，并尝试写入 | 能引用记忆；写入按权限被允许或拒绝，与清单一致 |
| 5 | 调用每个已接入的 MCP 与外部系统 | 每个至少成功一次 |
| 6 | 产出一个文件到 `/mnt/session/outputs/` | 能取回；配置了产物存储后，桶中对应前缀下能找到对象 |
| 7 | 越界请求（索要密钥、无关泛聊） | 拒绝并引回职责 |
| 8 | 命名空间校验 | 资源元数据与命名空间一致；用另一命名空间的标识操作被拒绝 |

### 10.4 合入前检查单

- [ ] 业务信息符合第 2 章，唯一归属无重复副本；资源包内无会话 ID、任务 ID 等实例信息

- [ ] 引用的原子能力均已登记，状态与版本范围合法，`pin` 已写入锁定清单

- [ ] 无密钥明文（含环境变量、日志、截图）
