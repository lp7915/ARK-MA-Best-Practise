> **定位：** 当前 MA 底座对资源包有一些容量上限。这些上限由平台底座决定，不是业务设计的要求。平台会**逐项在平台侧解决**，解决后业务方无需任何改动（对业务方透明）。本文记录每一项限制当前的数值、触及时怎么办、以及解决进度，供业务方规划时查阅。
> **怎么用：** 正常按知识本身的粒度组织资源包，通常不会触及这些上限。触及时按"临时处理"一栏调整；以后某项限制被平台解决，会在本文更新状态，交付规范正文不需要为此修订。

## 1. 当前限制一览

| 编号 | 限制项 | 当前数值 | 触及时的表现 | 状态 |
|---|---|---|---|---|
| L1 | 单个知识文件大小 | ≤ **100 KiB**（102,400 字节） | 构建失败并退回，指出超限文件 | 待平台解决 |
| L2 | 单个知识目录的文件总数 | ≤ **1,990 个**（含各级子目录；平台另生成少量索引文件，已预留） | 构建失败并退回，指出超限目录 | 待平台解决 |
| L3 | 知识目录数 + 长期记忆库数（合计，一位数字员工，**含它引用的全部子智能体各自声明的，以及 `registry/knowledge.json` 引用的共享知识（每个引用占 1 个）**） | ≤ **10 个** | 构建失败并退回，列出两类各自数量 | 待平台解决 |
| L4 | 单条长期记忆大小 | ≤ **100 KiB** | 构建失败并退回 | 待平台解决 |
| L5 | 单个长期记忆库条目数 | ≤ **2,000 条** | 构建失败并退回 | 待平台解决 |
| L6 | 可复用能力（Skill）整体体量 | ≤ 500 个文件；上传总大小 ≤ 30 MiB；解压后单文件 ≤ 30 MiB、总计 ≤ 120 MiB | 打包或上传失败 | 待平台解决 |
| L7 | 一个主智能体引用的子智能体数 | ≤ **20 个**（MA 平台限制） | 构建失败并退回 | 待平台确认是否可放宽 |

> 状态取值：`待平台解决` → `方案评估中` → `已解决`（解决后该行数值失效，标注生效日期）。

## 2. 触及时的临时处理

平台**不会自行切分文件或拆分目录**。解决前，由业务方按知识的自然边界调整，**无需向平台说明拆分原因**：

| 限制 | 临时处理 |
|---|---|
| L1 单文件超限 | 这份文件承载了多件事：按主题拆成多个文件，每个文件仍写明名称、适用范围、版本、负责人；原先引用它的地方改为引用拆分后的各文件 |
| L2 目录文件数超限 | 目录涵盖的主题太宽：按主题划分为多个知识目录，在 `knowledge.yaml` 中分别声明；逻辑引用按新目录名更新（多目录写成 `目录名/相对路径`） |
| L3 合计数量超限 | 每个已声明的知识目录占 1 个名额，每个长期记忆库占 1 个名额。先合并主题相近的目录；确实无法合并的，请在交付前与平台团队沟通，不要等到构建失败才发现 |
| L4 / L5 记忆超限 | 按记忆的自然分类拆成多个记忆库（同样占用 L3 的名额） |
| L6 Skill 超限 | 精简内容，把大体量的数据文件改为业务知识或外部存储引用 |
| L7 子智能体数超限 | 合并职责相近的子智能体；或拆成两位数字员工 |

**规划提示（L3）：**

| 例子 | 知识目录 | 长期记忆库 | 合计 | 是否合规 |
|---|---|---|---|---|
| 常规 | 3 | 2 | 5 | 是 |
| 临界 | 8 | 2 | 10 | 是 |
| 超限 | 9 | 2 | 11 | **否，构建失败并退回** |

规划时先数一下已有的长期记忆库，再决定知识目录的数量。**`main` 引用了 `sub` 的，要把每个 `sub` 包里声明的知识目录和长期记忆库一起算进去**（它们会合并到同一位数字员工的会话里）。按主题粒度合理划分，不要为了整理方便建很多小目录。

## 3. 平台的解决方式（对业务方透明）

平台会逐项评估，用对业务方不可见的方式承载，使业务方不需要为这些上限调整资源包结构。业务方交付物的格式与逻辑引用写法**保持不变**。

| 限制 | 方向（评估中，未承诺时间） |
|---|---|
| L1 单文件 | 平台侧透明分片，逻辑引用仍指向原文件 |
| L2 目录文件数 | 平台侧按目录透明分库，逻辑引用不变 |
| L3 合计数量 | 评估其他承载方式（例如多个知识目录合并承载、按需挂载） |
| L4 / L5 | 同 L1 / L2 的思路 |
| L6 | 与 Skill 市场的包体量规则对齐 |
