## 9. 验收

### 9.1 交付检查单

- [ ] 压缩包按 2.6 命名（`<业务线ID>-<数字员工ID>-<智能体ID>-<版本>.zip`）；链接无需登录即可下载、永久有效；已提交 SHA-256 且与压缩包一致；解压后只有 `<业务线ID>/<数字员工ID>/<智能体ID>/` 一个顶层目录，不含符号链接、密钥、缓存
- [ ] 目录为 `<业务线ID>/<数字员工ID>/<智能体ID>/`，三级 ID 格式合法且与 `registry/agent.json` 的 `id` 一致
- [ ] 目录结构符合第 2 章，`identity/identity.md`、`registry/agent.json` 齐全
- [ ] 每类信息只在唯一位置出现，无重复副本；包内无任务、会话、运行产生的编号
- [ ] 各智能体 `identity/` 的文件内标题从二级开始，同一规则不重复、不矛盾，`handoff.md` 中的角色均有定义
- [ ] 提示词与知识文件中引用知识一律使用逻辑引用，无运行环境绝对路径，引用的文件均存在于已声明的知识目录，多目录同名路径已带目录名
- [ ] 业务口径、标准、模板、案例、术语已放入业务知识目录，并已在 `knowledge.yaml` 中声明（只使用默认 `knowledge/` 时可省略）；每个文件带适用范围、版本、负责人
- [ ] 资源规模未超过《MA Agent 搭建容量限制说明》中的当前上限；知识按主题粒度组织，不为凑容量硬拆
- [ ] `registry/agent.json` 的 `role`、`visibility` 已填写；同一位数字员工里有且仅有一个 `role: main`；`main` 有 `registry/agents.json`，其中每个引用的 `id` 都存在、`role` 为 `sub`、`range` 合法、范围内有已发布的版本；**`sub` 没有 `registry/agents.json`，`main` 没有被任何智能体引用**；**`sub` 的 `visibility` 是 `internal`**（层数不超过一层）；`main` 的提示词中提到了每个子智能体的别名（平台只检查是否提及，分派规则是否合理由评审判断）
- [ ] `sub` 的提示词中没有写死具体的主智能体或数字员工名称；`visibility: internal` 的智能体（所有 `sub`，以及选择 `internal` 的 `main`），生产环境的渠道没有配置成"不限使用范围"
- [ ] 脚本文件名没有 `_v1`、`_old` 等版本或状态后缀，包内每个脚本只有当前版本
- [ ] 增量交付的：`change-set.yaml` 齐全，新增、修改、删除（记录与文件）都已显式登记，登记与增量包的实际内容一致；登记了 `prompt:identity` 的，提示词文件成套给出（没改动的也原样给出）；`base_version` 为最新已发布版本
- [ ] `registry/environment.json` 依赖均写明版本下限；环境变量无敏感内容
- [ ] `connections.yaml` 每条连接写明域名、变量名、提供人，无任何凭证值
- [ ] 需要长期记忆的，每个记忆库已逐个决策权限；选可修改的已写明内容类型、巡检人、巡检频率与备份来源，并已知悉平台不拦截写入、无历史版本可回溯
- [ ] 可复用能力已登记，字段完整、地址可取回
- [ ] `acceptance/cases.yaml` 至少 3 个用例，覆盖正常、边界、失败（或接续）；有子智能体的含分派用例与误路由反例
- [ ] 引用其他能力的，`id` 取自注册表，已写明版本范围，写在使用它的智能体所在的包里，没有复制内容
- [ ] 无密钥明文
- [ ] 版本号与变更说明已更新

### 9.2 验收用例

验收用例写在 `acceptance/cases.yaml`，**每个智能体包各自提供，各至少 3 个**，由业务方描述、业务方验收人判断是否合格。

> **验收的对象是"构建并映射到 MA 之后的环境"，不是你们本地的目录。** 你们**只负责写用例**；用例由平台在包被接收、构建、部署到 MA 之后执行，用的是真实的 Agent、真实的模型、真实的运行环境。所以：
>
> - **不需要**为验收另外做演示程序、演示页面、可视化脚本，也不要在本地手工"演一遍"业务流程；
> - 你们在本地能做的只有静态检查（目录、命名、引用是否合法，见 9.1）和 Skill 自己的打包自检（6.5），这两件事的结论不能当作验收结果；
> - 用例里的"预期结果"按**平台构建后会看到的**效果来写（例如"用户发一句话，pm 分派给 hotspot，返回一份报告"），不要写成"运行某个本地脚本的输出"。

```yaml
# acceptance/cases.yaml
cases:
  - id: AC-01
    title: 热点周报（正常流程）
    category: 正常                  # 正常 | 边界 | 失败 | 接续
    route: dispatch                 # direct：主智能体自己完成；dispatch：分派给子智能体并汇总
    agents: [pm, hotspot]           # 预期参与的智能体
    input: 提供 50 条样本数据文件，并发消息"出一份本周热点周报"
    expected: 在产物目录（`{{output}}`）产出 weekly.md 与 weekly.xlsx，字段符合 io/contracts/output.weekly-report.json；热点不少于 5 条，每条带数据来源
    acceptor: 张三（业务负责人）
  - id: AC-02
    title: 材料缺失时追问
    category: 失败
    route: direct
    agents: [pm]
    input: 只发消息"出一份周报"，不提供数据
    expected: 不分派、不产出报告，明确说明缺什么材料并请求补充
    acceptor: 张三
  - id: AC-03
    title: 容易误路由的需求
    category: 边界
    route: direct
    agents: [pm]
    input: "帮我写一段热点话术"（属于话术需求，不是热点分析）
    expected: 不分派给 hotspot，按话术口径直接回答或转给对应智能体
    acceptor: 李四
```

每个用例写明：

| 项 | 内容 |
|---|---|
| `title` | 一个具体、可重复的业务场景 |
| `category` | 正常、边界、失败、接续（长任务中断后恢复）之一 |
| `route`、`agents` | 这个用例走主智能体直接完成，还是分派给哪些子智能体 |
| `input` | 提供什么材料、说什么话 |
| `expected` | 期望的产物与质量要求，尽量写成可检查的条件 |
| `acceptor` | 谁来判断是否合格 |

**覆盖要求：**

- 至少覆盖正常、边界、失败（或接续）各一类，优先使用你们已有的业务样例；
- **`sub` 的用例单独执行**：平台把它当作独立智能体直接调用（用它自己的调试 bot），验证它自己的职责，不依赖任何 `main`；它的 `route` 一律写 `direct`，`agents` 写它自己；
- **`main` 的用例覆盖集成**：有引用子智能体的，至少有一个**分派给子智能体并汇总回来**的用例，以及一个**容易被误分派、实际应由主智能体或另一个智能体处理**的反例；
- **`route: dispatch` 的用例，验证的是"分层 agent 架构"在真实环境里成立**：入口智能体把任务分派给它引用的子智能体、子智能体完成自己的部分、结果回到入口智能体并汇总给用户。这要求**入口智能体与它引用的子智能体同时在同一个 MA 环境里可用**——这正是平台构建后才有、你们在本地无法复现的形态，所以这类用例**必须交给平台执行**，不要用本地脚本或页面模拟分派；
- 增量交付改动了某个智能体的，用例需覆盖被改动的智能体；改动的是 `sub` 并被 `main` 纳入新版本时，`main` 的集成用例要重新执行，并抽查一个未改动的场景确认没有退化；
- 修复 Skill 的，至少包含原来失败的用例和一个正常用例。

**执行与结论：** 平台执行用例；**有输入、产物契约的（5.6），平台会按契约检查用例的输入和产出是否符合**，并把检查结果写进回执。每个用例的结果包括：受检版本、实际使用的模型与环境、输入、预期、真实输出、执行时间、结论、证据位置。结论只有四种：**通过、失败、无结论、未执行**；没有实际运行过的用例必须写"未执行"，不能写"通过"。最终是否合格，由 `acceptor` 在回执上给出接受结论。

平台另行执行通用的冒烟检查（对话、命令执行、读取资料、产出文件、越界拒绝等）。

## 附录：收集表与交付物的对应

| 收集表内容 | 对应交付物位置 |
|---|---|
| 基本信息 | `registry/agent.json` |
| 提示词、角色与边界 | 各智能体包的 `identity/` |
| Skill 列表与附件 | `skills/`、`registry/skills.json`（可复用的见第 6 章） |
| 外部服务（MCP） | `tools/`、`connections.yaml` |
| 运行环境：依赖、网络、环境变量、初始化需求 | `registry/environment.json` |
| 外部系统凭证 | `connections.yaml` |
| 长期记忆与读写权限 | `memory/`、`memory/stores.yaml` |
| 业务口径、标准、模板、案例 | 业务知识目录、`knowledge.yaml` |
| 输入材料与产物的结构 | `io/contracts/`（5.6） |
| 智能体的角色、可见范围、子智能体引用 | `registry/agent.json`（2.3）、`main` 的 `orchestration.md` |
| 增量变更 | `change-set.yaml`（2.4） |
| 验收用例 | `acceptance/cases.yaml`（9.2） |

模型选型、资源命名、依赖版本锁定、存储规划、版本上线节奏由平台统一设计，不在业务方的交付范围内。
